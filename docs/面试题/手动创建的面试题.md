### 程序员在自建 RAG 里实际做什么
1. 文档接入 ：解析 PDF、Word、HTML、Markdown，处理图片、表格、扫描件；
2. 清洗与切片 ：按标题层级切、按语义切、设置重叠、加章节上下文，让切片可检索；
3. 索引 ：调用嵌入模型批量转换、管理维度、版本、重建，控制失败重试；
4. 检索 ：向量检索加关键词检索混合、重排、相似度阈值、按权限和时间过滤；
5. 生成 ：提示词设计、引用来源、答不上来时拒答、结构化输出校验；
6. 评测 ：建问题集，量召回率和答案准确率，每次改策略都跑回归；
7. 工程化 ：异步任务、限流、缓存、成本核算、调用日志、审计；
8. 权限与多租户 ：谁能看哪份文档，检索结果必须按权限裁剪；
9. 业务集成 ：接工单、客服、内部搜索，把问答嵌进真实流程。
这些没有现成产品能直接交付，因为每家的文档结构、权限模型、业务问题都不同。把“文档变成能查的资料”这件事做准，才是真功夫。



为什么在正是提问前使用改写：
当前没有查询改写，因为菜谱是全量注入，模型自己能看到目录和历史，指代理解交给了模型；知识库检索目前只是后台测试工具，运营输入的问题本身比较完整。缺点是两处：多轮追问时后端的条件解析会失效，同义词检索也不稳定。数据量上来、改成检索召回后，改写会变成必需的一步：先把追问补全成独立问题、做同义词归一，再走向量检索，改写失败退回原句。代价是多一次模型调用，需要用小模型和缓存控制成本。


提问最开始的意图分类：“当前没有显式意图分类，意图判断放在系统提示词里交给模型：一般问题返回空`recipeIds` ，推荐才返回编号。单场景下这样够用，但代价是闲聊也带全量目录、兜底不分意图、条件解析会把提问误判成条件。要规模化的话会加两层分类：规则或小模型做粗分类，大模型做细分类并给置信度；按意图路由到不同链路——闲聊不注入目录、做法问题走知识库检索、推荐才走菜谱校验。分类结果要落日志，才能评估准确率和优化。”



### 第二层：窗口层——带多少给模型
1. 滑动窗口 ：只带最近 N 轮。项目已做（8 条）。
2. 摘要压缩 ：超出窗口的旧对话用小模型总结成一段“长期记忆”，代替原文。比如把前 20 轮压成“用户不吃香菜、常做快手菜、家里只有微波炉”。
3. 结构化画像 ：从历史里抽取稳定偏好（忌口、口味、器具、技能水平）存成字段，每轮都带上，比带原文便宜得多。
4. 检索式记忆 ：把历史消息向量化，按当前问题检索最相关的几条，而不是全带。适合长会话。
5. 按 token 预算截断 ：不是按条数，而是按 token 数动态裁剪，保证不超模型上下文窗口。
关键区分： 原始消息用于合规审计，摘要和画像用于喂模型 。两者都存，但用途不同。

窗口层不是五个都上，而是按会话长度和用户属性选组合。滑动窗口和 token 预算必做，前者防无限增长，后者保证不超上下文窗口；结构化画像适合有稳定偏好的场景，比如忌口和可用器具；摘要压缩适合长会话，比如客服；检索式记忆成本最高，只在需要长期回溯时用。本项目会先做滑动窗口加 token 预算，再把忌口和器具抽成画像字段，摘要暂时不做，因为会话普遍很短。”


目前移动端的AI对话历史采取本地为主 + 登录后合并上云的方案；
窗口层采用只带最近 8条，超出窗口的旧对话，当达到模型窗口的百分之六十的时候开启压缩，添加模型的时候，增加上下文窗口大小设置，添加兜底措施：1、压缩失败，回滚原本的历史记录，2、如果上下文窗口设置错误，超过模型上下文窗口大小，则自动砍一半再去压缩，日志里针对错误醒目提示，
对话的生活周期暂时先设置30 分钟无操作自动开新会话，游客记录存储在本地，超过7天自动删除，登录用户30天自动删除，登录的时候，同步本地数据上云，提供新聊天记录按钮功能，不提供删除历史记录功能，历史记录超时自动从库里删除，暂定每天跑一次删除命令，删除超过30天的，删除用户账户的时候，连带删除它所有记录，但是日志不是30天删除一次，是180天，添加Redis，Redis放30分钟 内的消息，滑动过期删除
