# 数据库与媒体存储：从 SQLite 切到 PostgreSQL

本文对应一次真实迭代：把本地开发数据库从 SQLite 切换到本机 PostgreSQL，并把图片存储改造成可迁移的对象键方案。文中每个概念都按“先结论、再展开”的方式说明。

## 一、这次做了什么

1. 在本机 PostgreSQL 18 中创建专用角色 `meal_app` 和数据库 `meal_dev`，应用不再使用超级用户。项目统一改名为 MealMate 后，Docker Compose 与默认配置已改用 `mealmate`；本机数据库因当前角色缺少建库权限，暂时保留 `meal_dev`，详见 [03-项目标识与多端命名.md](03-项目标识与多端命名.md)。
2. 把 `server/.env` 的连接串从 SQLite 改为 PostgreSQL，启动时自动建表并写入演示数据。
3. 发现并修复一个只在 PostgreSQL 下暴露的种子数据问题：点赞记录插入时，被点赞的饭帖尚未落库，触发外键约束。
4. 新增媒体存储抽象层，数据库只保存对象键，访问地址统一由后端生成，为迁移到对象存储做准备。
5. 验证：10 张表创建成功，演示数据为 16 个用户、9 条饭帖、8 个菜谱、108 条点赞、6 个媒体资源；15 条接口测试全部通过；首页、菜谱、热榜、图片访问均正常。

## 二、知识点

### 1. 实例、数据库、角色不是一回事

- **实例**：一个正在运行的 PostgreSQL 服务进程，监听一个端口，管理一份数据目录。你电脑上的实例监听 5432。
- **数据库**：实例内部的逻辑库，一个实例可以有多个数据库，彼此隔离。本项目本机开发仍使用 `meal_dev`；Docker Compose 与默认配置使用 `mealmate`。
- **角色**：登录身份，可以拥有数据库、表和各种权限。`meal_app` 是应用专用角色，不是超级用户。

为什么要单独建角色，而不是让应用用 `postgres` 连接？因为超级用户可以做任何事，包括删除其他数据库、读写系统表。应用只需要自己那个库的权限，一旦连接信息泄露，损失被限制在单个库内。这是最小权限原则。

### 2. 开发用 SQLite、生产用 PostgreSQL 的原因

SQLite 是一个文件，不需要安装服务，适合本地开发和自动化测试；它不支持高并发写入，也不适合多实例共享。PostgreSQL 是客户端/服务端架构，支持并发控制、丰富的数据类型、扩展和主从复制，适合生产。

同一个项目用两套数据库，前提是代码只使用两者都支持的能力。本项目通过 SQLAlchemy 统一建模，避免使用某一方独有的语法。真正的生产项目通常会让开发、测试、生产使用同一种数据库，以减少“本地能跑、线上报错”的风险。

### 3. 外键与 SQLite 的默认行为

**外键（Foreign Key）** 是数据库层面的一条约束：子表某一列的值必须存在于父表的对应列。例如点赞表的 `post_id` 必须能在饭帖表中找到。

本次的问题：种子数据先添加用户，再添加饭帖和点赞，最后一次性提交。SQLAlchemy 理论上会按外键依赖排序插入，但在这次组合下，点赞先于饭帖被写入，PostgreSQL 立即报错。

SQLite 没有报错，是因为 **SQLite 默认不启用外键检查**，需要显式执行 `PRAGMA foreign_keys = ON` 才会生效。所以同一份代码在 SQLite 下能跑通，在 PostgreSQL 下暴露了顺序问题。

修复方式是在种子函数中按依赖顺序显式落库：先写用户并 `flush`，再写菜谱并 `flush`，再写饭帖并 `flush`，最后写点赞并提交。`flush` 的作用是把当前挂起的对象立即发送到数据库，但事务尚未提交，失败仍可整体回滚。

这件事的启示：**换数据库不只是换连接串，还要重新验证数据完整性和写入顺序**。

### 4. 异步驱动与连接串

Python 后端使用异步方式访问数据库，PostgreSQL 对应的驱动叫 `asyncpg`，SQLAlchemy 的连接串写成：

```text
postgresql+asyncpg://用户名:密码@主机:端口/数据库名
```

其中 `postgresql` 是数据库方言，`asyncpg` 是驱动。SQLite 对应的写法是 `sqlite+aiosqlite:///文件路径`。连接串写在 `.env` 中，该文件已被版本控制忽略，不会提交密码。

### 5. 对象键与存储抽象

**对象键（Object Key）** 是文件在存储系统中的唯一名字，例如 `uploads/m_abc.jpg`。它和访问地址是两件事：

- 对象键：稳定，跟着文件走，不随域名变化；
- 访问地址：可能从 `/media/uploads/m_abc.jpg` 变成 `https://cdn.example.com/uploads/m_abc.jpg`。

如果数据库直接存访问地址，迁移到云时就要批量改写所有记录，还容易漏掉历史数据。正确做法是数据库只存对象键，由后端根据当前存储后端生成地址。

本次新增的存储抽象层定义了四个方法：写入、删除、判断存在、生成地址。本地实现把对象键映射到磁盘目录；未来接对象存储时新增一个实现即可，业务代码和数据库都不动。旧的 `/media/...` 数据会在读取时自动还原为对象键，因此不需要一次性迁移历史记录。

## 三、面试题

### 问题一：SQLite 和 PostgreSQL 有什么区别，为什么开发能用 SQLite、生产不行？

**总结版**：SQLite 是嵌入式文件数据库，零配置、适合单机和小数据量；PostgreSQL 是客户端/服务端数据库，支持高并发、复杂查询、扩展和复制。生产环境多人同时写入、需要备份恢复和扩容，所以要换 PostgreSQL。

**详细版**：

SQLite 把整个数据库放在一个文件里，应用程序直接读写文件，没有独立服务进程。优点是部署极简、事务完整、读性能好，适合移动端、桌面端、测试环境和小型网站。缺点是写操作要锁住整个数据库文件，同一时间只能有一个写入者；不支持用户和权限体系；无法让多台服务器共享同一个库；备份和容量扩展能力有限。

PostgreSQL 是独立的服务进程，客户端通过网络连接。它支持多版本并发控制，读写互不阻塞；支持行级锁、复杂索引、窗口函数、JSON 字段、全文检索和扩展；支持主从复制和逻辑复制，能通过增加从库分担读流量。代价是需要安装、配置、备份和监控。

因此常见组合是：本地开发和自动化测试用 SQLite 追求速度，生产用 PostgreSQL 保证并发和可靠性。但要注意两者行为差异，例如 SQLite 默认不检查外键，切换数据库后必须重新跑一遍完整测试。

### 问题二：为什么图片不直接存进数据库？

**总结版**：数据库擅长结构化数据和事务，不擅长存大文件。图片放对象存储，数据库只存对象键，能避免备份膨胀、内存浪费、连接占用和无法水平扩展的问题。

**详细版**：

第一，备份成本。数据库备份会把所有数据一起打包，如果图片存在库里，备份体积会从几百兆变成几百吉，恢复时间也成倍增加。

第二，内存效率。数据库会把热点数据页缓存在内存中，图片这类大字段会挤占真正需要缓存的行，导致查询变慢。

第三，连接占用。图片上传下载如果走数据库连接，会长时间占用连接池，影响其他业务请求。

第四，扩展能力。关系型数据库扩容需要分片或升级机器，而对象存储天生分布式，容量按需增长，还提供多副本和跨区域复制。

所以主流方案是：文件写入对象存储，数据库保存对象键、大小、类型、宽高这类元数据。读取时先查数据库拿对象键，再由客户端访问对象存储或内容分发网络。

### 问题三：如何设计一套能从本地磁盘平滑迁移到云存储的文件方案？

**总结版**：数据库只存对象键；访问地址由服务端统一生成；存储层抽象成接口；本地目录结构与对象键一一对应；迁移时按对象键批量上传并校验。

**详细版**：

第一步，确定对象键规则。对象键只包含业务含义和唯一标识，例如 `uploads/2026/11/m_abc.jpg`，不包含域名、协议和服务器路径。

第二步，抽象存储接口。至少定义写入、删除、判断存在、生成地址四个方法。业务层只依赖接口，不直接操作文件系统。

第三步，统一地址生成。序列化响应时调用存储接口生成地址，页面和客户端不拼接路径。这样从相对路径切换到完整域名时只改一处。

第四步，本地目录与对象键保持一致。本地文件放在根目录下的 `对象键` 位置，迁移时可以用脚本按相同的键批量上传，不会出现路径对不上。

第五步，兼容历史数据。读取时识别旧格式（例如以 `/media/` 开头），先还原为对象键再生成地址；写入时只写新格式。迁移完成后可以再清理旧数据。

第六步，迁移后校验。逐条对比数据库中的对象键与对象存储中的对象是否存在，记录失败项并重试；切换前用灰度或双读验证访问地址。
