# 第一部分　工程基础：数据库、存储与项目标识

## 一、这部分解决什么问题

工程基础这一层解决的是“应用能不能长期、安全、可迁移地跑下去”：数据放在哪里（数据库与文件存储），以及同一个应用在各个平台上叫什么（项目标识与多端命名）。下面两节分别是两次真实迭代的记录。

### 1. 数据库与媒体存储

这一节对应一次真实迭代：把本地开发数据库从 SQLite 切换到本机 PostgreSQL，并把图片存储改造成可迁移的对象键方案。文中每个概念都按“先结论、再展开”的方式说明。

1. 在本机 PostgreSQL 18 中创建专用角色 `meal_app` 和数据库 `meal_dev`，应用不再使用超级用户。项目统一改名为 MealMate 后，Docker Compose 与默认配置已改用 `mealmate`；本机数据库因当前角色缺少建库权限，暂时保留 `meal_dev`，详见第一部分第五节第 6 小节。
2. 把 `server/.env` 的连接串从 SQLite 改为 PostgreSQL，启动时自动建表并写入演示数据。
3. 发现并修复一个只在 PostgreSQL 下暴露的种子数据问题：点赞记录插入时，被点赞的饭帖尚未落库，触发外键约束。
4. 新增媒体存储抽象层，数据库只保存对象键，访问地址统一由后端生成，为迁移到对象存储做准备。
5. 验证：10 张表创建成功，演示数据为 16 个用户、9 条饭帖、8 个菜谱、108 条点赞、6 个媒体资源；15 条接口测试全部通过；首页、菜谱、热榜、图片访问均正常。

### 2. 项目标识与多端命名

这一节对应一次真实的项目改名迭代：把根目录名改为 `mealmate` 之后，再把后端、Flutter、小程序、管理后台的工程名、应用标识和界面显示名称统一为 `mealmate` / `MealMate`。文中每个名词都先给结论，再解释原因。

1. 后端：Python 发行包名从 `meal-api` 改为 `mealmate-api`，FastAPI 应用名改为 `MealMate API`，日志记录器名称改为 `mealmate`，本地 SQLite 文件名改为 `mealmate_dev.db`。
2. Flutter：Dart 包名从 `meal_flutter` 改为 `mealmate`；Android 的 `namespace` 与 `applicationId` 改为 `com.mealmate.app`；iOS 的 `PRODUCT_BUNDLE_IDENTIFIER` 改为 `com.mealmate.app`；Android 桌面名称与 iOS 显示名称改为 `MealMate`。
3. 微信小程序 / H5：包名从 `meal-miniapp` 改为 `mealmate-miniapp`，`manifest.json`、`pages.json`、首页标题、登录页标题和入口 HTML 的标题统一为 `MealMate`。
4. 管理后台：包名从 `meal-admin` 改为 `mealmate-admin`，浏览器标题、登录页品牌、侧边栏品牌和路由标题统一为 `MealMate`。
5. Docker Compose：PostgreSQL 数据库名、用户名、默认密码和数据卷名称改为 `mealmate` 系列。
6. 客户端本地存储键：`meal_token`、`meal_profile`、`meal_device_id`、`meal_admin_token` 改为 `mealmate_` 前缀。
7. 验证：后端 20 条测试通过、Ruff 检查通过；管理后台类型检查与生产构建通过；小程序 H5 构建通过；Flutter 静态分析无问题、测试通过；Docker Compose 配置校验通过。
8. 边界：本机 PostgreSQL 的数据库名没有改名成功。当前登录角色 `meal_app` 是数据库所有者，但没有创建数据库的权限，执行重命名时数据库返回“权限不够”。Docker 与项目默认配置已经改为 `mealmate`，本机 `server/.env` 暂时保留原来的 `meal_dev`，不影响本地启动。

## 二、数据库基础

### 1. 实例、数据库、角色不是一回事

- **实例**：一个正在运行的 PostgreSQL 服务进程，监听一个端口，管理一份数据目录。你电脑上的实例监听 5432。
- **数据库**：实例内部的逻辑库，一个实例可以有多个数据库，彼此隔离。本项目本机开发仍使用 `meal_dev`；Docker Compose 与默认配置使用 `mealmate`。
- **角色**：登录身份，可以拥有数据库、表和各种权限。`meal_app` 是应用专用角色，不是超级用户。

为什么要单独建角色，而不是让应用用 `postgres` 连接？因为超级用户可以做任何事，包括删除其他数据库、读写系统表。应用只需要自己那个库的权限，一旦连接信息泄露，损失被限制在单个库内。这是最小权限原则。

### 2. 开发用 SQLite、生产用 PostgreSQL 的原因

SQLite 是一个文件，不需要安装服务，适合本地开发和自动化测试；它不支持高并发写入，也不适合多实例共享。PostgreSQL 是客户端/服务端架构，支持并发控制、丰富的数据类型、扩展和主从复制，适合生产。

同一个项目用两套数据库，前提是代码只使用两者都支持的能力。本项目通过 SQLAlchemy 统一建模，避免使用某一方独有的语法。真正的生产项目通常会让开发、测试、生产使用同一种数据库，以减少“本地能跑、线上报错”的风险。

### 3. 外键与 SQLite 的默认行为

**外键（Foreign Key）** 是数据库层面的一条约束：子表某一列的值必须存在于父表的对应列。例如点赞表的 `post_id` 必须能在饭帖表中找到。

本次的问题：种子数据先添加用户，再添加饭帖和点赞，最后一次性提交。SQLAlchemy 理论上会按外键依赖排序插入，但在这次组合下，点赞先于饭帖被写入，PostgreSQL 立即报错。

SQLite 没有报错，是因为 **SQLite 默认不启用外键检查**，需要显式执行 `PRAGMA foreign_keys = ON` 才会生效。所以同一份代码在 SQLite 下能跑通，在 PostgreSQL 下暴露了顺序问题。

修复方式是在种子函数中按依赖顺序显式落库：先写用户并 `flush`，再写菜谱并 `flush`，再写饭帖并 `flush`，最后写点赞并提交。`flush` 的作用是把当前挂起的对象立即发送到数据库，但事务尚未提交，失败仍可整体回滚。

这件事的启示：**换数据库不只是换连接串，还要重新验证数据完整性和写入顺序**。

### 4. 异步驱动与连接串

Python 后端使用异步方式访问数据库，PostgreSQL 对应的驱动叫 `asyncpg`，SQLAlchemy 的连接串写成：

```text
postgresql+asyncpg://用户名:密码@主机:端口/数据库名
```

其中 `postgresql` 是数据库方言，`asyncpg` 是驱动。SQLite 对应的写法是 `sqlite+aiosqlite:///文件路径`。连接串写在 `.env` 中，该文件已被版本控制忽略，不会提交密码。

## 三、数据库迁移

### 1. 什么是数据库迁移

**数据库迁移（Database Migration）** 是用可重复执行的脚本描述“数据库结构如何从旧版本变到新版本”。例如新增字段、修改索引、拆分表。

它解决三个问题：
1. 开发、测试、生产环境的表结构保持一致；
2. 变更可以按顺序执行，不会漏掉；
3. 出问题时知道执行过哪些变更。

### 2. 为什么 `create_all` 不够

本项目没有引入迁移框架，启动时用 SQLAlchemy 的 `Base.metadata.create_all` 建表。

`create_all` 的行为是：**表不存在就建表，表已存在就跳过**。它不会给已经存在的表补字段，也不会修改字段类型或索引。

所以，新数据库首次启动会自动带上新字段；老数据库必须手工执行一次 `ALTER TABLE`，否则运行时会报“字段不存在”。

### 3. 常见迁移工具对比

**迁移工具（Migration Tool）** 是把“表结构变更”记录成有版本号脚本的软件：每次变更写一个文件，工具负责按顺序执行、记录哪些已经执行过、必要时回滚。

| 工具 | 生态 | 优势 | 劣势 |
| --- | --- | --- | --- |
| Alembic | Python / SQLAlchemy | 与 SQLAlchemy 模型同一套定义；支持自动生成迁移草稿；可按版本升降级 | 自动生成不一定准确，仍需人工检查 |
| Django Migrations | Python / Django | 与框架模型深度集成，使用最省心 | 只能在 Django 项目里用 |
| Flyway | Java 为主，支持多语言 | 以纯 SQL 为中心，简单直接；社区成熟 | 不负责根据模型生成脚本，需要手写 SQL |
| Liquibase | Java 为主 | 支持多种格式；适合大型企业的审计与回滚要求 | 配置较重，学习成本高 |
| Prisma Migrate | Node.js / TypeScript | 类型安全，开发体验好 | 绑定 Prisma 生态 |

公司真实使用中，只要项目进入多人协作和正式环境，几乎都会使用迁移工具。“没有迁移工具、手工改表”只适合个人演示或非常早期的原型。具体选哪一个通常跟着技术栈走：Python + SQLAlchemy 用 Alembic，Django 项目用自带 Migrations，Java 项目多用 Flyway 或 Liquibase，Node.js + TypeScript 项目常用 Prisma Migrate。

本项目的选择理由：后端是 FastAPI + SQLAlchemy，Alembic 是 SQLAlchemy 官方迁移工具，模型和迁移共享同一套元数据，最贴合现状。当前阶段还没有引入，改用两份手写 SQL 代替，原因见下一节。

### 4. 本项目的迁移方式与两次实际操作

本次已在本地 PostgreSQL 与 SQLite 开发库上执行了新增字段的 `ALTER TABLE`，因此现有演示数据不需要重建。生产环境如果已有数据，应按迁移文件执行并先备份。

本项目新增了迁移文件 `server/migrations/20261119_posts_draft_price_tags_map.sql`，分别给出 PostgreSQL 和 SQLite 两种写法。执行前需要备份数据库，且 SQLite 的 `ALTER TABLE` 不支持“字段不存在才添加”，只能执行一次。

这两份迁移文件都放在 `server/migrations/` 目录下，用日期开头命名，按文件名就能看出执行顺序：

| 迁移文件 | 日期 | 内容 |
| --- | --- | --- |
| `server/migrations/20261119_posts_draft_price_tags_map.sql` | 2026-11-19 | 饭帖表增加人均价格、口味标签、店铺坐标、软删除时间六个字段 |
| `server/migrations/20261120_location_and_taste_tags.sql` | 2026-11-20 | 新建口味标签字典表 `taste_tags` 并写入初始值，新建用户最近定位表 `user_locations` |

#### 第一次迁移：2026-11-19 饭帖新增字段

- 给 `meal_posts` 增加六列：`avg_price`（人均价格，整数，可空）、`taste_tags`（口味标签，数组，默认空数组）、`store_lat` 与 `store_lng`（餐厅坐标，可空）、`store_poi_id`（地图服务商的地点编号，可空）、`deleted_at`（软删除时间，可空）。
- PostgreSQL 部分使用 `ADD COLUMN IF NOT EXISTS`，可以重复执行而不报错；`taste_tags` 用 `JSONB` 类型并默认 `'[]'::jsonb`，老数据不需要回填。
- SQLite 部分被注释掉保留在文件里，因为 SQLite 的 `ALTER TABLE` 一次只能加一列，也不支持 `IF NOT EXISTS`，只能在“还没加过字段”的库上执行一次。
- 新数据库不需要执行这个文件：首次启动时 `create_all` 会直接按最新模型建出带新字段的表。

#### 第二次迁移：2026-11-20 标签字典与用户定位

- 新建 `taste_tags` 表，作为口味标签的字典（“字典”指所有合法取值的总表）：`name` 为主键，另有 `sort_order`（展示顺序）、`enabled`（是否启用）、`created_at`。
- 写入 9 个初始标签：清淡、正常、香辣、酸甜、咸鲜、油炸、烧烤、汤羹、面食。插入语句带 `ON CONFLICT (name) DO NOTHING`，意思是“主键已存在就跳过”，因此重复执行不会报错，也不会覆盖运营后来改过的顺序。
- 新建 `user_locations` 表，每个账号一条记录，`account_id` 既是主键又外键引用 `users(id)`，保存 `lat`、`lng`、`area`、`updated_at`。用途是手机定位不可用时，拿上一次成功定位作为地图中心点。
- 同样附了 SQLite 版本：SQLite 没有布尔类型，用整数 0/1 表示 `enabled`；没有带时区的时间类型 `TIMESTAMPTZ`，改用 `DATETIME`；旧版本不支持 `ON CONFLICT ... DO NOTHING` 时改用 `INSERT OR IGNORE`。

两份文件都尽量写成可重复执行的形式（`IF NOT EXISTS`、`ON CONFLICT DO NOTHING`），目的是降低重复执行时的报错概率；但 SQLite 的加字段语句无法做到这一点，所以仍需先备份。

## 四、媒体存储

### 1. 对象键与存储抽象

**对象键（Object Key）** 是文件在存储系统中的唯一名字，例如 `uploads/m_abc.jpg`。它和访问地址是两件事：

- 对象键：稳定，跟着文件走，不随域名变化；
- 访问地址：可能从 `/media/uploads/m_abc.jpg` 变成 `https://cdn.example.com/uploads/m_abc.jpg`。

如果数据库直接存访问地址，迁移到云时就要批量改写所有记录，还容易漏掉历史数据。正确做法是数据库只存对象键，由后端根据当前存储后端生成地址。

本次新增的存储抽象层定义了四个方法：写入、删除、判断存在、生成地址。本地实现把对象键映射到磁盘目录；未来接对象存储时新增一个实现即可，业务代码和数据库都不动。旧的 `/media/...` 数据会在读取时自动还原为对象键，因此不需要一次性迁移历史记录。

## 五、项目标识与多端命名

### 1. 显示名称、工程名、应用标识不是同一件事

- **显示名称**：用户桌面上、任务栏里、应用商店里看到的名字。Android 在 `AndroidManifest.xml` 的 `android:label`，iOS 在 `Info.plist` 的 `CFBundleDisplayName`，小程序在 `manifest.json` 的 `name`。它可以随时改，只影响展示。
- **工程名**：代码仓库内部使用的名字，例如 `package.json` 的 `name`、`pubspec.yaml` 的 `name`、Python `pyproject.toml` 的 `name`。它主要影响依赖管理、导入路径和构建产物名称，用户一般看不到。
- **应用标识**：操作系统和应用商店用来区分“这是哪一个应用”的唯一标识。Android 叫 `applicationId`，iOS 叫 `Bundle Identifier`（应用包标识）。它决定安装、升级、推送、支付和商店数据归到哪个应用名下。

三者可以不同。例如显示名称是 `MealMate`，工程名是 `mealmate`，应用标识是 `com.mealmate.app`。这次为了减少理解成本，统一使用 `mealmate` / `MealMate`，但概念上仍然要分开。

### 2. Android 的 namespace 与 applicationId

- **`namespace`（命名空间）**：Kotlin 和 Java 代码的包名，也是自动生成的 `R` 类所在的包。它解决“代码里的类不要重名”的问题，只在编译期起作用。
- **`applicationId`（应用标识）**：安装到手机后，系统用来识别应用的唯一字符串，也是应用商店里的唯一标识。格式通常是反向域名，例如 `com.mealmate.app`。

两者可以不同。真实项目里常见做法是：`namespace` 长期保持公司内部代码包名，`applicationId` 使用对外发布的标识。如果只改 `namespace`，应用升级关系不变；如果改 `applicationId`，系统会把它当成一个新应用，旧版本无法直接升级，用户数据也不在同一个应用沙箱里。因此 `applicationId` 应在首次发布前确定，发布后不要改。

本次项目还没有发布，所以把两者一起改成 `com.mealmate.app`，避免以后混淆。

### 3. iOS 的 Bundle Identifier

**Bundle Identifier（应用包标识）** 是 iOS 应用的唯一身份，格式同样是反向域名，例如 `com.mealmate.app`。它被写入签名证书、描述文件、推送证书和应用商店记录。

发布到 App Store 后，Bundle Identifier 不能修改。想换标识只能发布一个全新的应用，原有下载量、评论、内购记录都不会迁移。因此它必须在创建应用时确定。

`Info.plist` 里还有两个容易混淆的字段：

- `CFBundleDisplayName`：用户看到的名称，本次改为 `MealMate`；
- `CFBundleName`：系统内部使用的短名称，本次改为 `mealmate`，通常不超过 16 个字符。

测试目标 `RunnerTests` 使用 `com.mealmate.app.RunnerTests`，这是 iOS 的惯例：测试包在主应用标识后面加后缀，避免和主应用冲突。

### 4. Dart 包名与 Flutter 工程名

Flutter 的 `pubspec.yaml` 里 `name` 字段就是 **Dart 包名**。规则是：

- 只能使用小写字母、数字和下划线；
- 不能以数字开头；
- 不能使用 Dart 保留字；
- 推荐使用“小写字母 + 下划线”的组合，例如 `mealmate`、`meal_flutter`。

包名决定代码里的导入路径。例如测试文件原来写：

```dart
import 'package:meal_flutter/theme/app_theme.dart';
```

改名后必须改成：

```dart
import 'package:mealmate/theme/app_theme.dart';
```

改完要重新执行 `flutter pub get`，因为 Flutter 会重新生成 `.dart_tool/package_config.json`，这个文件记录“包名对应哪个磁盘目录”。不重新生成，编辑器仍会按旧包名找文件。

### 5. uni-app 的 name 与 appid

`manifest.json` 里有两个不同概念：

- `name`：应用名称，本次改为 `MealMate`，会显示在 H5 标题、部分平台的应用信息里；
- `appid`：DCloud 平台分配的应用标识，用于云打包、统计和部分原生能力。它与微信小程序的 `appid` 不是同一个东西。

微信小程序真正的应用标识在 `manifest.json` 的 `mp-weixin.appid` 字段。它必须与微信公众平台里注册的小程序一致，否则微信开发者工具无法上传和预览。本项目当前没有真实小程序账号，所以该字段保持为空；这不影响本地 H5 构建，但正式发布前必须填写。

### 6. 数据库名、用户名与 Docker 数据卷

- **数据库名**：PostgreSQL 实例内部的逻辑库名称。本次 Docker 配置从 `meal` 改为 `mealmate`。
- **用户名**：登录数据库的角色名称。本次 Docker 配置从 `meal` 改为 `mealmate`。
- **数据卷（Volume）**：Docker 管理的持久化存储目录，容器删除后数据仍然保留。本次从 `meal_pgdata`、`meal_media`、`meal_redis` 改为 `mealmate_pgdata`、`mealmate_media`、`mealmate_redis`。

需要特别注意：**改数据卷名称等于换了一个新卷**。Docker 不会自动把旧卷的数据复制到新卷，旧数据仍然留在旧卷里。对生产环境来说，必须先备份、再迁移数据，确认新卷可用后才能删除旧卷。本项目是开发环境，没有生产数据，所以直接使用新卷即可。

本机 PostgreSQL 的重命名失败，是因为 PostgreSQL 规定：重命名数据库需要数据库所有者身份，并且需要拥有创建数据库的权限。当前 `meal_app` 只是数据库所有者，没有创建数据库的权限，所以被拒绝。用超级用户执行下面的命令即可完成：

```text
psql -U postgres -c "ALTER DATABASE meal_dev RENAME TO mealmate_dev;"
```

执行后把 `server/.env` 里的数据库名从 `meal_dev` 改成 `mealmate_dev`。角色名 `meal_app` 的修改需要更高权限，本地环境可以不改。

### 7. 为什么数据库表名 `meal_posts` 没有改

数据库表名描述的是业务对象（饭帖），不是品牌标识。把 `meal_posts` 改成 `mealmate_posts` 会带来一串连锁工作：修改模型映射、修改所有查询、写数据迁移脚本、处理外键、停机窗口和回滚方案。品牌改名不需要动业务表名，否则收益很小、风险很大。

工程里保留的 `meal_post` 审计对象类型也是同样的道理：它是已经写入数据库的业务枚举值，改名要做数据迁移，不适合和品牌改名混在一起。

### 8. 本地存储键改名会影响登录状态

`meal_token`、`meal_profile`、`meal_device_id` 是客户端保存在本地的键名。改名后，旧版本保存的登录令牌不会再被新版本读取，效果等同于“退出登录”。这是可以接受的代价；如果应用已经上线，就要考虑兼容读取旧键、迁移后再删除旧键，避免用户无感丢失登录状态。

## 六、面试题

### 问题一：SQLite 和 PostgreSQL 有什么区别，为什么开发能用 SQLite、生产不行？

**总结版**：SQLite 是嵌入式文件数据库，零配置、适合单机和小数据量；PostgreSQL 是客户端/服务端数据库，支持高并发、复杂查询、扩展和复制。生产环境多人同时写入、需要备份恢复和扩容，所以要换 PostgreSQL。

**详细版**：

SQLite 把整个数据库放在一个文件里，应用程序直接读写文件，没有独立服务进程。优点是部署极简、事务完整、读性能好，适合移动端、桌面端、测试环境和小型网站。缺点是写操作要锁住整个数据库文件，同一时间只能有一个写入者；不支持用户和权限体系；无法让多台服务器共享同一个库；备份和容量扩展能力有限。

PostgreSQL 是独立的服务进程，客户端通过网络连接。它支持多版本并发控制，读写互不阻塞；支持行级锁、复杂索引、窗口函数、JSON 字段、全文检索和扩展；支持主从复制和逻辑复制，能通过增加从库分担读流量。代价是需要安装、配置、备份和监控。

因此常见组合是：本地开发和自动化测试用 SQLite 追求速度，生产用 PostgreSQL 保证并发和可靠性。但要注意两者行为差异，例如 SQLite 默认不检查外键，切换数据库后必须重新跑一遍完整测试。

### 问题二：为什么图片不直接存进数据库？

**总结版**：数据库擅长结构化数据和事务，不擅长存大文件。图片放对象存储，数据库只存对象键，能避免备份膨胀、内存浪费、连接占用和无法水平扩展的问题。

**详细版**：

第一，备份成本。数据库备份会把所有数据一起打包，如果图片存在库里，备份体积会从几百兆变成几百吉，恢复时间也成倍增加。

第二，内存效率。数据库会把热点数据页缓存在内存中，图片这类大字段会挤占真正需要缓存的行，导致查询变慢。

第三，连接占用。图片上传下载如果走数据库连接，会长时间占用连接池，影响其他业务请求。

第四，扩展能力。关系型数据库扩容需要分片或升级机器，而对象存储天生分布式，容量按需增长，还提供多副本和跨区域复制。

所以主流方案是：文件写入对象存储，数据库保存对象键、大小、类型、宽高这类元数据。读取时先查数据库拿对象键，再由客户端访问对象存储或内容分发网络。

### 问题三：如何设计一套能从本地磁盘平滑迁移到云存储的文件方案？

**总结版**：数据库只存对象键；访问地址由服务端统一生成；存储层抽象成接口；本地目录结构与对象键一一对应；迁移时按对象键批量上传并校验。

**详细版**：

第一步，确定对象键规则。对象键只包含业务含义和唯一标识，例如 `uploads/2026/11/m_abc.jpg`，不包含域名、协议和服务器路径。

第二步，抽象存储接口。至少定义写入、删除、判断存在、生成地址四个方法。业务层只依赖接口，不直接操作文件系统。

第三步，统一地址生成。序列化响应时调用存储接口生成地址，页面和客户端不拼接路径。这样从相对路径切换到完整域名时只改一处。

第四步，本地目录与对象键保持一致。本地文件放在根目录下的 `对象键` 位置，迁移时可以用脚本按相同的键批量上传，不会出现路径对不上。

第五步，兼容历史数据。读取时识别旧格式（例如以 `/media/` 开头），先还原为对象键再生成地址；写入时只写新格式。迁移完成后可以再清理旧数据。

第六步，迁移后校验。逐条对比数据库中的对象键与对象存储中的对象是否存在，记录失败项并重试；切换前用灰度或双读验证访问地址。

### 问题四：Android 的 `namespace` 和 `applicationId` 有什么区别？

**总结版**：`namespace` 是代码的包名，决定 Kotlin/Java 类和 `R` 类放在哪个包，只在编译期使用；`applicationId` 是应用在手机和应用商店里的唯一身份，决定安装、升级和商店数据归属。两者可以不同，`applicationId` 发布后不应修改。

**详细版**：

`namespace` 解决的是代码组织问题。两个库如果有同名的 `Utils` 类，只要包名不同就不会冲突。Android 构建工具还会根据它生成 `R` 类，代码通过 `R.layout.xxx` 访问资源。

`applicationId` 解决的是应用身份问题。手机安装应用时，系统用 `applicationId` 判断这是不是同一个应用：相同则升级，不同则并存。应用商店、推送服务、支付回调、崩溃统计也都用它来归档数据。

发布后修改 `applicationId` 的后果是：商店认为这是一个新应用，老用户收不到更新，原有评分和内购不会迁移，推送和深链也要重新配置。因此它必须在首次发布前确定。

### 问题五：iOS 的 Bundle Identifier 是什么，为什么发布后不能改？

**总结版**：Bundle Identifier 是 iOS 应用的唯一身份，采用反向域名格式，被签名、描述文件、推送和应用商店共同使用。发布后修改它会被当成另一个应用，原应用的数据和商店记录无法继承，所以不能改。

**详细版**：

iOS 应用安装时，系统用它区分应用和共享数据容器。开发者证书和描述文件会绑定这个标识，推送证书也按它签发。App Store 的应用记录同样以它为主键。

`CFBundleDisplayName` 只是显示名称，可以随时改；Bundle Identifier 是身份标识，不能随意改。一个常见误区是把二者混为一谈，以为改桌面名称就是换应用，实际上系统仍认为是同一个应用。

### 问题六：为什么改一个工程名会牵动这么多文件？

**总结版**：工程名同时出现在包管理配置、应用标识、导入路径、构建产物、锁文件和本地缓存里。只改一处会导致依赖解析失败、导入找不到文件、构建仍带旧名称。正确做法是按“配置 → 代码 → 锁文件 → 缓存 → 构建验证”的顺序整体替换。

**详细版**：

以 Flutter 为例，`pubspec.yaml` 的 `name` 决定 `package:` 导入路径；测试文件需要同步修改；`flutter pub get` 会重写 `.dart_tool/package_config.json`；Android 和 iOS 的显示名称又分别在 `AndroidManifest.xml` 和 `Info.plist`。任何一处漏改，都会出现“代码能跑但显示旧名字”或“导入失败”的问题。

工程改名后要重新构建，而不是只看源码搜索。构建产物会暴露遗漏，例如管理后台的 `dist/index.html` 标题、小程序的 H5 页面标题。最后再用全局搜索确认旧标识没有残留。

### 问题七：修改 Docker 数据卷名称会发生什么？

**总结版**：Docker 会把新名称当成一个全新的空卷，旧卷的数据不会自动迁移。开发环境可以直接换；生产环境必须先备份、迁移数据、验证后再删除旧卷。

**详细版**：

Docker 卷是一块由 Docker 管理的持久化目录，名称就是它的唯一键。容器启动时按名称挂载，名称变了就挂载到另一个目录。Docker 不会因为名称相似就复制数据。

正确迁移步骤是：停止写入、备份旧卷、创建新卷、把数据复制过去、用新卷启动并验证、确认无误后再删除旧卷。直接改名称而不迁移，表现就是“数据库突然空了”或“历史图片全部丢失”。

### 问题八：为什么本地存储键改名会让用户退出登录？

**总结版**：登录令牌保存在客户端本地的键值存储里，键名就是读取时的地址。键名从 `meal_token` 改成 `mealmate_token` 后，新版本按新地址读取，读不到旧令牌，所以表现为未登录。

**详细版**：

Flutter 使用 `SharedPreferences`，小程序使用 `uni.getStorageSync` 一类的本地存储。它们本质上都是“键 → 值”的字典。改名后新旧键同时存在，但新代码只读新键。

已上线应用通常这样做：启动时先读新键，读不到再读旧键，读到旧键就写入新键并删除旧键。这叫兼容迁移。本项目尚未上线，直接改名即可；代价是本地原有登录状态失效，需要重新登录。

### 问题九：品牌改名时，数据库表名要不要一起改？

**总结版**：一般不改。表名描述业务对象，不承担品牌展示功能；改表名需要数据迁移、外键调整、查询改写和停机安排，风险和成本远大于收益。品牌改名优先改工程名、应用标识和显示名称。

**详细版**：

数据库表名是持久化契约的一部分，模型、查询、报表、备份恢复脚本、外部数据同步都可能依赖它。改名不是简单的字符串替换，还要考虑外键约束、索引名称、历史数据、灰度发布和回滚。

如果确实要改，应该单独做一次数据库迁移：新增表或重命名表、同步数据、双写或灰度切读、验证后再清理旧结构。把品牌改名和数据库结构迁移混在一起，会让问题定位和回滚都变得困难。

### 问题十：什么是数据库迁移？为什么 `create_all` 不够？

**总结版**：数据库迁移是用有序脚本管理表结构变化。`create_all` 只会创建不存在的表，不会给已有表加字段、改类型或建索引，所以老数据库升级时必须执行迁移脚本。正式项目通常使用 Alembic、Flyway 等迁移工具。

**详细版**：

数据库迁移记录“第 1 版表结构是什么、第 2 版增加了什么、第 3 版修改了什么”，并按顺序执行。它保证开发、测试、生产环境的表结构一致，也方便回滚和排查。

SQLAlchemy 的 `create_all` 只做一件事：检查表是否存在，不存在就按模型建表。它不会比较模型和数据库的差异，也不会自动执行 `ALTER TABLE`。因此：
- 新环境：`create_all` 能建出完整的新表；
- 老环境：表已存在，`create_all` 直接跳过，新字段不会出现，运行时报错。

本项目的处理方式是提供手写 SQL 迁移文件，并在本地数据库执行。正式项目应使用迁移工具：
- Alembic 可以根据模型自动生成迁移脚本，适合 Python 与 SQLAlchemy；
- Flyway 以 SQL 文件为中心，适合多语言团队；
- Liquibase 支持多种描述格式，适合复杂企业环境。

迁移的原则：先备份、只向前、每次变更可重复验证、生产执行前先在测试环境演练。

# 第二部分　管理后台与角色权限

本部分对应管理后台第一阶段：管理员登录、角色权限、饭帖审核、用户封禁、审计日志，以及独立的 `app_admin` 前端工程。阅读顺序是先看总结版，再看零基础详细版，最后看技术选型对比和面试题。

本部分中的“角色权限”指基于角色的访问控制（Role-Based Access Control，业界常简写为 RBAC）。为了不造成理解障碍，正文优先写中文全称，首次出现时补充英文全称。

## 一、这次做了什么

### 1. 完成范围

1. 管理员独立账号体系：独立的账号表、会话表、鉴权依赖，不复用普通用户手机号登录。
2. 角色与权限点：管理员、角色、权限点三层关系，权限在服务端按接口校验。
3. 饭帖审核：通过、拒绝、下架三条状态流转，重复操作幂等，非法流转返回冲突。
4. 用户管理：列表、详情、封禁、解封；封禁时撤销该用户全部未注销会话。

## 二、知识点总结版

| 概念 | 一句话结论 |
| --- | --- |
| 独立身份体系 | 后台账号不和普通用户共用表、令牌和鉴权代码，任何一边的漏洞不会直接打通另一边 |
| 角色权限控制 | 账号不直接持有权限，而是先拥有角色，角色再拥有权限点，最终权限是所有角色权限点的并集 |
| 权限点 | 最小操作单位，例如 `post.review` 表示审核饭帖，接口在服务端声明所需权限点 |
| 密码哈希 | 数据库只存不可逆的哈希值；本项目使用 Argon2id，内存开销大，能显著提高批量猜密码的成本 |
| 加盐 | 每个密码在哈希前混入随机值，使相同密码得到不同哈希，防止彩虹表批量反查 |
| 令牌摘要 | 发给前端的是随机令牌，数据库只保存它的 SHA-256 摘要，数据库泄露也无法直接冒充登录 |
| 会话表 | 服务端保存会话记录，可以设置过期时间、主动撤销、按账号批量撤销 |
| 登录锁定 | 按“用户名 + 来源地址”统计失败次数，10 分钟窗口内失败 5 次锁定 15 分钟 |
| 状态机 | 饭帖状态只允许三条流转路径，其他组合一律拒绝 |
| 幂等 | 同一个操作重复执行，结果与执行一次相同；重复审核返回当前状态且不重复写日志 |
| 行锁 | 审核前用 `SELECT ... FOR UPDATE` 锁住该行，两个管理员同时审核时排队执行 |
| 事务 | 业务状态变更与审计日志在同一个事务提交，避免只成功一半 |
| 审计日志 | 只追加的记录：谁、什么时间、从哪里、对什么对象、做了什么、为什么 |
| 封禁 | 只改状态并撤销会话，不删除数据，保证可追溯、可恢复 |
| 游标分页 | 用上一页最后一条的排序值作为下一页起点，避免数据插入导致的重复或漏行 |
| 数据库迁移 | 建表工具不会修改已存在的表，字段变更必须用迁移工具，本项目生产阶段需要引入 Alembic |
| 前端权限 | 菜单和按钮的隐藏只是体验优化，真正的安全边界在服务端 |

## 三、知识点详细版（零基础）

### 1. 为什么后台要独立账号、独立会话、独立鉴权

**普通用户体系长什么样**：用户用手机号加验证码登录，会话有效期较长，账号数量大，注册几乎没有门槛。

**后台用户体系长什么样**：管理员用用户名加密码登录，数量很少，但能审核内容、封禁用户、查看审计日志，权限极高。

如果两套身份共用同一张账号表，会带来三个问题：

1. 普通用户注册入口一旦被滥用，攻击者可能通过修改某个字段把自己变成管理员。
2. 普通用户会话有效期长，管理员会话需要更短，同一个会话表无法同时满足两种策略。
3. 任意一端出现令牌解析漏洞，另一端会直接被波及。

所以本项目做了三套隔离：

- 表隔离：`admin_users`、`admin_sessions` 与 `users`、`sessions` 完全分开。
- 令牌隔离：管理员令牌以 `adm_` 开头，摘要时额外拼接固定前缀，普通用户令牌无法冒充管理员令牌。
- 代码隔离：`admin_deps.py` 是独立的管理员鉴权依赖，不修改普通用户鉴权逻辑。

这不是“多写一套代码”，而是把两类风险隔开。真实公司里的后台通常还会再加一层网络隔离，例如只允许公司内网或虚拟专用网络访问。

### 2. 基于角色的权限控制

#### 2.1 三个层次

- 账号：具体的人，例如“张三”。
- 角色：岗位，例如“内容运营”“审计员”。
- 权限点：最小操作，例如“审核饭帖”“查看审计日志”。

关系是：

```text
管理员账号 --多对多--> 角色 --多对多--> 权限点
```

一个管理员可以有多个角色，最终权限是所有角色权限点的并集并去重。

#### 2.2 为什么不把权限直接挂在账号上

假设公司有 50 个内容运营，如果权限直接挂在账号上，每次调整审核范围都要逐个修改 50 次，一定有人漏配。用角色以后，只改角色即可，账号自动继承。

#### 2.3 本项目的权限点

| 权限点 | 含义 |
| --- | --- |
| `post.review` | 查看待审饭帖、通过、拒绝 |
| `post.unpublish` | 下架已公开饭帖 |
| `user.read` | 查看用户列表与详情 |
| `user.ban` | 封禁与解封用户 |
| `recipe.manage` | 管理菜谱（后续阶段使用） |
| `ai.log.read` | 查看 AI 调用日志（后续阶段使用） |
| `ai.config.write` | 修改 AI 配置（后续阶段使用） |
| `kb.document.manage` | 管理知识库文档（后续阶段使用） |
| `kb.search.test` | 测试知识库召回（后续阶段使用） |
| `audit.read` | 查看审计日志 |
| `admin.manage` | 管理管理员与角色（后续阶段使用） |

#### 2.4 四个内置角色

| 角色 | 权限 |
| --- | --- |
| 超级管理员 | 全部十一个权限点 |
| 内容运营 | 审核、下架、查看用户、封禁、菜谱管理 |
| AI 运营 | AI 日志、AI 配置、知识库文档、召回测试 |
| 审计员 | 只看用户列表与审计日志，不能修改任何数据 |

#### 2.5 权限在服务端怎么校验

FastAPI 的依赖注入允许把“取当前管理员”和“校验权限”写成可复用函数。依赖注入的意思是：开发者只声明函数需要哪些参数，由框架在调用前自动准备好并传进来，不需要在每个接口里手动组装。路由声明如下：

```python
@router.post("/posts/{post_id}/approve")
async def approve(
    post_id: str,
    principal: AdminPrincipal = Depends(require_permission("post.review")),
):
    ...
```

请求进入路由函数之前，`require_permission` 已经完成两件事：

1. 解析请求头里的令牌，确认会话未过期、未注销、账号未停用。
2. 查询该管理员的权限点，确认包含 `post.review`，否则返回 403（表示已登录但没有权限；未登录或会话失效则是 401）。

这样写的好处是“接口需要什么权限”和“接口实现”在同一个位置，新增接口时不容易漏掉。

### 3. 密码为什么要哈希，为什么选 Argon2id

#### 3.1 哈希是什么

哈希函数把任意长度的输入变成固定长度的输出，并且不可逆。数据库保存哈希值，登录时把用户输入的密码用同样方法算一遍，再比对两个哈希值。

绝不能保存明文密码，也不能保存可逆加密后的密码。因为一旦数据库泄露，明文或可解密的数据等于把所有用户的密码直接交出去。

#### 3.2 加盐是什么

如果两个人密码都是 `123456`，不做处理时哈希值完全相同。攻击者可以预先算好大量常见密码的哈希，做成一张对照表，这叫彩虹表。

加盐是在哈希前给每个密码混入一段随机值，并把这个随机值一起存进哈希字符串。这样相同密码也会得到不同结果，彩虹表失效。

Argon2 的哈希字符串本身已经包含算法、参数和盐，所以数据库只需要一个 `password_hash` 字段。

#### 3.3 为什么选 Argon2id

密码哈希算法的目标是“验证一次很快，暴力尝试很慢”。Argon2id 有三个可调开销：

- 时间开销：迭代多少轮。
- 内存开销：每次计算占用多少内存，默认约 64 兆字节。
- 并行度：允许几路并行计算。

内存开销是关键。图形处理器擅长并行计算，普通哈希算法在图形处理器上每秒可以尝试几十亿次；Argon2id 强制每次尝试占用大量内存，攻击者很难用显卡堆出同样的吞吐量。

本项目使用 Python 的 `argon2-cffi` 库（Argon2 算法的 Python 实现）的默认参数，并通过 `PasswordHasher` 统一封装。更换参数时旧哈希仍可校验，因为参数写在哈希字符串里。

#### 3.4 一个容易忽略的细节：响应时间差

如果用户名不存在时立刻返回，存在时才开始计算哈希，攻击者可以通过“哪个请求更快”判断用户名是否存在。本项目在用户名不存在时也执行一次虚拟哈希校验，让两条路径耗时接近。这叫降低时间侧信道差异。

### 4. 令牌为什么只存摘要

登录成功后，服务端生成一个随机令牌发给前端。之后的请求把令牌放在 `Authorization: Bearer 令牌` 请求头里。`Authorization` 是存放凭证的标准请求头，`Bearer` 表示“持有这个令牌的人就被认为是已登录”，后面跟令牌原文。

数据库不保存令牌原文，而是保存它的 SHA-256 摘要。SHA-256 是“安全哈希算法第 256 位版本”的英文缩写，它把任意长度的输入变成一段 64 个十六进制字符的固定输出，同样不可逆。之所以摘要用普通哈希而密码用慢哈希，是因为数据库泄露时，攻击者拿到摘要也无法反推出令牌。

流程是：

1. 登录成功，生成随机令牌，例如 `adm_xxx`。
2. 计算摘要，把摘要、管理员标识、过期时间写入 `admin_sessions`。
3. 把令牌原文返回给前端。
4. 后续请求带来令牌，服务端再算一次摘要，用摘要查会话。

注意：令牌摘要和密码哈希的强度要求不同。令牌本身是足够长的随机值，不存在“用户设置弱密码”的问题，所以用 SHA-256 足够；密码来自人，可能很弱，必须用慢哈希。

### 5. 登录失败锁定

#### 5.1 规则

同一用户名与同一来源地址，在 10 分钟统计窗口内失败 5 次，锁定 15 分钟。锁定期间即使密码正确也拒绝登录。

#### 5.2 为什么按“用户名 + 来源地址”而不是只按用户名

只按用户名计数，攻击者可以故意用别人的用户名连续输错，把真实用户锁死，这叫恶意锁定。加入来源地址后，攻击者只能锁住自己那个地址，影响范围被限制。

反过来，只按来源地址计数也不行，因为公司内网很多人共用一个出口地址，一个人输错会连累所有人。

#### 5.3 为什么要落库

如果把计数放在进程内存里，服务重启后计数清零，多实例部署时每个实例各算各的，限制形同虚设。本项目新增 `admin_login_attempts` 表保存失败次数、窗口开始时间和锁定截止时间。

这里说明一个与方案文档的差异：方案文档 5.1 节只描述了锁定规则和会话表，没有单列失败统计表。本项目为了让锁定在多实例与重启后仍然有效，补充了这张表。它属于实现层的必要补充，不改变对外行为。

#### 5.4 返回什么状态码

- 用户名或密码错误：401，错误码 `ADMIN_LOGIN_FAILED`，同时返回剩余尝试次数。
- 触发锁定：423（资源被锁定），错误码 `ADMIN_LOGIN_LOCKED`，返回剩余秒数，并设置 `Retry-After` 响应头。
- 账号被停用：403，错误码 `ADMIN_DISABLED`。

### 6. 状态机：饭帖只能按规则流转

饭帖有四个状态：

- `pending_review`：待审核。
- `published`：已公开。
- `rejected`：已拒绝。
- `unpublished`：已下架。

允许的流转只有三条：

```text
pending_review --通过--> published
pending_review --拒绝--> rejected
published      --下架--> unpublished
```

其他组合一律返回 409（冲突，表示当前资源状态不允许这个操作），例如“已拒绝的帖子再通过”“待审核的帖子直接下架”。

为什么要有状态机？因为审核不是随便改一个字段，而是有业务含义的流程。没有状态机时，代码里会出现各种临时判断，最终没人说得清哪些操作合法。把规则收拢到一处，测试也容易覆盖。

### 7. 幂等：重复点击不产生重复数据

幂等的意思是同一个操作执行一次和执行多次，最终结果一致。

后台页面可能因为网络慢被用户连点，也可能因为超时自动重试。如果“通过”接口每次都写一条审计日志，日志里就会出现两条一模一样的记录，排查问题时无法判断到底发生了几次。

本项目的处理：

- 如果帖子已经是目标状态，直接返回当前状态，`changed=false`。
- 如果帖子处于其他非法状态，返回 409。

这样重复点击是安全的，也不会污染审计日志。

### 8. 事务与审计日志

#### 8.1 事务是什么

事务是一组要么全部成功、要么全部失败的操作。数据库事务有四个特性：原子性、一致性、隔离性、持久性。

本项目的审核操作包含两步：

1. 修改饭帖状态。
2. 写入一条审计日志。

这两步必须在同一个事务里提交。否则可能出现“内容改了但没有日志”或“有日志但内容没改”，两种情况都会让审计失去意义。

#### 8.2 审计日志记什么

| 字段 | 作用 |
| --- | --- |
| 操作人标识与名称 | 谁做的；名称单独存一份快照，账号改名后历史日志仍然可读 |
| 动作 | 例如 `post.approve`、`user.ban` |
| 对象类型与标识 | 对哪条饭帖或哪个用户 |
| 原因 | 拒绝、下架、封禁必须填写 |
| 变更前快照 | 操作前的状态、审核人、审核时间等关键字段 |
| 变更后快照 | 操作后的对应字段 |
| 来源地址 | 从哪个网络地址发起 |
| 请求标识 | 与响应头 `X-Request-Id` 一致，便于把一次操作和日志对上 |
| 创建时间 | 操作时间 |

#### 8.3 为什么只追加

审计日志的价值在于可信。如果管理员可以修改或删除日志，日志就无法证明任何事情。所以应用层不提供修改和删除接口，测试里也验证了删除请求返回 405。

生产环境还可以进一步收紧：给应用使用的数据库账号只授予插入和查询权限，不授予更新和删除权限。这样即使代码出现漏洞，也无法篡改历史日志。

### 9. 行锁：两个管理员同时审核怎么办

假设管理员甲和管理员乙同时打开同一条待审饭帖，几乎同时点“通过”。如果代码都是“先读状态，判断是待审核，再改状态”，两个请求可能都读到待审核，然后都写入，产生两条审计日志。

本项目的处理是在读取时加排他锁：

```sql
SELECT ... FROM meal_posts WHERE id = ? FOR UPDATE;
```

`FOR UPDATE` 的含义是：这一行在当前事务提交前被锁住，第二个事务想锁同一行时必须等待。于是两个请求被串行化，第二个请求读到的是已经变成 `published` 的状态，走幂等分支直接返回，不再写日志。

需要注意：SQLite 不支持这个语法，SQLAlchemy 会自动忽略，所以测试环境仍能运行。生产使用 PostgreSQL 时才是真正的行锁。

### 10. 封禁为什么必须撤销会话

只把用户状态改成 `disabled` 是不够的。用户手里已经有一个未过期的令牌，如果服务端解析会话时只检查令牌是否存在，不检查用户状态，那么用户在封禁后仍然可以继续点赞、发布。

本项目的做法是双保险：

1. 封禁时把用户所有未注销会话写入撤销时间。
2. 解析普通用户会话时同时检查账号状态，停用账号直接拒绝。

解封只把状态改回 `active`，不会恢复旧会话，用户需要重新登录。这是合理的，因为无法判断旧令牌是否已经泄露。

封禁不删除用户、饭帖、点赞等数据，保证可追溯、可恢复。真正需要删除数据的场景属于“注销”或“合规删除”，要走单独流程。

### 11. 游标分页

#### 11.1 页码分页的问题

页码分页是 `第 1 页、第 2 页`，数据库用 `OFFSET` 跳过前面的行。它有两个问题：

1. 数据插入后偏移。用户看第 1 页时有人新发了一条，翻到第 2 页会看到第 1 页已经看过的内容，或者漏掉一条。
2. 深分页变慢。`OFFSET 100000` 需要数据库先数过十万行再丢弃，越往后越慢。

#### 11.2 游标分页怎么做

游标分页记录“上一页最后一条的排序值”，下一页从它之后开始。本项目按创建时间倒序，游标里保存 `createdAt` 和 `id`：

```text
created_at < 上一页最后一条的创建时间
或者 created_at 相同且 id < 上一页最后一条的 id
```

第二个条件是为了处理创建时间相同的情况，保证排序稳定、不重复不遗漏。

前端不需要理解游标内容，只需要把响应里的 `nextCursor` 原样传回下一次请求。

### 12. 数据库迁移：建表工具不会改表

本项目开发阶段用 SQLAlchemy 的 `create_all` 建表，它只会创建不存在的表，不会给已存在的表增加字段、修改类型或删除字段。生产环境数据不能丢，结构变更必须写成带版本号的迁移脚本，按顺序执行并支持回滚；本项目当前采用手写 SQL 迁移文件的做法。

数据库迁移的概念、工具对比和本项目两次迁移的实际操作，见第一部分《工程基础：数据库、存储与项目标识》第三节“数据库迁移”。

### 13. 前端权限控制只是体验优化

管理后台前端做了三件事：

1. 登录后保存令牌与权限点。
2. 路由守卫检查页面所需权限，没有权限就跳到第一个可用页面或“无可用权限”提示页。
3. 侧边栏菜单按权限点过滤，没权限的入口不显示。

这三件事都只能改善体验，不能作为安全边界。因为任何人都可以用工具直接发请求，绕过整个前端。真正的拦截必须在服务端，也就是每个后台接口上的 `require_permission`。

这也是面试里很常见的追问：“前端已经隐藏按钮了，为什么后端还要校验？”答案就是上面这句。

## 四、技术选型对比

### 1. 密码哈希：Argon2id 与 bcrypt、scrypt、PBKDF2

| 算法 | 原理 | 优势 | 劣势 | 使用情况 |
| --- | --- | --- | --- | --- |
| Argon2id | 内存硬算法，同时消耗内存与计算 | 抗图形处理器暴力破解最强；2015 年密码哈希竞赛冠军；参数可调 | 每次校验占用较多内存；老系统支持较少 | 新项目首选，OWASP 当前推荐的第一选择 |
| bcrypt | 基于 Blowfish 的慢哈希，可调代价因子 | 成熟稳定，语言支持极广；自带盐 | 有 72 字节输入上限；不消耗大量内存，抗显卡能力弱于 Argon2id | 大量存量系统仍在使用，很多公司默认选项 |
| scrypt | 内存硬算法，可调内存与并行度 | 抗硬件破解强；比 Argon2 更早出现 | 参数调不好容易占用过多内存；部分环境支持一般 | 加密货币与部分安全要求高的系统 |
| PBKDF2 | 对密码做大量带盐的重复哈希 | 实现最简单，标准库普遍自带；合规场景接受度高 | 只消耗计算不消耗内存，图形处理器破解效率高 | 老系统、受监管行业的历史系统；不推荐新项目单独使用 |

本项目的选择理由：这是一个新项目，没有历史兼容负担，直接选当前推荐度最高的 Argon2id，并用成熟的 `argon2-cffi` 封装，避免自己实现密码学细节。

### 2. 会话存储：数据库会话、无状态令牌、Redis 会话

先解释两个名词：

- 无状态令牌：令牌本身携带用户信息和签名，服务端不保存会话记录。最常见的实现是 JSON Web Token，直译是“JSON 网络令牌”。
- 有状态会话：服务端保存一条会话记录，令牌只是查询这条记录的钥匙。

| 方案 | 优势 | 劣势 | 典型场景 |
| --- | --- | --- | --- |
| 数据库会话 | 实现简单，数据持久；可随时撤销、可按账号批量撤销；不依赖额外组件 | 每次请求多一次数据库查询；高并发时数据库压力较大 | 中小规模后台、需要强撤销能力的系统 |
| 无状态令牌 | 服务端不用查存储，水平扩展容易；适合多服务共享身份 | 主动撤销困难，只能等过期；令牌一旦泄露在有效期内都可用；需要额外设计刷新令牌 | 微服务、开放接口、跨域单页应用 |
| Redis 会话 | 查询快；支持过期和主动删除；多实例共享 | 多引入一个组件；需要处理持久化与高可用；内存成本 | 高并发互联网业务的主流方案 |

本项目第一阶段选择数据库会话，原因有三点：

1. 后台管理员数量很少，请求量低，多一次数据库查询完全可以接受。
2. 后台最重要的是“能立刻踢下线”，数据库会话可以直接写入撤销时间。
3. 当前项目 Redis 是可选组件，没有配置时也能运行，不应该让后台登录依赖它。

真实公司里，普通用户的高并发会话通常放 Redis，管理后台这种低流量但高安全要求的系统反而常放数据库。

### 3. 权限模型：角色权限控制与访问控制列表、属性权限控制

| 模型 | 中文全称 | 怎么描述权限 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 角色权限控制 | 基于角色的访问控制 | 账号拥有角色，角色拥有权限 | 管理成本低；新人分配角色即可；容易审计 | 角色数量膨胀后变复杂；难以表达“只能改自己部门的数据” | 绝大多数后台系统 |
| 访问控制列表 | 访问控制列表 | 每个资源单独列出谁能做什么 | 粒度最细，直观 | 资源和用户多了以后条目爆炸，难以维护 | 文件系统、少量敏感资源 |
| 属性权限控制 | 基于属性的访问控制 | 根据属性动态判断，例如部门、时间、资源归属 | 表达能力强，能写复杂规则 | 规则设计和排查复杂；性能开销大 | 大型企业、云平台、强合规场景 |

本项目的选择理由：后台的操作种类有限，岗位划分清晰，角色权限控制刚好匹配。将来如果需要“内容运营只能审核自己负责的板块”，可以在角色权限控制之外再加一条数据范围条件，这就是常见的“角色权限控制 + 数据权限”组合。

### 4. 分页：游标分页与页码分页

| 方案 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- |
| 游标分页 | 不重复不遗漏；深分页性能稳定；适合持续追加的数据 | 不能直接跳到第 N 页；实现稍复杂；排序字段必须稳定 | 信息流、审计日志、聊天记录 |
| 页码分页 | 用户可以直接跳页；实现简单；总数直观 | 数据变化时偏移；深分页慢 | 后台表格、搜索结果、数据量可控的列表 |

本项目的选择理由：审计日志持续追加，页码分页会重复或漏行；公开内容流也是无限下拉，不需要跳页。因此统一使用游标分页。

### 5. 数据库迁移：Alembic 与其他工具

本项目后端是 FastAPI + SQLAlchemy，Alembic 是 SQLAlchemy 官方的迁移工具，模型和迁移共享同一套元数据，因此选它。其他迁移工具各自的取舍见第一部分《工程基础：数据库、存储与项目标识》第三节“数据库迁移”。

### 6. 后台前端：Vue 3 + Element Plus 与 React + Ant Design

| 方案 | 优势 | 劣势 | 使用情况 |
| --- | --- | --- | --- |
| Vue 3 + Element Plus | 上手快；中文文档完善；表格、表单、弹窗组件齐全；与国内团队协作成本低 | 复杂状态管理不如 React 生态丰富；超大型应用的组织方式需要额外约定 | 国内中后台非常常见 |
| React + Ant Design | 组件质量高；生态最大；适合复杂交互和长期演进 | 概念更多，学习曲线更陡；需要自行组合路由、状态管理等方案 | 国内外大型中后台常见 |

本项目的选择理由：后台以表格、筛选、表单、弹窗为主，Element Plus 覆盖度高；项目里的另一套前端已经使用 Vue 3，团队心智负担更小；后台是独立工程，不和用户端打包在一起。

## 五、面试题

### 问题一：管理后台为什么不用普通用户的账号体系？

**总结版**：两类身份的注册方式、数量、权限和会话策略完全不同。独立账号、独立会话、独立鉴权可以把风险隔开，避免普通用户端的漏洞直接影响后台。

**详细版**：

第一，注册门槛不同。普通用户用手机号加验证码就能注册，几乎无门槛；管理员账号必须由内部创建，不能开放自助注册。

第二，权限大小不同。普通用户只能操作自己的内容；管理员可以审核全平台内容、封禁用户、查看审计日志。权限差距越大，越不应该共用身份表。

第三，会话策略不同。普通用户希望长期免登录；管理员应该短会话、可随时踢下线。同一个会话表很难同时满足。

第四，故障隔离。如果共用一套令牌解析代码，一处越权漏洞会同时影响用户端和后台。分开之后，两套令牌的格式、摘要前缀、解析函数都不同，不能互相冒用。

第五，审计要求不同。后台操作必须记录操作人，普通用户行为日志的留存要求通常低得多。独立表也方便单独设置权限和保留策略。

### 问题二：说说你的权限设计，权限是怎么校验的？

**总结版**：三层模型，管理员拥有角色，角色拥有权限点，最终权限是并集。每个后台接口用 `require_permission("权限点")` 声明所需权限，服务端在进入业务逻辑前校验，没有权限返回 403。前端隐藏菜单只改善体验。

**详细版**：

数据层有四张表：管理员表、角色表、管理员角色关联表、角色权限关联表。权限点是最小操作单位，例如 `post.review` 表示审核饭帖。

登录时，服务端查询该管理员所有角色的权限点，去重排序后和令牌一起返回。前端用这份列表决定菜单和按钮是否显示。

接口层使用 FastAPI 的依赖注入。路由函数声明 `Depends(require_permission("post.review"))`，请求进入业务代码之前，依赖会先解析令牌、确认会话有效、查询权限点，不满足就直接抛 403。

这样设计有三个好处：

1. 权限声明和接口定义在同一个位置，新增接口不容易漏。
2. 校验逻辑只写一次，所有接口行为一致。
3. 权限变更不需要改接口代码，只改角色与权限点的关联。

还要强调：前端隐藏按钮不是安全边界。任何人可以用命令行工具直接发请求，所以服务端必须独立校验。

### 问题三：密码应该怎么存？为什么选 Argon2id？

**总结版**：只存不可逆哈希，每个密码加随机盐，使用慢哈希算法。本项目选 Argon2id，因为它同时消耗内存和计算，抗显卡暴力破解能力最强，是当前新项目的首选。

**详细版**：

第一，绝不存明文。数据库泄露时，明文等于把所有账号直接交出去。

第二，不用可逆加密。可逆意味着只要密钥泄露就能还原全部密码。

第三，必须加盐。盐是随机值，让相同密码得到不同哈希，防止彩虹表批量反查。

第四，使用慢哈希。普通哈希算得太快，攻击者每秒能尝试几十亿次。密码哈希算法通过增加计算轮次、内存占用或并行度，把单次验证控制在几十毫秒，正常登录几乎无感，暴力破解成本却成倍上升。

Argon2id 是 2015 年密码哈希竞赛的获胜方案，结合了两种模式的优点，能抵抗侧信道攻击，同时强制占用大量内存。图形处理器虽然有大量核心，但内存带宽和容量有限，很难把 Argon2id 的尝试速度堆上去。

bcrypt 也很成熟，但输入有 72 字节上限，而且不消耗大量内存。PBKDF2 兼容性最好，但只消耗计算，抗显卡能力弱。scrypt 同样消耗内存，但参数配置和库支持不如 Argon2 统一。

最后补充一个实现细节：用户名不存在时也要执行一次虚拟哈希校验，避免攻击者通过响应时间判断账号是否存在。

### 问题四：会话令牌怎么设计？数据库会话和 JSON 网络令牌怎么选？

**总结版**：令牌用足够长的随机值，数据库只存摘要，设置过期时间并支持主动撤销。后台选数据库会话，因为管理员数量少、最重要的是能立即踢下线；高并发用户端常用 Redis；无状态令牌适合多服务共享身份但撤销困难。

**详细版**：

先看令牌生成。使用密码学安全的随机数生成器，长度足够，避免被猜中。本项目令牌以 `adm_` 开头，方便区分普通用户令牌。

再看存储。数据库只保存令牌的 SHA-256 摘要。请求带来令牌时，服务端重新计算摘要再查询。这样即使数据库泄露，攻击者拿到摘要也不能直接当令牌使用。

然后看会话记录。每条会话包含管理员标识、摘要、过期时间、撤销时间、来源地址和创建时间。注销不是删除记录，而是写入撤销时间，保留“谁在什么时候退出”的记录。

三种存储方案的取舍：

- 数据库会话：实现简单、持久、撤销方便，缺点是每次请求多一次查询。适合管理员这种低流量高安全场景。
- Redis 会话：查询快、支持过期和共享，缺点是多一个组件要运维。适合高并发用户端。
- 无状态令牌：服务端不查存储，扩展容易，缺点是撤销困难、令牌泄露后在有效期内一直可用。适合微服务之间或开放接口。

如果后台一定要用无状态令牌，通常会配合短有效期和刷新令牌，并把“强制下线”做成黑名单，但黑名单又回到了需要存储的问题。

### 问题五：两个管理员同时审核同一条饭帖，怎么避免重复操作？

**总结版**：在读取待变更记录时加数据库行锁，让两个事务串行执行；后到的请求读到已变更状态，走幂等分支直接返回，不重复写审计日志。同时状态机拒绝非法流转。

**详细版**：

先说不加锁会发生什么。两个事务都执行“查询状态、判断是待审核、修改状态、写日志”。由于两个事务彼此看不到对方未提交的修改，可能都判断成功，最终产生两条审计日志，甚至后一次覆盖前一次的结果。

解决方案有三种常见思路：

1. 悲观锁：查询时使用 `SELECT ... FOR UPDATE`，锁住这一行，第二个事务等待第一个提交。实现直接，适合冲突不频繁但必须正确的场景。
2. 乐观锁：给记录加版本号，更新时带上前一次读到的版本号，更新影响行数为零就说明被别人改过。适合冲突很少、读多写少的场景。
3. 条件更新：直接把状态作为更新条件，例如 `UPDATE ... WHERE id = ? AND status = 'pending_review'`，根据影响行数判断是否成功。实现简单，但一次只能完成一个字段的流转。

本项目选悲观锁，因为审核冲突不频繁，加锁范围只有一行，代价很小，而且代码最直观。

同时配合幂等：如果记录已经是目标状态，直接返回当前状态并标记 `changed=false`。这样既防止并发重复，也防止用户连点。

还要注意数据库差异：SQLite 不支持 `FOR UPDATE`，SQLAlchemy 会忽略它，所以测试环境通过；生产 PostgreSQL 才会真正加锁。

### 问题六：审计日志应该怎么设计？

**总结版**：只追加，不修改不删除；记录操作人、时间、来源、对象、动作、原因、请求标识和前后快照；业务变更与日志在同一事务提交；应用层不提供删除接口，生产环境可进一步限制数据库账号权限。

**详细版**：

第一，字段设计。至少包含：操作人标识、操作人名称快照、动作、对象类型、对象标识、原因、变更前快照、变更后快照、来源地址、请求标识、创建时间。操作人名称单独存快照，是因为账号以后可能改名或停用，历史日志仍然要能读懂。

第二，写入时机。审计日志必须和业务变更在同一个事务里提交。如果先提交业务再写日志，日志可能失败；如果先写日志再提交业务，业务可能回滚。两种都会造成不一致。

第三，只追加原则。应用层不提供修改和删除接口。测试里专门验证了删除请求返回 405。生产环境还可以让数据库账号只有插入和查询权限。

第四，查询能力。支持按操作人、动作、对象类型、对象标识、时间范围筛选，使用游标分页。审计日志持续追加，页码分页会重复或漏行。

第五，敏感信息。日志里只放关键字段快照，不记录密码、完整手机号、令牌这类敏感数据。否则审计日志本身会变成新的泄露源。

第六，保留策略。真实公司会根据合规要求设置保留期，例如六个月或三年，到期归档而不是直接删除。归档也要保证不可篡改。

### 问题七：封禁用户时要注意什么？

**总结版**：改状态只是第一步，还必须撤销该用户所有未注销会话；封禁不删除数据，保证可恢复；解封后不恢复旧会话，要求重新登录；系统账号要保护；整个过程要写审计日志。

**详细版**：

第一，撤销会话。用户手里的令牌在过期前一直有效，如果只改状态不撤销会话，用户仍然可以继续操作。本项目封禁时批量写入所有未注销会话的撤销时间。

第二，解析会话时双重检查。即使某个会话没被撤销，解析时也会检查账号状态，停用账号直接拒绝。这是双保险。

第三，不删除数据。封禁是临时措施，不是注销。删除用户会连带影响饭帖、点赞、收藏、审计记录，既不可恢复，也可能破坏统计口径。

第四，解封不恢复旧会话。无法判断旧令牌是否已经泄露，要求用户重新登录更安全。

第五，保护特殊账号。系统账号不允许通过后台封禁，避免误操作导致演示数据或系统流程失效。

第六，必须写审计日志。封禁是高风险操作，必须记录谁、什么时间、为什么封禁了谁，以及撤销了多少个会话。

第七，接口要幂等。重复封禁返回当前状态，不重复写日志；重复解封同理。

## 二、地图服务选型与后端代理

### 1. 地图服务商的常见选择

市面上常见的地图服务有三类：

| 类型 | 代表产品 | 特点 | 常见使用场景 |
| --- | --- | --- | --- |
| 国内商业地图服务 | 高德地图、百度地图、腾讯地图 | 国内地点数据全、合规、接口稳定，需要申请密钥，免费额度有限 | 国内应用的地点搜索、导航、定位 |
| 国外商业地图服务 | Google Maps、Mapbox | 海外数据强，国内访问和合规成本高 | 面向海外用户的应用 |
| 开源地图方案 | OpenStreetMap、Leaflet、OpenLayers | 免费、可自建，但地点数据和导航能力要自己维护 | 预算有限、需要完全可控的内部系统 |

公司真实使用中，面向国内用户的产品大多数会选择高德、百度或腾讯中的一家，原因是地点数据、坐标体系和导航唤起能力都已经成熟，不需要自己维护地图数据。三家的选择通常取决于：
- 团队已有的账号和商务合作；
- 小程序、手机应用对导航唤起的支持程度；
- 地点搜索、路径规划、静态地图等具体接口的配额和价格。

本项目是个人开发的非商业应用，最终选择腾讯位置服务，主要原因是免费额度最适合这个场景：

| 服务商 | 个人开发者的免费情况 | 坐标体系 | 本项目是否适合 |
| --- | --- | --- | --- |
| 腾讯位置服务 | 每个接口每天 1 万次调用、每秒 5 次查询，仅限非商业用途 | 国测局坐标系（GCJ-02） | 适合：日常开发和小规模上线足够 |
| 高德地图 | 个人开发者关键词搜索额度较低（现行价格页约为每月 5000 次、每秒 3 次，具体以官网为准） | GCJ-02 | 可用，但搜索额度更容易用完 |
| 百度地图 | 有免费额度，但使用 BD-09 坐标 | BD-09 | 不合适：与已有坐标不一致，需要转换，位置会偏几十到几百米 |
| OpenStreetMap 公共接口 | 数据免费，但公共服务有严格使用政策，不保证可用性 | WGS-84 | 不适合：国内地点数据不够全，公共接口不能商用、无服务承诺 |

除了额度，腾讯的接口形态也简单：地点搜索和静态地图都是普通网络请求，返回结构化数据或一张图片，不强制绑定客户端软件开发工具包；地点编号和坐标可以直接用于导航链接；Flutter 用普通图片组件和系统浏览器就能接入。

需要说明的是，免费额度只适用于个人学习和非商业项目。如果这个应用将来要上架收费、投放广告或由公司运营，就需要按腾讯的商业授权购买额度，这是选择任何商业地图服务商都要面对的成本。

### 2. 腾讯接口与高德接口的关键差异

切换供应商不是改一个域名那么简单，下面这些差异如果漏改，会出现“搜索不到”“地图位置偏移”“导航打不开”等问题：

| 对比项 | 腾讯位置服务 | 高德地图 |
| --- | --- | --- |
| 地点搜索路径 | `/ws/place/v1/search` | `/v3/place/text` |
| 关键词参数名 | `keyword` | `keywords` |
| 搜索范围参数 | `boundary=nearby(纬度,经度,半径,是否自动扩大)` | `location=经度,纬度` |
| 坐标顺序 | 纬度在前、经度在后 | 经度在前、纬度在后 |
| 成功标志 | `status` 等于数字 0 | `status` 等于字符串 "1" |
| 距离字段 | `_distance` | `distance` |
| 静态地图路径 | `/ws/staticmap/v2/` | `/v3/staticmap` |
| 静态地图中心点 | `center=纬度,经度` | `location=经度,纬度` |
| 导航链接 | `apis.map.qq.com/uri/v1/marker` | `uri.amap.com/marker` |

两家都使用 GCJ-02（国测局坐标系），所以数据库里已经保存的店铺坐标不需要转换，这是本次能平滑切换的前提。如果当初选了百度，坐标是 BD-09，切换时就必须批量转换历史数据，否则地图上的标记会整体偏移。

### 3. 腾讯的签名校验：Key 与 Secret Key

腾讯的密钥有两种：

- **Key（开发密钥）**：写在请求地址里，用来标识“是哪个应用在调用、扣哪个账号的额度”。
- **Secret Key（简称 SK）**：32 位字符串，不在网络上传输，只用来计算签名。控制台开启“签名校验”后才会生成。

只靠 Key 不够安全：Key 会出现在请求地址、代理日志、浏览器网络面板里，一旦泄露，别人就能拿你的额度去调用。SK 相当于第二把钥匙，只有同时持有 Key 和 SK 才能算出正确的签名，从而证明请求确实来自你的服务端。

签名算法（GET 请求）只有四步：

1. 取请求路径，例如 `/ws/place/v1/search`；
2. 把所有参数按参数名从小到大排序；
3. 用“参数名=原始值”并用 `&` 连接，值必须是未编码的原始数据；
4. 拼成“路径?排序后的参数+SK”，对整串做 MD5，得到 32 位小写字符串，作为 `sig` 参数一起发送。

本项目的实现放在 `map_service.py` 的 `_signature()` 函数里，SK 从环境变量 `TENCENT_MAP_SECRET_KEY` 读取，绝不进入客户端。几个容易踩的坑：

- **sig 不能参与排序**：签名算完后再把 `sig` 加进参数，否则会陷入“签名需要包含签名本身”的死循环。
- **路径必须完全一致**：静态地图的请求路径是 `/ws/staticmap/v2/`，结尾有斜杠，签名里也必须带斜杠。
- **签名用原始值，发送时再编码**：MD5 时用未编码的中文和括号，真正发请求时由网络库做网址编码。
- **特殊字符要过滤**：`#`、`%`、`&` 会破坏“参数名=值”的拼接结构，腾讯建议在端上过滤；本项目的搜索关键词会先去掉这三个字符。
- **SK 泄露要重新生成**：控制台支持重置 SK，重置后旧签名立即失效。

除了签名校验，腾讯还提供两种访问限制，可以按需选择：

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 签名校验 | 每个请求附带用 SK 计算的 sig | 安全性最高，请求被篡改会失败 | 有开发量，参数变化后要重新签名 |
| IP 白名单 | 只允许指定服务器 IP 调用 | 配置简单，无需写代码 | 服务器 IP 变化时要同步修改 |
| 域名白名单 | 只允许指定网页域名调用 | 适合浏览器端调用 | 只对网页来源有效，服务端调用不适用 |

常见状态码也要能区分：`110` 表示请求来源未被授权（IP 或域名白名单不通过），`111` 表示签名验证失败（SK 不对或参数拼接错误），`121` 表示该 Key 当天调用量已达上限（配额问题，不是代码问题）。

### 4. “Web 服务接口”和“地图软件开发工具包”的区别

**软件开发工具包（Software Development Kit，缩写为 SDK）** 是厂商提供的一套客户端代码库，用来简化某个平台上的开发。地图软件开发工具包通常负责在客户端绘制可交互地图、处理手势缩放、显示定位点。

**Web 服务接口（Web Service API）** 是通过网络地址调用的普通接口，返回结构化数据（通常是 JSON 格式）或图片。它不负责在界面上画地图，只负责给出数据。

两者的对比如下：

| 对比项 | 地图软件开发工具包 | Web 服务接口 |
| --- | --- | --- |
| 运行位置 | 客户端（小程序、手机应用、浏览器） | 服务端或客户端都可以，但通常放服务端 |
| 是否需要密钥 | 需要，且密钥会进入客户端 | 需要，但可以只放在服务端 |
| 是否需要地图组件 | 需要引入厂商组件或插件 | 不需要，普通网络请求即可 |
| 可交互地图 | 支持缩放、拖动、点击 | 只能搜索地点或返回一张静态图片 |
| 接入成本 | 三端各接一次，平台差异大 | 后端接一次，三端共用 |
| 适合场景 | 需要完整地图交互 | 只需要“搜地点 + 看位置 + 导航” |

本项目只需要“发布时搜店铺、详情页看店铺位置、点按钮导航”，不需要在页面里拖动地图，所以选择 Web 服务接口。这样后端只写一次，所有客户端都调用同一套接口。

### 5. 为什么密钥必须放在后端

**密钥（Key）** 是调用地图服务时用来标识“是谁在调用、该扣谁的额度”的一串字符。

如果把密钥写在小程序或手机应用里：
1. 小程序的代码包可以被解包，手机应用可以被反编译，密钥很容易被提取；
2. 浏览器里按 F12 打开网络面板就能看到请求地址中的密钥；
3. 密钥泄露后，别人可以拿你的额度去刷自己的业务，费用由你承担。

放在后端后，客户端只知道“调用我们自己的接口”，不知道腾讯的密钥。后端还可以统一做登录校验、限流、缓存和错误处理。

**这种“客户端调用自己的后端，后端再调用第三方服务”的结构叫作代理（Proxy）。**

### 6. 代理的代价与应对

代理不是没有成本：
- **多一跳网络**：客户端到后端、后端到腾讯，总耗时比直连略高；
- **后端带宽**：静态地图图片要经过后端转发，访问量大时会占用带宽；
- **单点故障**：后端不可用时地图也不可用；
- **配额集中**：所有用户共用同一个密钥的额度。

本项目的应对方式：
- 静态地图响应设置一天的浏览器缓存，同一张店铺地图不会反复请求；
- 腾讯地图请求设置 6 秒超时，地图服务卡住时不会拖垮发布流程；
- 没有配置密钥时返回 503 并给出明确提示，客户端降级为手动填写地址；
- 地点搜索要求登录，避免匿名用户把接口当成免费的地点搜索代理；
- 地点搜索限制关键词长度和返回数量，减少无效调用。

更成熟的生产系统还会增加：按用户或来源地址限流、Redis 缓存热门关键词、熔断与重试、图片内容分发网络缓存。至于“多个地图服务商互为备份”，本项目刻意没有做，原因见本节第 9 小节“为什么不做双地图”。

### 7. 什么是“兴趣点”

**兴趣点（Point of Interest，缩写为 POI）** 是地图上一个有名字、有坐标的地点，例如一家餐厅、一个地铁站、一所学校。地点搜索接口返回的就是一组兴趣点。

本项目只保存兴趣点的编号、名称、坐标和地址。编号用于以后重新拉取或去重；坐标用于静态地图和导航；名称与地址用于展示和回填表单。

### 8. 静态地图与动态地图

- **动态地图**：可以拖动、缩放、点击标记，需要地图组件和脚本。
- **静态地图**：服务端直接生成一张带标记的图片，客户端用普通图片标签显示。

静态地图的优点是接入极简、加载稳定、不依赖地图组件；缺点是不能交互、缩放级别固定、尺寸受服务商限制。本项目详情页只需要“让用户知道店在哪”，静态地图足够。

那么全屏选点页为什么仍然用静态地图？三种方案对比如下：

| 方案 | 交互能力 | 密钥安全 | 接入成本 | 本项目 |
| --- | --- | --- | --- | --- |
| 原生地图软件开发工具包 | 完整拖动、缩放、标记 | 密钥进入客户端，需配置包名和签名 | 高 | 不选 |
| 网页视图嵌入地图网页 | 较完整 | 密钥进入网页，需处理网页与原生通信 | 中 | 不选 |
| 后端代理的静态地图图片 | 不能拖动，只能按坐标重新请求 | 密钥只在后端 | 低 | 选用 |

需求只要求“搜索 → 地图定位到店铺 → 看详情 → 确认”，不需要用户自由拖动地图，所以静态图足够。代价是不能手指平移，页面用三个按钮弥补：放大、缩小、回到当前位置。每次中心点或缩放变化，都会用新参数请求一张新图片。

**软件开发工具包（Software Development Kit，缩写 SDK）** 是厂商提供的客户端代码库，前面第 4 小节已经对比过它和 Web 服务接口的差别。地图 SDK 负责在客户端绘制可交互地图，功能完整，但需要分别接入安卓和苹果，而且密钥必须下发到客户端。

### 9. 为什么不做“双地图”：单一供应商的取舍

“双地图”指同时接入两家地图服务商，一家失败时自动切换另一家。听起来更稳，但对这个项目来说，复杂度远大于收益：

1. **两套协议**：两家接口的路径、参数名、坐标顺序、响应字段都不同。腾讯用 `keyword` 加 `boundary=nearby(纬度,经度,半径,是否自动扩大)`，高德用 `keywords` 加 `location=经度,纬度`；距离字段一家叫 `_distance`，另一家叫 `distance`。每加一个地图能力都要写两遍适配。
2. **两套地点编号**：同一家店在两家服务商里的编号不同。如果一会儿用腾讯、一会儿用高德，同一条饭帖可能被存成两条，“重新拉取店铺信息”和去重都会失效。
3. **两套错误码与配额**：需要分别处理密钥错误、配额超限、参数错误，还要监控两份额度，测试用例也要写两遍。
4. **切换策略本身有坑**：采用“主供应商失败再切备用”时，用户可能先后看到两份不一致的结果；采用“同时请求取最快”时，调用量直接翻倍，免费额度也消耗翻倍。
5. **个人项目没有这个需求**：单家每天 1 万次的额度，在真实用户量起来之前根本用不完。等真的不够用时，说明产品已经有规模，那时购买商业额度比长期维护两套代码更划算。

更重要的是：**代理层已经隔离了供应商**。客户端只认后端返回的 `name/address/lat/lng`，将来真要换地图，只需要重写 `map_service.py` 里的两个函数，客户端不需要发版。既然切换成本已经被架构控制住，就没有必要为“不确定的将来”提前付出双份维护成本。这是“避免过度设计”的一个具体例子。

## 三、数据模型设计

### 1. 新增字段

饭帖表新增了以下字段：

| 字段 | 类型 | 含义 | 为什么这样设计 |
| --- | --- | --- | --- |
| `avg_price` | 整数，可空 | 人均价格，单位元 | 餐饮人均很少精确到角，整数足够；可空表示用户不想填 |
| `taste_tags` | JSON 数组 | 口味标签 | 标签固定且数量少，用数组读写简单 |
| `store_lat` | 浮点数，可空 | 店铺纬度 | 导航需要精确坐标 |
| `store_lng` | 浮点数，可空 | 店铺经度 | 同上 |
| `store_poi_id` | 字符串，可空 | 腾讯地点编号 | 便于以后重新拉取或去重 |
| `deleted_at` | 时间，可空 | 软删除时间 | 为空表示未删除 |

状态字段新增了两个取值：
- `draft`：草稿；
- `deleted`：作者已删除。

原有状态仍然保留：`pending_review` 待审核、`published` 已发布、`rejected` 已拒绝、`unpublished` 已下架。

### 2. 为什么区分“发布者位置”和“店铺位置”

项目原本就有 `coarse_lat`、`coarse_lng`、`coarse_area`，表示发布者本人的粗略位置，只保留三位小数（约百米级），用于“附近三公里”推荐。

新增的 `store_lat`、`store_lng` 表示餐厅的精确位置，只用于详情页地图和导航，不参与附近排序。

两者不能合并，原因：
1. 精度要求不同：发布者位置要模糊化保护隐私，店铺位置本来就是公开信息，导航需要精确；
2. 用途不同：附近推荐关心“发布者在哪”，地图导航关心“店在哪”；
3. 隐私风险不同：如果用自己的精确位置代替店铺位置，会暴露发布者住址或公司地址。

### 3. 人均价格为什么用整数

金额在计算机里用浮点数（小数）会出现精度问题，例如 `0.1 + 0.2` 不一定等于 `0.3`。严肃的金融系统通常用“最小货币单位整数”（例如分）或高精度十进制类型。

本项目的人均价格是估算值，不是账单金额，精确到元已经足够，所以直接用整数元。如果以后要做订单、结算，应该改成“分”为单位的整数，或者使用数据库的精确小数类型。

### 4. 口味标签为什么先用 JSON 数组

**关联表** 是指再建一张“饭帖—标签”表，每一行表示某条饭帖拥有某个标签。它的优点是查询和统计方便，缺点是每次读写都要多查一张表，代码更复杂。

需要区分两件事：
- **标签字典**（有哪些合法标签、顺序、是否启用）放在独立的 `taste_tags` 表里；
- **饭帖选了哪些标签**仍然用饭帖表的 JSON 数组保存。

本项目的标签每条饭帖最多三个、只用于展示和简单筛选，所以选择这种“字典表 + JSON 数组”的组合：
- 写入简单：一次保存整个数组；
- 读取简单：一次返回整个数组；
- 不需要额外的表和关联查询。

缺点是：
- 按标签统计或筛选时，数据库无法高效使用普通索引，需要额外处理；
- 标签改名或删除时，历史 JSON 数据不会自动更新；
- 无法用外键保证标签一定合法，只能靠应用层校验。

如果以后要做“按口味标签筛选”“统计最受欢迎的口味”，就应该拆分出标签表和关联表。这是典型的“先简单、后演进”，不是一开始就过度设计。

### 5. 口味标签最终改为数据库字典

口味标签必须固定，不能让用户自由输入。原因是自由输入会产生“辣”“有点辣”“微辣口”等同义标签，无法筛选也无法统计。

最初的做法是“后端写一个固定枚举，前端写一份相同选项”。这个方案很快暴露了问题：两端的值没有强制性关联，后端改了一个值、前端忘了改，就会出现“前端能选、后端拒绝”的 422 错误，这正是缺陷 BUG-001。

最终改成**数据库字典**：
- 表 `taste_tags` 保存标签文字、展示顺序、是否启用；
- 接口 `GET /taste-tags` 只返回启用中的标签，前端按返回顺序展示；
- 后端在“发布、存草稿、改草稿、草稿发布”四个写入入口统一查库校验，未知或停用标签返回 422，错误码 `TASTE_TAG_INVALID`。

这样做的优点：
1. 只有一份数据源，前后端不可能再各写一套；
2. 运营增减标签、调整顺序、临时停用标签，只改数据库，不需要发客户端版本；
3. 停用不删除，历史饭帖里的旧标签仍然能正常展示。

代价与取舍：
- 每次保存要多一次轻量查询；标签表只有十几行，这点开销可以忽略；
- 标签改名不会自动更新历史饭帖的 JSON 数组；口味标签基本不会改名，可以接受；
- 没有做后台标签管理页面，目前用数据库工具维护，等运营真的需要自助操作时再补。

**字典表的具体结构**

表结构：

```text
taste_tags
- name        标签文字，主键
- sort_order  展示顺序
- enabled     是否启用
- created_at  创建时间
```

初始数据就是旧前端展示的 9 个：清淡、正常、香辣、酸甜、咸鲜、油炸、烧烤、汤羹、面食。

为什么用标签文字直接做主键：饭帖里保存的也是标签文字（JSON 数组），文字做主键可以让两边直接对应，查询时不用再关联。代价是改标签文字要同步改历史数据；口味标签基本不改名，可以接受。

为什么用“停用”而不是删除：历史饭帖可能还引用这个标签，直接删行会让历史内容出现“查不到的标签”。停用后新内容不能选，历史内容照常展示。

为什么只下发启用中的标签：停用的标签不该再出现在新发布的内容里；历史详情仍然按饭帖里保存的文字展示，不受影响。

**四个写入校验点**

口味标签的校验放在服务层函数 `validate_taste_tags` 里，被四个入口调用：

1. `POST /posts` 直接发布；
2. `POST /posts/drafts` 新建草稿；
3. `PUT /posts/{id}/draft` 更新草稿；
4. `POST /posts/{id}/publish` 草稿发布。

只在一个入口校验是不够的：客户端可以绕过发布页，直接调草稿接口写入非法标签。四个入口共用同一个函数，规则只有一份，新增入口时也不容易漏。

为什么先校验标签再校验图片：标签校验只是一次轻量查库，图片校验要查多张图片的归属和状态；参数本身不合法时尽早失败，避免无意义的重查询。

### 6. 用户历史定位表

本项目只需要“最近一次在哪”，所以每个账号只保留一条记录，主键就是账号编号：

```text
user_locations
- account_id  主键，同时是外键，指向 users.id
- lat         纬度
- lng         经度
- area        区域名称，可为空
- updated_at  更新时间
```

为什么用账号编号直接做主键：一个账号只能有一条，主键天然保证唯一；保存时先查、没有就插入、有就覆盖，逻辑简单，也不会出现同一账号多条记录。

为什么不在手机本地保存、为什么不做定位流水，见第三部分第七节第 3 小节。

### 7. 软删除

**软删除** 是不真正删除数据库记录，而是把状态改成 `deleted` 并记录删除时间。**物理删除** 是执行 `DELETE` 语句把行删掉。

本项目选择软删除，原因：
1. 点赞、收藏、审核记录都引用这条饭帖，物理删除会产生悬空引用；
2. 内容安全场景需要保留证据，删除后仍要能追溯；
3. 以后可以做“最近删除”恢复功能；
4. 统计口径不会因为用户删除而突然变化。

公开列表只查询 `status = published`，所以软删除后内容立刻不可见。作者删除时统一把状态改成 `deleted`，并写入 `deleted_at`。

软删除有一个容易踩的坑：**唯一约束仍然生效**。例如“同一作者 + 同一幂等键只能有一条饭帖”的唯一约束，不会因为状态变成 `deleted` 就失效。如果用户删除后用同一个幂等键重新发布，数据库会报唯一约束冲突。本项目的处理方式是：查询幂等结果时排除 `deleted` 和 `draft`，但数据库层面仍保留唯一约束。更彻底的做法是把唯一约束设计成“只对未删除记录生效”的部分唯一索引，这需要数据库支持，SQLite 与 PostgreSQL 的写法也不同。

### 8. 草稿为什么也放在饭帖表

草稿和已发布饭帖的字段几乎完全一样，只是允许内容不完整、状态不同。如果单独建一张草稿表，会出现两套几乎相同的字段和两套转换代码，维护成本高。

放在同一张表的好处：
- 字段复用；
- 草稿发布只是改状态，不需要复制数据；
- 图片、作者、审核记录等关联都可以直接复用。

代价是：所有公开查询都必须显式排除草稿和已删除内容。本项目在首页、热榜、详情、我的发布、后台审核列表都分别处理了这一点，并用测试覆盖。

## 四、草稿功能的设计

### 1. 草稿与发布使用两套校验

- 草稿请求模型只校验长度和格式，允许标题为空、评价为空、图片为零张、来源为空；
- 发布请求模型要求标题、评价、至少一张图片，并且外卖必须填店名、到店必须填地址。

为什么不在草稿阶段就强制完整？因为草稿的意义就是“先存一半”。如果存草稿也要填完所有内容，草稿就没有价值了。

为什么发布不直接信任草稿？因为草稿可能是在旧版本客户端保存的，或者被绕过前端直接调用接口写入。发布时必须重新走完整校验，草稿不能成为绕过审核规则的凭证。

### 2. 为什么更新草稿用 PUT 而不是 PATCH

**PUT** 表示“用请求体整体替换资源”，**PATCH** 表示“只修改请求体中出现的字段”。

发布页每次都持有完整表单，保存草稿时直接提交全部字段并用新值覆盖旧值，逻辑最简单，也不会出现“这个字段没传到底是没改，还是被清空”的歧义。

如果以后要做“自动保存单个字段”，才需要考虑 PATCH。

### 3. 草稿的创建、更新、发布、删除

| 操作 | 接口 | 说明 |
| --- | --- | --- |
| 新建草稿 | `POST /posts/drafts` | 允许内容不完整 |
| 更新草稿 | `PUT /posts/{编号}/draft` | 整体覆盖，仅作者本人 |
| 发布草稿 | `POST /posts/{编号}/publish` | 请求体是完整的发布内容 |
| 查看草稿 | `GET /me/drafts/{编号}` | 返回编辑页需要的原始字段 |
| 草稿列表 | `GET /me/drafts` | 按更新时间倒序分页 |
| 删除草稿 | `DELETE /posts/{编号}` | 软删除，仅作者本人 |

“我的发布”列表会自动排除草稿和已删除内容，草稿只在独立的草稿箱接口中出现。

### 4. 幂等键与草稿的关系

**幂等（Idempotent）** 是指同一个操作执行一次和执行多次，结果相同。发布接口使用 `Idempotency-Key` 请求头实现幂等：同一个用户用同一个键重复提交，后端返回第一次的结果，不会产生两条饭帖。

草稿不需要幂等键：
- 草稿本身就是一条可编辑的数据，重复保存只是覆盖或新增草稿；
- 草稿不会出现在公开列表，不会造成公开内容重复；
- 如果客户端真的重复提交，用户可以在草稿箱里看到并删除多余的一条。

草稿发布也不需要幂等键：发布成功后草稿状态变成 `published`，重复请求会得到“这不是草稿”的业务错误，不会重复创建内容。

### 5. 为什么不属于自己的内容返回 404 而不是 403

**403** 表示“我知道这个资源存在，但你无权访问”；**404** 表示“这个资源不存在”。

如果删除别人的饭帖返回 403，攻击者可以通过状态码判断“这个编号确实存在”，从而枚举内容。统一返回 404 可以隐藏资源是否存在。

当然，如果产品需要明确告诉用户“这是别人的内容”，也可以返回 403。本项目选择更保守的 404。

## 五、接口清单

所有业务接口统一使用 `/api/v1` 前缀，统一返回 `{ code, message, data }` 包装。下表合并了两次迭代新增的接口。

| 方法 | 路径 | 是否需要登录 | 作用 |
| --- | --- | --- | --- |
| GET | `/api/v1/maps/config` | 否 | 返回地图功能是否可用 |
| GET | `/api/v1/maps/places` | 是 | 按关键词搜索地点 |
| GET | `/api/v1/maps/static` | 否 | 返回静态地图图片 |
| GET | `/api/v1/taste-tags` | 否 | 返回启用中的口味标签字典，按展示顺序排列 |
| GET | `/api/v1/me/location` | 是 | 读取当前账号最近一次保存的定位；没有则为 `null` |
| PUT | `/api/v1/me/location` | 是 | 保存/覆盖当前账号最近一次定位 |
| POST | `/api/v1/posts` | 是 | 直接发布饭帖 |
| POST | `/api/v1/posts/drafts` | 是 | 新建草稿 |
| PUT | `/api/v1/posts/{编号}/draft` | 是 | 更新草稿 |
| POST | `/api/v1/posts/{编号}/publish` | 是 | 发布草稿 |
| DELETE | `/api/v1/posts/{编号}` | 是 | 删除自己的饭帖或草稿 |
| GET | `/api/v1/me/drafts` | 是 | 我的草稿列表 |
| GET | `/api/v1/me/drafts/{编号}` | 是 | 我的草稿详情 |

`/maps/places` 必须同时携带 `lat`（纬度）和 `lng`（经度）。缺少任意一个时返回 400，错误码为 `LOCATION_REQUIRED`，提示“请先开启定位后再搜索店铺”。原因见第三部分第七节“定位兜底流程”。

列表卡片与公开详情新增返回：
- `avgPrice`：人均价格，可能为空；
- `tasteTags`：口味标签数组；
- `storeLocation`：店铺坐标对象，可能为空。

**为什么保存定位用 PUT 而不是 POST**：

- `POST` 通常表示“新建一个资源”，重复提交可能产生多条记录；
- `PUT` 表示“把资源整体替换成请求体里的值”，同一账号重复提交结果相同，天然幂等。

**幂等（Idempotent）** 是指同一个操作执行一次和多次，最终结果相同。定位保存用 PUT，网络重试不会产生多条记录。

## 六、定位基础

### 1. 系统定位服务与 App 定位权限不是一回事

手机定位能不能用，取决于两层开关：

| 层级 | 是什么 | 在哪里控制 | 关闭后的表现 |
| --- | --- | --- | --- |
| 系统定位服务 | 整台手机的位置能力总开关 | 安卓下拉快捷开关、设置里的“位置信息”；苹果的“隐私与安全性 → 定位服务” | 所有应用都拿不到位置 |
| App 定位权限 | 当前应用是否被允许使用位置 | 首次使用时系统弹窗；之后在应用权限里修改 | 其他应用不受影响，只有本应用拿不到 |

所以代码里必须先查“系统定位服务是否开启”，再查“本应用有没有权限”。只查其中一项会出现误判：系统开关关着但权限已允许，仍然拿不到位置；权限被拒绝但系统开关开着，也拿不到位置。

### 2. 定位权限的几种状态

以 Flutter 的 `geolocator` 插件为例，权限状态有：

- `denied`：还没授权，或者用户这次点了拒绝。可以再次弹出系统授权框。
- `deniedForever`：用户选择了“不再询问”，或者系统策略禁止。此时再调用“申请权限”不会弹框，只能引导用户去应用设置里手动打开。
- `whileInUse`：只允许应用在前台时使用位置。本项目只需要前台取一次位置，这个状态就够用。
- `always`：始终允许，包括后台。本项目不需要后台定位，不应该申请这个权限。

**为什么不申请后台定位**：后台定位耗电更高、审核更严、隐私风险更大，而“选店铺”只需要用户看着屏幕时取一次位置。权限要按最小必要原则申请。

### 3. 定位精度等级

`geolocator` 提供多个精度等级，常用的有：

| 等级 | 大致含义 | 耗电 | 适用场景 |
| --- | --- | --- | --- |
| `low` | 粗略位置，可能靠基站或网络 | 低 | 只看城市、看附近几公里 |
| `medium` | 平衡精度与速度 | 中 | 选店铺、看附近商家 |
| `high` | 高精度，通常启用卫星定位 | 高 | 导航、运动轨迹 |

本项目选 `medium`：选店铺不需要米级精度，`medium` 更快、更省电，室内也更容易成功。

### 4. 经纬度与坐标系

**纬度（Latitude）** 表示南北位置，范围 -90 到 90；**经度（Longitude）** 表示东西位置，范围 -180 到 180。

国内地图使用 **GCJ-02（国测局坐标系，俗称“火星坐标”）**。手机系统定位返回的通常是 WGS-84（国际通用坐标系），在国内直接画到腾讯地图上会有几十到几百米偏移。本项目使用的定位插件返回的是系统原始坐标，而腾讯地图静态图使用 GCJ-02；在当前“选附近店铺”的场景里，这个偏差可以接受，因为搜索本身由腾讯按附近范围计算，最终以腾讯返回的店铺坐标为准。更严格的做法是调用坐标转换接口，把 WGS-84 转成 GCJ-02 后再展示或存储。关于坐标系的更多内容见第三部分第二节。

## 七、定位兜底流程

### 1. 严格的三级顺序

发布页点击“外卖 / 到店”时执行：

1. **静默检查当前定位**：
   - 系统定位服务是否开启；
   - App 是否有定位权限；
   - 取一次当前位置（8 秒超时）。
2. 成功 → 使用当前定位，并异步保存到后端“最近定位”。
3. 失败 → 请求后端 `GET /me/location`，有历史定位就用历史定位。
4. 两者都没有 → 弹框“请先开启手机定位”，用户点“去开启”后跳系统设置。
5. 用户取消，或设置后仍未开启 → **来源保持原样**，不切换成外卖/到店。

为什么“来源保持原样”：如果用户点了外卖但定位失败，页面却已经切到外卖，用户会以为可以继续填，最后发布时才失败。保持原样能让用户明确知道“这一步没成功”。

### 2. 为什么“静默检查”而不是直接申请权限

第一次取位置时，如果直接调用会弹系统授权框。用户刚点“外卖”，还没理解为什么要位置，突然弹框很容易被拒绝；一旦拒绝，后续再申请会更麻烦。

所以流程是：
- 已经授权 → 静默取位置，用户无感；
- 没授权 → 不弹系统框，直接走历史定位；
- 历史定位也没有 → 用我们自己的弹框解释“外卖和到店需要用当前位置查找附近店铺”，用户点“去开启”后再申请权限或跳设置。

这样系统权限框只在用户明确同意后出现，授权率更高，体验也更自然。

### 3. 历史定位为什么放后端，而不是手机本地

对比三种常见方案：

| 方案 | 优点 | 缺点 | 本项目选择 |
| --- | --- | --- | --- |
| 只存手机本地（例如 `shared_preferences`） | 实现简单、不经过网络、隐私留在本机 | 换手机、重装应用、清缓存就丢失；同一账号多设备不共享 | 不选 |
| 存后端，每个账号一条最新记录 | 换设备仍可用；接口鉴权后只有本人能读；不依赖本地存储 | 需要多一个接口和一张表；定位数据离开手机 | 选用 |
| 存后端定位流水（每次定位一条历史） | 可分析轨迹 | 数据量大、隐私风险高、业务上不需要 | 不选 |

本项目选择“存后端，每个账号一条最新记录”：换设备仍可用、接口鉴权后只有本人能读、不依赖本地存储。表结构与主键设计见第三部分第三节第 6 小节“用户历史定位表”。

### 4. 为什么保存 6 位小数，而公开位置只留 3 位

- 历史定位是**本人私密数据**，只用于给地图一个中心点，保留 6 位小数（约 0.1 米）足够精确，也不会无意义地损失精度。
- 饭帖的“大概位置”是**公开数据**，会出现在首页“附近”，所以后端统一四舍五入到 3 位小数。纬度 1 位小数约 11 公里，3 位小数约 100 米，既能表达“在哪个片区”，又不至于暴露具体楼栋。

同一份坐标，用途不同，精度策略就不同。这是数据最小化原则的具体应用。

### 5. “去开启”之后做什么

用户点“去开启”后，代码分两种情况：

1. **系统定位服务没开**：调用 `openLocationSettings()` 跳系统“位置信息”设置页；如果跳转失败，退回 `openAppSettings()` 打开本应用设置。
2. **系统定位已开，但 App 权限被永久拒绝**：只能 `openAppSettings()`，让用户手动打开权限。
3. **系统定位已开，权限只是普通拒绝**：直接 `requestPermission()` 再弹一次系统授权框。

跳转设置后不会自动重试定位：用户回到应用后需要再点一次“外卖 / 到店”。这样逻辑简单，也避免用户还在设置页时应用反复请求。

## 八、全屏静态地图选点页

### 1. 页面结构

页面是一个全屏堆叠布局：

- 底层：`Image.network` 展示静态地图，铺满屏幕；
- 中心：固定一个定位标记。静态图不能拖动，屏幕中心就是地图中心，标记指向的正是当前中心点；
- 顶部：返回按钮和页面标题；
- 右侧：放大、缩小、回到当前位置；
- 底部：浮动面板，包含搜索框、搜索结果列表（可滚动，点击切换）、确认按钮。

底部面板用 `Positioned` 固定在底部，并加上键盘高度 `MediaQuery.viewInsets`，键盘弹出时面板整体上移，输入框不会被遮住。

### 2. 1 秒防抖是什么

**防抖（Debounce）** 是指：事件连续触发时，只在“最后一次触发后等待一段时间没有新事件”才真正执行。用户每输入一个字都会触发一次输入事件，如果每次输入都请求地图接口，打十个字就是十次请求，既浪费配额又容易卡顿。

本项目用 `Timer` 实现防抖：

```dart
void _onKeywordChanged(String _) {
  _debounce?.cancel();          // 取消上一次还没到时间的任务
  _debounce = Timer(const Duration(seconds: 1), _search);
}
```

每次输入都取消旧计时器、重新计时 1 秒；用户停手 1 秒后才真正搜索。用户点键盘上的“搜索”或页面上的“搜索”按钮时，立即取消计时器并马上请求。

**防抖和节流的区别**：

| 名称 | 行为 | 类比 |
| --- | --- | --- |
| 防抖 | 连续触发结束后只执行一次 | 电梯门：有人不断进出就一直不关，最后一个人进来后等几秒才关 |
| 节流 | 固定时间内最多执行一次 | 红绿灯：不管来多少车，每 30 秒只放行一批 |

搜索框适合防抖，因为用户想要的是“输入完成后搜一次”；滚动加载更多适合节流，因为过程中需要持续触发。

### 2.1 搜索结果为什么展示成列表

地图的地点搜索返回的是“兴趣点（Point of Interest，缩写 POI，指地图上的餐厅、商场、车站等具体地点）”列表，而不是唯一答案。搜索“肯德基”时，附近可能有三家分店，名称相同、地址不同；接口会按距离、匹配度等规则排序返回，但“排在第一”不等于“用户想去的那一家”。

如果客户端只取 `items.first`，会带来两个问题：

1. 用户无法区分同名分店，容易把饭帖关联到错误门店；
2. 接口明明返回了多条，界面只展示一条，用户会误以为“地图里只有这一家”。

现在的做法是把整个结果保存为列表 `_results`，底部面板用 `ListView` 展示每一条的名称、地址和距离：

- **默认不选中任何一条**，地图中心也不移动，避免替用户做决定；
- 点击某一条时更新 `_selected`，同时把地图中心移到该条坐标，选中项用边框和主题色高亮；
- 点“确认使用”时：点过某条就提交该条（带坐标），一条都没点就提交输入框里的名称（无坐标）；
- 列表高度设上限（键盘弹出时进一步压矮），多条结果在列表内滚动，不会把确认按钮顶出屏幕。

关键区别是“默认值”和“用户选择”：这里干脆不给默认值，把选择权完全交给用户。面试里被问到“接口返回多条数据前端怎么处理”时，不要只回答取第一条。

### 2.2 为什么搜索结果默认不选中任何一条

把结果显示成列表只解决了“结果太多选哪个”，还要解决“默认选谁”。

早期实现是搜索成功后自动选中第一条。问题在于：**“排在第一”只代表接口按距离或匹配度排序的结果，不代表用户想去的那一家**。一旦默认选中，用户什么都不点直接确认，就会把饭帖挂到一个自己没看过的门店上，店名、坐标、导航全部指向别家；用户也可能误以为自己已经选好了。

后来改成“列表下方再加一个都不对选项”，能解决问题，但页面多了一个按钮，而且用户仍然要先意识到“默认那一条不是我要的”。最终方案更简单：

1. **搜索结果默认不选中任何一条**，也不移动地图中心，选中状态只由用户点击产生；
2. 点“确认使用”时按有无选中分两种结果：`_selected != null` 提交该地点并带坐标；`_selected == null` 提交输入框里的名称，不保存坐标；
3. 列表标题写明“点击选中；不选则使用输入的名称”，让规则直接可见，不再需要额外按钮。

这里的关键概念是**显式选择与隐式默认**。需要用户确认的对象（门店、地址、支付方式）应该由用户显式选择；默认值适合用在“选错代价很低、且用户大概率接受”的场景，例如排序方式。门店选错会污染数据，所以不给默认值更安全。

手写名称没有坐标，所以发布页只回填名称或地址，`storeLocation` 留空，详情页也就没有地图与导航入口。这是有意的取舍：宁可少一个导航按钮，也不能把饭帖挂到错误的门店上。

### 3. 请求竞态：旧结果不能覆盖新结果

网络请求的返回顺序没有保证。用户先搜“KFC”，再快速改成“麦当劳”，可能“KFC”的响应反而更晚回来，把麦当劳的结果覆盖掉。

解决办法是给每次请求编号：

```dart
final seq = ++_searchSeq;
final items = await apiClient.searchPlaces(...);
if (seq != _searchSeq) return; // 不是最新请求，直接丢弃
```

只有编号等于当前最新编号的响应才允许更新页面。这是处理竞态最简单有效的方式，比“取消请求”更容易实现，也不依赖网络库是否支持取消。

### 4. 静态地图的尺寸与清晰度

手机屏幕尺寸用“逻辑像素”表示，实际物理像素还要乘以**设备像素比（Device Pixel Ratio，缩写 DPR）**。例如逻辑宽度 360、像素比 3，物理宽度就是 1080。

如果用逻辑尺寸去请求静态图，图片会被放大，看起来模糊。所以页面这样计算：

```dart
final mapWidth = (屏幕逻辑宽度 × 像素比).round().clamp(100, 1024);
```

腾讯静态地图接口限制宽高最大 1024，所以再截断到 1024。图片用 `BoxFit.cover` 铺满屏幕，超出部分裁掉，保证不变形。

### 5. 地图里没找到怎么办

搜索返回空列表时，页面提示“地图里没找到这个店铺，确认后将直接使用你输入的名称”。用户仍然可以点“确认使用”，返回结果里只有名称、没有坐标。

发布页拿到结果后：
- 外卖：把名称填进“店家名称”；
- 到店：优先填地址，没有地址就填名称；
- 有坐标才生成 `storeLocation`，没有坐标就不保存店铺坐标。

这样“地图服务挂了”或“小店在地图上没有收录”都不会阻塞发布，只是失去地图导航能力。

### 6. 搜索按钮与自动搜索共用一套逻辑

自动搜索（防抖）和手动搜索（点按钮 / 键盘搜索键）最终都调用同一个 `_search()`：

- 关键词为空 → 清空结果并返回；
- 请求中允许重复触发吗？页面用“搜索中”文案提示，但不强行禁用，因为防抖和手动可能同时触发；真正的保护是请求编号，旧响应会被丢弃。

## 九、定位如何变成饭帖的“大概位置”

改版前，用户需要手动打开“公开大概位置”开关，再填写位置描述；改版后这个模块删掉了。

现在的规则：

- 来源是“自己做” → 不带公开位置；
- 来源是“外卖 / 到店” → 自动把已解析的定位作为公开大概位置提交，`publicConsent` 固定为 `true`；
- 后端收到后统一把经纬度四舍五入到 3 位小数，再写入饭帖的 `coarse_lat`、`coarse_lng`。

为什么可以自动带：用户点击“外卖 / 到店”并使用地图选店，本身就是在使用位置服务，位置与内容强相关；公开的是百米级大概位置，不是精确坐标。首页“附近”依赖这个字段，如果完全取消，外卖和到店内容就无法出现在附近推荐里。

为什么仍然保留 `publicConsent` 字段：后端和历史客户端、历史数据都依赖这个字段判断“用户是否同意公开大概位置”。新客户端固定传 `true`，老数据保持原样，不需要改表。

隐私边界：
- `user_locations` 里的精确坐标只有本人登录后才能读取；
- 饭帖里的公开坐标已经降精度；
- 店铺坐标是商家公开信息，可以精确保存，用于导航。

## 十、发布页的实现要点

前端语法不是本部分重点，这里只说明与后端契约相关的部分。

### 1. 地图不可用时的降级

改版后，店名与地址统一通过“全屏静态地图页”选择，不再有单独的“搜索店铺”模块。地图不可用时仍然不阻塞发布：

- 静态地图图片加载失败时，地图区域显示“地图加载失败，可以直接输入店铺名称后确认”；
- 地点搜索返回 503 时，地图页提示“地图服务暂时不可用，可以直接确认使用输入的名称”；
- 用户点“确认使用”后，输入的店铺名称照样回填到发布页，只是不保存店铺坐标。

这样即使没有申请地图密钥，发布流程也能完整走通。

### 2. 静态地图作为普通图片

详情页直接把 `/maps/static?lat=...&lng=...` 当作图片地址使用。图片加载失败时隐藏地图，只保留文字地址和导航按钮，不影响页面其他内容。

### 3. 导航的方式

Flutter 使用 `url_launcher` 打开腾讯地图的统一资源标识符：

```text
https://apis.map.qq.com/uri/v1/marker?marker=coord:纬度,经度;title:店铺名称;addr:店铺地址&referer=mealmate
```

- `coord:` 后面是“纬度,经度”。注意顺序和日常说的“纬度、经度”一致，而高德是“经度在前、纬度在后”，切换供应商时这是最常见的错误来源。
- `title:` 和 `addr:` 分别是标记点名称和地址，腾讯要求必填，并且都要做网址编码；否则店名里的空格、斜杠、中文标点会破坏链接结构。
- `referer` 是腾讯要求必填的调用来源，填应用名称即可。

这个链接在手机上会优先唤起已安装的腾讯地图应用，没有安装时退回网页版地图。小程序端按项目规则已暂停开发，其原有 `uni.openLocation` 由运行环境决定使用哪个地图应用，不绑定具体供应商。

### 4. 草稿编辑页

草稿编辑页不能复用公开详情接口，因为公开详情只返回图片地址，不返回图片编号；而保存草稿需要图片编号才能在不换图的情况下继续保存。所以草稿有独立的详情接口，返回原始字段和与图片编号一一对应的图片地址。

### 5. 地图搜索为什么要求先开启定位

腾讯的地点搜索接口必须带“搜索范围”参数 `boundary`，只有 `nearby(纬度,经度,半径,是否自动扩大范围)` 和 `region(城市名, 是否自动扩大范围)` 两种写法，没有“全国”这种合法范围；用 `region(全国,0)` 兜底实测会返回“请求成功但零结果”，比报错更难排查。因此后端在缺少 `lat` 或 `lng` 时直接返回 400，错误码 `LOCATION_REQUIRED`，而发布页在点击“外卖 / 到店”时就会先完成定位，进入地图页时一定带着可用的中心点。完整的兜底顺序见第三部分第七节“定位兜底流程”，为什么不在服务端伪造默认坐标见第三部分问题二十二。

### 6. JSON 数字类型：`int` 还是 `double`

联调菜谱列表时，页面报错 `type 'double' is not a subtype of type 'int?'`，位置在数据模型的 `servings`（份数）字段。原因不在界面，而在“数字类型”的传递过程：

1. 数据库里 `servings` 列的类型是浮点数（`Float`），种子数据写的是 `1`；
2. PostgreSQL 的浮点列读出来会变成 Python 的 `1.0`，不是整数 `1`；
3. 序列化后 JSON 里是 `1.0`，而 JSON 规范只有一种数字类型，不区分整数和小数；
4. Dart 的 `json['servings'] as int?` 要求这个值必须是整数对象，遇到 `1.0` 就抛出类型错误。

修复方式是“先按数字接收，再按业务转换”：

```dart
servings: (json['servings'] as num?)?.toInt() ?? 1,
```

`num` 是 Dart 中 `int` 和 `double` 的共同父类型，`toInt()` 会把 `1.0` 转成 `1`。同一个菜谱对象里的 `totalMinutes`（总分钟数）也一起改成这种写法，避免以后数据库列类型变化时再次踩坑。

更一般的原则是：接口文档写“数字”时，客户端先按 `num` 解析，再按业务需要转换；只有确定后端一定返回整数时才可以直接 `as int`。这不是前端“多写一行”的问题，而是跨语言类型系统的边界问题：数据库类型、后端语言类型、JSON 类型、客户端类型是四层，任何一层变化都可能让强类型客户端崩溃。

### 7. 发布结果为什么用 Overlay 提示，而不是跳详情页

发布成功后的交互是：点击发布后页面立即返回上一页，同时屏幕上方（约屏幕高度 12% 的位置）淡入一个结果卡片（“发布成功”或“已提交审核”）；卡片停留约 0.9 秒后淡出并自动移除。提示和返回同时发生，不让用户等动画结束。

三个选择各有原因：

| 方案 | 位置/行为 | 是否选用 |
| --- | --- | --- |
| `SnackBar` | 固定在屏幕底部 | 不选，位置不符合“中心靠上方” |
| `showDialog` | 屏幕中央，但必须点按钮关闭 | 不选，发布会打断用户，还要多一次点击 |
| `OverlayEntry` | 可以任意定位，无遮罩、不阻塞操作 | 选用，显示固定时长后自动移除 |

实现上是先 `Overlay.of(context).insert(entry)`，然后立刻 `Navigator.pop()`：浮层挂在 Navigator 的 Overlay 上，不会随发布页一起销毁，所以能在上一页继续显示。卡片内部用 `AnimationController` 做 180 毫秒淡入、停留 900 毫秒、180 毫秒淡出，动画结束后回调移除 `OverlayEntry`；移除前判断 `entry.mounted`，避免用户在提示期间继续操作导致重复移除。卡片外面包 `IgnorePointer`，提示显示时不会挡住其他点击。

为什么发布后返回上一页，而不是自动进入详情页：

1. 用户刚点完发布，最可能的行为是继续逛或再发一条，强制跳详情会打断；
2. 详情页需要再发一次请求，网络慢时会出现“发布成功但详情打不开”的尴尬；
3. 返回上一页后，首页或我的发布列表刷新就能看到新内容，验证路径更短。

### 8. 作者做法的食材和步骤为什么用自由文本

产品上不再要求“每行一项”，食材和步骤各给一个多行输入框，用户想怎么写就怎么写。原因是普通用户不会为了发一条饭帖去理解“数组”“每行一项”这种程序概念，强制按行输入会增加负担，也容易产生空行和格式错误。

存储上仍然保持列表结构：提交时按换行拆分并去掉空项。用户写成一段话，列表里就是一条；用户自己分了行，就按行拆成多条。这样详情页可以按条目展示，也保留了以后做结构化编辑（例如给每条食材加数量）的空间。

边界在于后端只校验“食材和步骤必须成对出现、不能为空”，不校验行数。约束放在业务真正需要的粒度上，而不是为了前端控件好实现去限制用户。

### 9. 页面顶部为什么去掉大标题，晒饭按钮为什么和筛选按钮同排

四个主页面（首页、热榜、菜谱、我的）以及发布页、登录页等二级页面，顶部原本都有一行大标题，例如“今天吃啥”“今日热榜”“发布今天的饭”。这一轮统一去掉了标题文字，只保留需要的内容：

1. **标签栏已经说明了用户在哪**：四个主页面底部有导航栏，当前页签高亮；顶部再写一遍“今天吃啥”属于重复信息，还占掉手机屏幕最宝贵的第一屏高度。
2. **二级页面有返回按钮**：用户关心的是“怎么回去”，标题文字不是必需；发布页、登录页等二级页面顶部只保留返回按钮，功能和身份仍然可识别。
3. **组件层面统一处理**：`AppHeader` 的 `title` 改为可选，并且当标题、说明、返回按钮、右侧操作全部为空时返回 `SizedBox.shrink()`，页头不再占高度。这样各页面不用各写一套判断。

首页还多做了一步：原来“晒饭”是页头右侧的按钮，页头去掉后按钮没有地方放，于是把它移到“全部、附近”筛选按钮的同一行右侧。为了保证美观，需要三件事一致：

- **高度一致**：筛选按钮固定高 44，晒饭按钮也改成固定 `height: 44`，而不是“最小高度”；
- **圆角一致**：筛选按钮圆角 22（高度的一半，形成胶囊形），晒饭按钮也从 24 改成 22；
- **对齐方式**：用 `Row` + `Spacer` 把筛选放左边、晒饭推右边，不写死坐标，屏幕宽度变化时仍然贴边。

这类“同一行的控件怎么看起来像一组”的问题，本质是设计令牌（Design Token，指颜色、圆角、间距、字号这些可复用的设计变量）要统一：同一行里圆角和高度只要有一个不一致，视觉上就会觉得歪。

## 十一、数据库迁移

- 启动时用 SQLAlchemy 的 `Base.metadata.create_all` 只建不改：表不存在就建表，表已存在就跳过，不会给老表补字段，也不会改字段类型或索引。

- `create_all` 为什么不能替代迁移、Alembic / Flyway / Liquibase 等工具的对比，见第一部分《工程基础：数据库、存储与项目标识》第三节“数据库迁移”。

## 十二、安全、性能与降级

1. **密钥安全**：地图密钥只存在服务端环境变量中，客户端的网络请求里看不到。
2. **越权防护**：草稿编辑、草稿发布、删除都校验“作者必须是当前登录用户”，不属于自己的内容返回 404。
3. **定位接口鉴权**：只从登录令牌取账号，不接受客户端传用户编号，避免读取或覆盖别人的定位。
4. **输入校验**：标题、评价、价格、标签数量、标签是否在数据库字典中且已启用、坐标范围、图片归属全部在后端校验。
5. **配额保护**：地点搜索要求登录并限制返回数量；1 秒防抖减少请求次数；后端限制关键词长度；静态地图响应带 `Cache-Control: public, max-age=86400`，客户端图片缓存可直接复用，后续可在网关层加限流。
6. **超时与降级**：地图请求 6 秒超时，失败返回 502 或 503；图片加载失败、搜索返回 503 时，客户端仍允许用户直接确认手写名称，降级为手动填写地址。
7. **请求竞态**：请求编号丢弃过期响应，避免旧结果覆盖新结果。
8. **定位数据最小化**：每个账号只保留一条最新记录，不保存轨迹；公开位置降为 3 位小数。
9. **系统权限最小化**：只申请前台定位，不申请后台定位；先解释用途，再弹系统授权框。
10. **软删除与隐私**：删除后公开入口不可见；发布者位置只保留三位小数；店铺位置与发布者位置分开存储。
11. **后台过滤**：后台审核列表默认排除草稿和已删除内容，避免未完成内容和已删除内容占用审核视线。

## 十三、面试题

### 问题一：为什么地图密钥不能放在客户端？后端代理有什么代价？

**总结版**：客户端代码可以被解包、反编译或抓包，密钥放客户端必然泄露，可能被盗刷额度。后端代理可以隐藏密钥、统一限流缓存，但会增加一次网络转发、占用后端带宽，并形成单点故障，需要超时、缓存和降级来兜底。

**详细版**：

小程序代码包可以被工具解包，手机应用可以被反编译，浏览器更直接，打开网络面板就能看到请求参数。密钥一旦泄露，别人可以用你的账号调用地图接口，产生的费用和配额消耗由你承担。虽然后台可以配置域名白名单、签名校验等限制，但这些只能提高门槛，不能从根本上保护密钥。

把密钥放在后端后，客户端只调用自己的接口，第三方密钥不会出现在任何客户端代码或网络请求中。后端还能统一做登录校验、按用户限流、缓存热门查询、记录调用日志。

代理的代价是：多一次网络转发，延迟略微增加；静态地图图片经过后端会占用带宽；后端服务不可用时地图也不可用；所有用户共用同一个密钥额度。应对方式包括：设置超时、给图片加缓存、限制返回数量、准备降级方案（手动填写地址），以及在访问量增大时把静态地图改为由内容分发网络缓存。

---

### 问题二：地图软件开发工具包和 Web 服务接口有什么区别，什么时候选哪个？

**总结版**：软件开发工具包在客户端绘制可交互地图，功能完整但三端各接一次、密钥暴露；Web 服务接口由服务端返回地点数据或静态图片，接入简单、密钥可控，但不能拖动缩放。需要完整地图交互选工具包，只需要搜地点、看位置、导航选 Web 服务接口。

**详细版**：

地图软件开发工具包通常包含地图渲染引擎、手势处理、图层、标记、定位等能力，运行在客户端。优点是交互流畅、功能完整；缺点是需要分别适配小程序、安卓、苹果和网页，包体积增大，而且密钥必须下发到客户端。

Web 服务接口是普通的网络接口，输入关键词或坐标，返回地点列表、路径规划结果或一张静态图片。它不负责界面渲染，所以不能拖动和缩放，但接入成本极低：后端写一次，所有客户端共用。密钥可以只放在服务端，安全性更好。

选择标准：
- 需要用户自由拖动地图、点击标记、查看实时路况：选软件开发工具包；
- 只需要“搜索店铺、展示位置、点击导航”：选 Web 服务接口；
- 两者也可以混用：发布页用接口搜索地点，详情页用静态图片，真正导航时唤起系统地图。

### 问题三：地图接口的签名校验是怎么做的？为什么有了 Key 还要 Secret Key？

（本题与问题一相关联：问题一讲为什么密钥要放后端，本题讲放在后端之后如何进一步证明请求来源。）

**总结版**：Key 用来标识应用，会出现在请求地址里，泄露后别人就能盗刷额度；Secret Key 不参与网络传输，只用来计算签名。开启签名校验后，请求要把路径和排序后的参数拼上 Secret Key 做 MD5，得到 `sig` 一起发送。Secret Key 只放服务端，泄露后要立即重置。

**详细版**：

先区分两个概念：

- Key 是“身份标识”，相当于会员卡号，请求地址里必须带，方便服务端识别你属于哪个账号、扣哪份额度。
- Secret Key 是“证明你是持卡人的暗号”，相当于签名笔迹。它不随请求发送，只用来计算一个只有持卡人才能算出的结果。

如果只校验 Key，会有一个漏洞：Key 会出现在请求地址、日志、浏览器网络面板里，任何人拿到 Key 都能冒充你调用接口。签名校验要求调用方额外提交 `sig`，而 `sig` 必须用 Secret Key 才能算出来。攻击者只拿到 Key、没有 Secret Key，就算不出正确的 `sig`，请求会被拒绝。

腾讯的签名算法如下：

1. 取请求路径，例如 `/ws/place/v1/search`；
2. 把参数按参数名升序排列；
3. 用“参数名=原始值”并用 `&` 连接；
4. 拼成“路径?排序后的参数+Secret Key”，做 MD5，得到 32 位小写字符串。

实现时有四个关键点：

第一，`sig` 不能参与排序和计算。必须先算签名，再把 `sig` 加进参数，否则会无限递归。

第二，路径必须和真实请求完全一致。腾讯允许路径结尾带不带斜杠，但“签名时带、请求时不带”就会失败。本项目的静态地图路径是 `/ws/staticmap/v2/`，签名里也保留斜杠。

第三，计算签名时用未编码的原始值，发送请求时再让网络库做网址编码。中文、括号、逗号在 MD5 时保持原样，否则签名对不上。

第四，特殊字符 `#`、`%`、`&` 会破坏“参数名=值”的拼接结构。腾讯建议在端上过滤，本项目会先去掉搜索关键词里的这三个字符。

签名校验不是唯一方案。还可以用 IP 白名单（只允许固定服务器地址调用）或域名白名单（只允许指定网页调用）。IP 白名单更简单，但服务器换 IP 时要同步修改；签名校验更安全，但参数一变就要重新计算。真实项目里常见组合是：Secret Key 只放服务端、开启签名校验、再配合按用户限流和配额告警，形成多层防护。

最后要能看懂状态码：`110` 是来源未授权，`111` 是签名失败，`121` 是当天配额用完。这三种错误分别对应白名单、密钥配置和额度问题，不能混为一谈。本次实测就先后遇到了 `111` 和 `121`：前者说明签名没配对，后者说明签名已经对了、但账号配额不足。

### 问题四：为什么这个项目只接一家地图服务商？双地图的代价是什么？

（本题与问题一、问题二相关联：问题一讲为什么由后端代理，问题二讲为什么选 Web 服务接口，本题讲在代理层内部要不要接两家供应商。）

**总结版**：双地图要维护两套请求参数、响应解析、错误码、地点编号和配额监控，代码量和测试量翻倍，还容易出现同一家店重复、结果不一致的问题。个人项目的调用量远低于单家免费额度，双地图没有收益。后端代理已经把供应商隔离在服务层，将来真需要切换时只改一处，客户端不用发版。

**详细版**：

先明确“双地图”的两种常见形态：

1. **故障切换**：默认调用主供应商，失败或超时后再调用备用供应商。听起来可靠，但两家的搜索结果排序、距离精度、地点编号都不同，用户刷新一次可能看到不同的店，同一家店也可能因为编号不同被存成两条数据。
2. **双活请求**：同时请求两家，取最先返回的结果。这样调用量直接翻倍，免费额度消耗翻倍，而且仍然要处理两份结果不一致的问题。

无论哪种形态，都要付出这些成本：

- **协议适配成本**：腾讯用 `keyword`、`boundary=nearby(纬度,经度,...)`、`_distance`、`status=0`；高德用 `keywords`、`location=经度,纬度`、`distance`、`status="1"`。每个地图能力都要写两套参数拼装和两套响应解析。
- **数据一致性成本**：兴趣点编号是服务商内部的，换一家就对不上。数据库里的 `store_poi_id` 只能对应一家；如果两家混用，去重、重新拉取店铺信息都会失效。
- **测试与排查成本**：每个功能要准备两份模拟响应、两份错误码用例；线上出问题时还要先判断是哪家供应商、哪条链路出的问题。
- **配额与监控成本**：两份额度要分别监控、分别告警，商务上也要维护两份授权。
- **坐标成本**：国内几家使用的坐标系不完全相同，腾讯和高德都是 GCJ-02，百度是 BD-09。多接一家百度就多一层坐标转换，转换误差和遗漏都会导致位置偏移。

反过来看收益：腾讯个人开发者每个接口每天 1 万次调用，对一个还没上线的个人项目来说远远用不完；真正用超时，说明产品已经有真实规模，那时购买商业额度是更合理的做法，而不是长期维护两套代码。

更关键的是架构边界：本项目的客户端只依赖后端返回的 `name/address/lat/lng` 这套统一字段，供应商细节全部关在 `map_service.py` 里。将来如果真的要换供应商，只需要重写这个服务文件里的请求和解析，客户端、数据库字段、接口文档都不用改。**既然“未来可能换”的成本已经被隔离在一个文件里，就没有必要现在就为它付出双份维护成本。** 这就是常说的“避免过度设计”：不是不做扩展准备，而是用低成本的结构（代理层）保留扩展能力，而不是提前实现两套完整逻辑。

### 问题五：静态地图和动态地图有什么区别？为什么全屏选点仍然用静态地图？

**总结版**：动态地图可以拖动、缩放、点击，需要地图组件；静态地图是服务端生成的一张带标记的图片，接入简单、加载快、密钥可以只留在后端，但不能交互。只需要展示位置时用静态地图。全屏选点页要做的是“搜店 → 看位置 → 确认”，不需要自由拖动，所以仍然用静态图，并用“放大、缩小、回到当前位置”三个按钮和“搜索后自动居中”弥补不能拖动。

**详细版**：

动态地图由客户端地图引擎渲染，支持手势、图层、标记点击、实时路况等交互，功能完整但依赖地图组件和脚本，包体积和接入成本更高。

静态地图由服务端根据坐标、缩放级别、尺寸生成一张图片，客户端用普通图片标签显示。优点是没有脚本依赖、加载稳定、实现简单；缺点是缩放级别固定、不能拖动、标记样式受服务商限制、尺寸有上限。

本项目的详情页只需要让用户看到店铺大致位置，并提供导航按钮，所以静态地图足够。如果以后要做“地图找饭”“拖动查看附近饭帖”，就需要升级为动态地图。

原生地图软件开发工具包（SDK）能拖动、缩放、点标记，但需要分别接入两个平台，密钥必须放在客户端，还要配置包名和签名证书；网页视图方案要处理网页与原生通信，安全边界也更复杂。

静态地图是一张服务端生成的图片，客户端用普通图片组件显示。它的能力有限：不能手指平移，缩放级别要重新请求图片。但对“选店铺”这个任务来说，用户的核心动作是“输入店名 → 看地图确认位置 → 点确认”，不是自由探索地图。搜索命中后地图自动移动到店铺，用户还可以点按钮缩放或回到当前位置，已经够用。

这也是“按需求选技术”的例子：不是越强的地图能力越好，而是刚好满足需求、维护成本最低最好。

### 问题六：第三方服务不可用时，后端应该如何降级？

**总结版**：先设置超时，失败时返回明确的业务错误码，客户端根据错误码降级到备用流程；同时做好缓存、限流和监控，避免第三方故障拖垮整个系统。

**详细版**：

第三方服务随时可能超时、限流、返回错误或变更接口。后端不能无限等待，也不能把第三方错误原样抛给用户。

本项目的做法：
1. 给腾讯地图请求设置 6 秒超时；
2. 没有配置密钥时返回 503，错误码为 `MAP_NOT_CONFIGURED`，提示可以手动填写地址；
3. 腾讯返回错误或网络异常时返回 502，提示地图暂时不可用；
4. 客户端收到 503 后隐藏地图搜索，保留手动填写地址；
5. 静态地图响应加一天缓存，减少重复调用。

更完整的生产方案还包括：熔断（连续失败后暂时不再调用）、重试（只对幂等请求重试）、多供应商备份、异步补偿、监控告警和按用户限流。

### 问题七：人均价格为什么用整数？金额一般怎么存？

**总结版**：人均价格是估算值，整数元足够，避免小数精度问题。严肃的金额场景应该用“分”为单位的整数或高精度十进制类型，不能直接使用普通浮点数。

**详细版**：

计算机里的浮点数采用二进制表示，很多十进制小数无法精确表示，例如 `0.1` 在二进制里是无限循环小数。直接用它做加减乘除会出现 `0.1 + 0.2 != 0.3` 这样的误差。

常见处理方式：
1. **最小货币单位整数**：人民币用“分”，数据库存 `1999` 表示 19.99 元；计算全部用整数，展示时再除以 100。
2. **高精度十进制类型**：数据库提供 `DECIMAL` 或 `NUMERIC`，可以精确表示指定小数位；编程语言使用对应的十进制类型。
3. **普通浮点数**：只适合估算值、科学计算或对精度要求不高的场景。

本项目的人均价格是用户估算，精确到元即可，所以用整数元。如果以后要做订单金额、退款、分账，必须改成“分”为单位的整数或高精度十进制，并补充完整的金额校验与测试。

### 问题八：口味标签用 JSON 数组还是关联表？标签字典该放在哪、怎么校验？

**总结版**：饭帖“选了哪些标签”用 JSON 数组最简单；“有哪些合法标签、顺序、是否启用”应该放在独立的字典表 `taste_tags` 里，由 `GET /taste-tags` 下发。只做展示、标签数量少时不需要拆“饭帖—标签”关联表；需要按标签筛选、统计、改名或保证引用完整性时再拆。JSON 数组的缺点是难以高效索引、无法用外键约束、改名要批量更新。校验不能只放在发布入口，四个写入入口都要查库，未知或停用标签统一返回 422 和 `TASTE_TAG_INVALID`。

**详细版**：

JSON 数组把标签直接存在饭帖的一列里，例如 `["香辣", "咸鲜"]`。优点是读写简单，一次查询就能拿到全部标签，不需要关联表；适合标签数量少、结构稳定的场景。

标签的合法性则不能靠前端写死。本项目最初两端各写一份枚举，结果出现“前端能选正常、后端只认重口下饭”的不一致，发布直接 422。修复方式是加一张字典表 `taste_tags`（标签文字、排序、是否启用），由 `GET /taste-tags` 下发前端选项，后端在四个写入入口查库校验。这样合法标签只有一份数据源，运营调整标签也不用发版。

**字典表的结构与维护规则**

表结构：

```text
taste_tags
- name        标签文字，主键
- sort_order  展示顺序
- enabled     是否启用
- created_at  创建时间
```

初始数据就是旧前端展示的 9 个：清淡、正常、香辣、酸甜、咸鲜、油炸、烧烤、汤羹、面食。

为什么用标签文字直接做主键：饭帖里保存的也是标签文字（JSON 数组），文字做主键可以让两边直接对应，查询时不用再关联。代价是改标签文字要同步改历史数据；口味标签基本不改名，可以接受。

为什么用“停用”而不是删除：历史饭帖可能还引用这个标签，直接删行会让历史内容出现“查不到的标签”。停用后新内容不能选，历史内容照常展示。

为什么只下发启用中的标签：停用的标签不该再出现在新发布的内容里；历史详情仍然按饭帖里保存的文字展示，不受影响。

**四个写入校验点**

口味标签的校验放在服务层函数 `validate_taste_tags` 里，被四个入口调用：

1. `POST /posts` 直接发布；
2. `POST /posts/drafts` 新建草稿；
3. `PUT /posts/{id}/draft` 更新草稿；
4. `POST /posts/{id}/publish` 草稿发布。

只在一个入口校验是不够的：客户端可以绕过发布页，直接调草稿接口写入非法标签。四个入口共用同一个函数，规则只有一份，新增入口时也不容易漏。

为什么先校验标签再校验图片：标签校验只是一次轻量查库，图片校验要查多张图片的归属和状态；参数本身不合法时尽早失败，避免无意义的重查询。

关联表通常设计成“标签表”和“饭帖标签关联表”。优点是：
- 可以给标签建索引，按标签筛选效率高；
- 可以统计每个标签的使用次数；
- 标签改名只需要改标签表一处；
- 可以用外键保证饭帖只能引用存在的标签。

缺点是每次读取都要关联查询，写入也要维护关联表，代码更复杂。

选择标准：
- 只要展示，不按标签筛选：JSON 数组；
- 需要筛选、统计、排序、改名：关联表；
- 数据量很大且查询复杂：关联表加索引，甚至使用专门的搜索系统。

本项目当前只需要展示和简单筛选，因此采用“字典表 + 饭帖 JSON 数组”；如果以后要做“按口味找饭帖”、统计每个标签的使用次数，再迁移到“饭帖—标签”关联表。

### 问题九：软删除和物理删除有什么区别？软删除有哪些坑？

**总结版**：物理删除真正删掉数据，软删除只改状态并记录删除时间。软删除能保留审计和关联数据，但会让表越来越大、唯一约束仍然生效、所有查询都必须记得排除已删除数据。删除后重新创建同唯一键的记录时尤其容易出问题。

**详细版**：

物理删除执行 `DELETE`，数据消失，无法恢复；如果有其他表引用它，可能报外键错误或产生悬空引用。软删除只把状态改成“已删除”并写入删除时间，数据仍在，可以恢复和审计。

软删除的优点：
- 保留历史，满足内容安全和审计要求；
- 不会破坏点赞、收藏、审核记录等关联；
- 统计口径稳定；
- 可以实现“最近删除”恢复。

软删除的坑：
1. **唯一约束仍然生效**：已删除记录仍占用唯一键，重新创建相同键会冲突。可以用“部分唯一索引”只约束未删除记录，或在业务层生成新的键。
2. **查询容易漏过滤**：每个公开查询都要记得排除已删除状态，漏一处就会泄露内容。最好封装统一的查询条件。
3. **表会持续变大**：需要定期归档或清理真正不再需要的数据。
4. **关联数据的处理**：饭帖删除后，点赞和收藏是否还显示？本项目的收藏列表会检查目标状态，已删除内容标记为不可用。
5. **隐私合规**：如果法规要求真正删除个人信息，软删除可能不够，需要额外的匿名化或物理清理流程。

### 问题十：如何设计草稿功能？草稿和发布如何共用校验？

**总结版**：草稿允许内容不完整，使用宽松的请求模型；发布使用严格的请求模型，必须重新校验全部字段。两者共用同一套字段赋值逻辑，避免字段丢失。草稿与正式内容放在同一张表，用状态区分，公开查询必须排除草稿。

**详细版**：

草稿的核心矛盾是“保存时宽松、发布时严格”。如果草稿也要求完整，用户就没法先存一半；如果发布直接信任草稿，用户就可能绕过校验发布不完整或不合法的内容。

本项目的做法：
1. 草稿请求模型只限制字段长度和格式，标题、评价、图片、来源都可以为空；
2. 发布请求模型要求标题、评价、至少一张图片，并校验外卖店名、到店地址；
3. 发布草稿时，客户端提交完整的发布内容，后端用发布请求模型重新校验；
4. 草稿和发布共用同一个字段赋值函数，保证人均价格、口味标签、店铺坐标等新字段不会只在一个入口生效；
5. 草稿与正式内容共用一张表，通过状态区分，公开列表只查已发布状态。

这样设计的好处是：逻辑集中、字段不漂移、草稿不能绕过审核，并且以后新增字段只需改一处赋值逻辑。

### 问题十一：幂等键是什么？为什么草稿不需要幂等键？

**总结版**：幂等键让同一个提交重复执行也只产生一次结果，常用于防止用户连点或网络重试造成重复发布。草稿本身可编辑、不进入公开列表，重复保存不会造成公开内容重复，所以不需要幂等键。

**详细版**：

用户点击发布后，如果网络超时，客户端不知道服务端有没有成功，可能会重试。如果没有幂等控制，重试会创建两条相同的饭帖。

幂等键的做法是：客户端为一次提交生成唯一键，放在请求头里；服务端记录“这个用户 + 这个键”已经处理过，再次收到就直接返回第一次的结果。数据库通常用唯一约束兜底，防止并发时两条请求同时通过检查。

草稿不需要幂等键，因为：
- 草稿是私人内容，不进入公开列表；
- 重复保存只会产生多条草稿或覆盖同一条草稿，不会造成公开内容重复；
- 用户可以在草稿箱里看到并删除多余草稿。

草稿发布也不需要幂等键：发布成功后状态变成已发布，重复请求会得到“这不是草稿”的错误，不会重复创建内容。

### 问题十二：为什么删除别人的内容返回 404 而不是 403？

**总结版**：403 表示资源存在但无权访问，404 表示资源不存在。返回 404 可以避免攻击者通过状态码判断资源是否存在，降低枚举风险。如果产品明确需要告知“这是别人的内容”，也可以返回 403。

**详细版**：

假设删除接口对别人的饭帖返回 403，攻击者可以不断尝试不同的编号：返回 403 说明这个编号存在，返回 404 说明不存在。这样就能枚举出系统里有哪些内容。

返回 404 时，攻击者无法区分“编号不存在”和“编号存在但不属于我”，枚举成本更高。

这不是绝对安全，只是降低信息泄露。真正防止越权还要靠后端校验作者身份，前端隐藏按钮只能改善体验，不能作为安全措施。

### 问题十三：系统定位服务和 App 定位权限有什么区别？为什么两个都要检查？

**总结版**：系统定位服务是整台手机的总开关，关了所有应用都拿不到位置；App 定位权限只控制当前应用。只查权限会漏掉“系统开关关闭”的情况，只查系统开关会漏掉“应用被拒绝”的情况，所以两个都要查。

**详细版**：

安卓和苹果都把定位拆成两层。系统层是全局开关，用户可以在下拉快捷开关或设置里关闭；应用层是每个应用单独的授权，首次使用时系统弹窗询问。

代码里如果只调用“申请权限”，在系统定位关闭时可能仍然返回“已授权”，但取位置会失败或一直等待。反过来，系统开关开着但用户拒绝了应用权限，申请权限会直接返回拒绝。

本项目的检查顺序是：先 `isLocationServiceEnabled()` 判断总开关，再 `checkPermission()` 判断应用权限，最后才 `getCurrentPosition()`。任何一步不满足就返回“没有当前定位”，交给历史定位兜底。这样错误原因清晰，也不会让用户在一个永远失败的请求上等待。

---

### 问题十四：用户没开定位时，如何设计兜底？历史定位为什么放后端？

**总结版**：优先级是“当前定位 → 后端历史定位 → 提示开启”。历史定位放后端是因为换设备、重装应用后仍然可用，且接口鉴权后只有本人能读；只存一条最新记录，不存轨迹，符合数据最小化。

**详细版**：

只依赖手机本地缓存的问题是：换手机、重装应用、清理缓存都会丢失，同一个账号在平板和手机上也不共享。放在后端后，只要用户登录，任何设备都能拿到上一次成功定位。

表设计成“账号编号做主键”，一个账号只有一条记录，保存就是覆盖。业务上只需要“最近一次在哪”，保存轨迹既没有使用场景，又会放大隐私风险，所以不存历史流水。

读取接口只从登录令牌取账号，客户端不能传别人的账号编号，因此不存在越权读取。定位精度保留 6 位小数，但这个数据只在本人接口里返回，不进入公开内容；公开到饭帖的坐标由后端统一降到 3 位小数。

### 问题十五：为什么不能一进页面就弹系统定位授权框？

**总结版**：用户还没理解为什么要位置，突然弹框容易被拒绝；一旦拒绝，后续申请更麻烦。正确做法是先静默检查已有权限，没有权限时先用自己的弹框解释用途，用户同意后再申请系统权限或跳设置。

**详细版**：

系统授权框是有限资源：安卓和苹果都会记录用户的选择，多次拒绝后可能变成“不再询问”，应用再也弹不出授权框，只能让用户去设置里手动打开。

所以本项目把“检查”和“申请”分开：
- 页面点击“外卖 / 到店”时只做静默检查，不弹系统框；
- 没有权限就尝试历史定位；
- 历史定位也没有，才弹自己的说明框：“外卖和到店需要用当前位置查找附近店铺”；
- 用户点“去开启”后，系统定位关闭就跳系统设置，权限被永久拒绝就跳应用设置，普通拒绝才再次申请。

这样系统授权框只在用户明确知情并同意后出现，授权成功率更高，也符合“先解释、再申请”的隐私设计原则。

### 问题十六：什么是防抖？为什么地图搜索用 1 秒防抖？防抖和节流有什么区别？

**总结版**：防抖是“连续触发结束后只执行一次”。搜索框每输入一个字都请求会浪费配额、增加卡顿，1 秒防抖让用户停手后才搜一次；点搜索按钮则立即执行。节流是固定时间内最多执行一次，适合滚动加载等持续触发场景。

**详细版**：

用户输入“麦当劳”会触发三次输入事件。如果每次输入都请求地点搜索，就是三次网络请求、三次地图配额消耗，而且前两次的结果还没用就过期了。

防抖的实现是“每次事件都取消旧计时器、重新计时”：1 秒内没有新输入才真正执行。用户输入很快时，中间请求全部被取消，只发最后一次。

防抖和节流的区别：
- 防抖关注“结束”：连续触发结束后执行一次；
- 节流关注“频率”：无论触发多密集，固定时间内最多执行一次。

搜索框适合防抖，因为用户的目标是“输入完成后搜一次”；页面滚动加载适合节流，因为滚动过程中需要持续触发。选错会导致体验问题：搜索用节流会在用户还没输完时就发请求，滚动用防抖会在停止滚动前什么都不加载。

### 问题十七：多个搜索请求同时返回，如何避免旧结果覆盖新结果？

**总结版**：给每次请求编号，响应回来时只有编号等于当前最新编号才更新页面，过期响应直接丢弃。这比取消请求简单，也不依赖网络库支持取消。

**详细版**：

网络请求的返回顺序不等于发出顺序。用户先搜“KFC”再搜“麦当劳”，KFC 的响应可能更晚回来；如果不做处理，页面会先显示麦当劳，再被 KFC 覆盖，用户看到的结果和输入框不一致。

本项目用一个自增编号 `_searchSeq`：每次发起请求先自增并记下当前值，`await` 返回后比较编号。不相等说明期间又发起了新请求，这次结果已经过期，直接 `return`，不调用 `setState`。

另一种方案是“取消请求”（例如使用支持取消的 HTTP 客户端），但 Flutter 常用的 `http` 包取消支持有限，而且取消后仍要处理异常。编号方案不依赖具体网络库，代码量更少，适用面更广。

### 问题十八：定位是敏感信息，接口和存储如何保护？

**总结版**：精确位置只存本人一条，接口只按登录身份读写；公开到饭帖的位置由后端降到 3 位小数；只申请前台定位权限；不保存轨迹。核心原则是“最小必要、最小保存、最小暴露”。

**详细版**：

具体措施：

1. **接口鉴权**：`GET /me/location` 和 `PUT /me/location` 都要求登录，账号从令牌解析，客户端不能指定用户编号。
2. **只存一条**：一个账号一条最新记录，不保存历史轨迹，减少泄露后的影响面。
3. **精度分级**：本人接口返回 6 位小数；饭帖公开位置四舍五入到 3 位小数（约百米级）。
4. **权限最小化**：只申请前台定位，不申请后台定位；先解释用途再弹系统授权框。
5. **公开与私密分离**：精确位置在 `user_locations`，公开位置在饭帖的 `coarse_lat/coarse_lng`，两者用途和精度不同。
6. **传输安全**：生产环境必须使用 HTTPS，避免定位在传输过程中被截获。

更严格的合规场景还需要：隐私政策明确告知、提供关闭定位的入口、支持删除定位数据、日志脱敏、按法规做数据留存期限管理。

### 问题十九：为什么“大概位置”要由后端降精度？3 位小数大概是多少米？

**总结版**：客户端传来的坐标可能被篡改或误传，精度处理必须放在可信的后端；3 位小数的纬度精度约 100 米，既能支持“附近”推荐，又不会暴露具体楼栋。

**详细版**：

纬度 1 度约 111 公里，所以：
- 1 位小数约 11 公里；
- 2 位小数约 1.1 公里；
- 3 位小数约 111 米；
- 6 位小数约 0.11 米。

经度在不同纬度上的实际距离不同，赤道附近与纬度类似，高纬度会缩短，但数量级相同。

降精度放在后端的原因：
1. 客户端可以被修改，不能信任它“已经模糊处理”；
2. 历史客户端可能仍然上传高精度坐标，后端统一处理才能保证所有数据一致；
3. 以后调整精度策略只改后端，不需要发客户端新版本。

本项目在序列化前把公开位置四舍五入到 3 位小数，精确位置只存在本人可见的定位表里，两者用途不同、精度不同。

### 问题二十：保存定位为什么用 PUT 而不是 POST？

**总结版**：PUT 表示“把资源整体替换成请求体的值”，同一账号重复提交结果相同，天然幂等；POST 通常表示新建，重复提交可能产生多条记录。定位每个账号只有一条，适合 PUT。

**详细版**：

HTTP 方法的语义：
- `GET`：读取，不改变数据；
- `POST`：新建资源，或者执行一个非幂等操作；
- `PUT`：用请求体整体替换目标资源，重复执行结果相同；
- `PATCH`：只修改请求体里出现的字段。

本项目的定位资源地址可以理解为“`/me/location` 这个资源”，每个账号只有一份。客户端每次提交完整经纬度，服务端有记录就覆盖、没有就创建，重复提交不会多出一条。这正好符合 PUT 的语义，也让客户端在网络超时后可以放心重试。

如果未来要保存“定位历史流水”，每次都是新建一条，就应该用 POST，并且要考虑分页查询和清理策略。

### 问题二十一：删掉“公开大概位置”开关后，如何保证首页“附近”仍然可用？

**总结版**：外卖和到店发布时自动把已解析的定位作为公开大概位置提交，后端降精度后写入饭帖；自己做的内容不带位置。这样用户少一步操作，“附近”仍然有数据，隐私也仍然由后端统一保护。

**详细版**：

旧流程要求用户手动打开“公开大概位置”并填写区域描述。问题是大部分用户不会主动打开，导致外卖和到店内容没有坐标，首页“附近”筛不出内容。

新流程把定位和来源绑定：
- 点击“外卖 / 到店”必须先拿到定位（当前或历史），否则不能切换来源；
- 发布时客户端把这份定位作为 `location` 提交，`publicConsent` 固定为 `true`；
- 后端统一降到 3 位小数后写入饭帖的大概位置；
- 来源是“自己做”时不提交位置，首页“附近”不会出现它。

这样“附近”始终有可用数据，同时公开的只是百米级位置，不是精确坐标。`publicConsent` 字段保留是为了兼容历史数据和老客户端，新客户端固定传 `true`。

### 问题二十二：为什么地图搜索必须带定位？腾讯的“全国搜索”有什么问题？

（本题与问题三、问题四相关联：问题四讲为什么只接一家供应商，问题三讲密钥与签名，本题讲这家供应商的搜索范围限制如何影响接口设计。）

**总结版**：腾讯地点搜索必须给出搜索范围，要么是某个坐标附近，要么是某个城市，没有“全国”这个合法范围。用 `region(全国,0)` 会返回“成功但零结果”，很难排查。所以后端要求客户端必须带经纬度，缺少时返回 400 和明确的业务错误码，让客户端引导用户开启定位。

**详细版**：

腾讯地点搜索的 `boundary`（搜索范围）只有两种形态：

- `nearby(纬度,经度,半径,是否自动扩大)`：以坐标为中心搜索；
- `region(城市名, 是否自动扩大)`：在城市范围内搜索。

它没有“不限范围”的写法。最初为了兼容“用户没开定位”的情况，后端尝试用 `region(全国,0)` 兜底，结果接口返回 `status = 0`、`count = 0`。`status = 0` 在腾讯的约定里表示“请求成功”，所以这不是报错，而是“成功但没有任何结果”。这类响应会让排查方向完全跑偏：日志里看不到错误，前端只看到空列表，很容易误判成关键词不对或网络问题。

最终的处理是：

1. 后端把 `lat`、`lng` 改为搜索的必需参数，缺少时返回 400，错误码 `LOCATION_REQUIRED`；
2. 前端在点击“外卖 / 到店”时先静默检查手机定位：已开启就取当前位置并保存为最新定位；没有就读取后端历史定位；两者都没有才弹框引导开启。这样进入地图页时一定有坐标，省掉无效请求；
3. 有坐标时使用 `nearby(纬度,经度,1000,1)`，按距离排序，返回用户附近的店。

为什么不用其他方案兜底？

- **让用户选城市**：需要额外的城市选择器和城市列表数据，交互更重，而且“我附近的店”本来就和城市无关；
- **用网络地址反查城市**：服务端看到的可能是代理或机房的地址，定位不准，还涉及隐私；
- **用发布者资料里的常住城市**：资料可能没填，也可能和用户当前位置不一致。

这几个方案都比“直接用当前定位”更复杂，收益也更低。接口设计上要记住一点：**当第三方接口缺少某个必需参数时，应该尽早失败并给出可识别的业务错误码，而不是构造一个看似合法的假参数去调用。** 否则错误会被第三方“成功但为空”的响应吞掉。

### 问题二十三：后端返回的 JSON 数字，客户端为什么不能直接 `as int`？

（本题与问题七相关联：问题七讲金额为什么用整数存储，本题讲数字类型在数据库、后端、JSON、客户端之间传递时会发生什么变化。）

**总结版**：JSON 只有一种数字类型，不区分整数和小数；数据库的浮点列读出来是 `1.0` 这样的浮点数。Dart 是强类型语言，`as int?` 遇到 `1.0` 会直接抛类型错误。正确做法是按 `num` 接收，再按业务需要调用 `toInt()` 或 `toDouble()`。

**详细版**：

这次联调菜谱列表时出现的报错是：

```text
type 'double' is not a subtype of type 'int?'
```

触发点是份数字段 `servings`。完整链路是：

1. 数据库列 `servings` 的类型是 `Float`（浮点数），种子数据虽然写的是 `1`，但浮点列读出来是 `1.0`；
2. Python 的 `1.0` 序列化成 JSON 后仍然是 `1.0`；
3. JSON 规范里数字只有一种类型，没有 `int` 和 `double` 之分，具体是整数还是小数由各语言自己判断；
4. Dart 解析时，`1.0` 是 `double`，`as int?` 要求它是 `int`，于是抛出类型错误。

修复方式：

```dart
servings: (json['servings'] as num?)?.toInt() ?? 1,
totalMinutes: (json['totalMinutes'] as num?)?.toInt() ?? 0,
```

`num` 是 `int` 和 `double` 的公共父类型，`(json[...] as num?)` 表示“允许为空，非空时只要是数字就行”，`toInt()` 负责把 `1.0` 变成 `1`，空值再用 `??` 给默认值。

为什么不直接把后端改成返回整数？因为份数在业务上允许小数（例如 1.5 人份），数据库列本来就是浮点；为了迁就客户端而强行取整会丢数据。退一步说，即使这次把后端改成整数，下次别的浮点字段仍会踩同一个坑，问题应该修在“客户端如何解析数字”这一层。

更普遍的原则：

- 接口契约写“数字”时，客户端用 `num` 解析，再按业务转换；
- 只有契约明确写“整数”且后端类型可以保证时才用 `as int`；
- 金额不要依赖客户端取整，应该由后端用“分”为单位的整数或高精度十进制返回；
- 类型错误要在开发联调阶段暴露，不要靠线上崩溃日志才发现。

### 问题二十四：地图搜索为什么要展示候选列表，而不是只取第一条？

**总结版**：地点搜索返回的是兴趣点列表，连锁店同名分店很常见。只取第一条会让用户选到错误门店，也让其他结果“看不见”。正确做法是把接口返回的候选按顺序展示，并且默认不选中任何一条：用户点哪条就选中哪条，确认时提交选中的地点；一条都没点，就提交输入框里的名称，不保存坐标。

**详细版**：

地图接口返回的是“兴趣点（Point of Interest，缩写 POI，指地图上的餐厅、商场、车站等具体地点）”列表，而不是唯一答案。搜索“肯德基”时，附近可能有三家分店，名称相同、地址不同；接口按距离、匹配度等规则排序返回，但排序第一不等于用户想去的那一家。

客户端原来的写法是 `items.first`，只把第一条渲染成一张卡片。这会带来两个问题：

1. 用户无法区分同名分店，容易把饭帖关联到错误门店；
2. 接口明明返回了 10 条，界面只展示 1 条，用户会误以为“地图里只有这一家”。

改法是把整个结果保存为列表 `_results`，底部面板用 `ListView` 展示每一条的名称、地址和距离：

- 搜索结果出来后默认不选中任何一条，地图中心也不移动，避免替用户做决定；
- 点击某一条时更新 `_selected`，同时把地图中心移到该条坐标，选中项用边框和主题色高亮；
- 点“确认使用”时按有无选中分两种结果：点过某条就提交该地点并带坐标；一条都没点就提交输入框里的名称，不保存坐标；
- 列表高度设上限（键盘弹出时进一步压矮），多条结果在列表内滚动，不会把确认按钮顶出屏幕。

这个改动本质上是在处理“显式选择与隐式默认”：需要用户确认的对象（门店、地址、支付方式）应由用户显式选择，默认值只适合“选错代价很低、用户大概率接受”的场景。门店选错会污染数据，所以不给默认值更安全。面试里被追问“接口返回多条数据前端怎么处理”时，不要只回答取第一条。详细说明见第三部分第十节第 2.1、2.2 小节。

### 问题二十五：页面顶部的大标题为什么可以去掉？同一行的按钮怎么保证视觉一致？

**总结版**：主页面底部导航已经标明当前位置，顶部再写一遍标题属于重复信息，还占用第一屏高度；二级页面靠返回按钮就能让用户知道怎么回去，标题不是必需。组件层面把标题参数改为可选，没有标题、说明、返回按钮和操作时页头直接不占高度。同一行放主操作和筛选按钮时，高度、圆角、对齐方式必须用同一套值，否则视觉上会歪。

**详细版**：

先说大标题。手机屏幕高度有限，第一屏要尽量留给内容。四个主页面底部有标签栏，“首页、热榜、菜谱、我的”文字就在屏幕上，而且当前页签高亮，用户已经知道自己在哪里；顶部再显示一遍“今天吃啥”“今日热榜”既重复又浪费空间。删除后，首页第一行直接是筛选和晒饭，热榜第一行直接是“今日点赞 TOP20”，内容出现得更早。二级页面（发布页、登录页、我的发布、收藏）顶部只保留返回按钮：返回按钮负责导航，页面身份由内容本身表达。连说明性副标题也一并去掉，是因为它们和标题一样属于“顶部文案”，在内容型页面里优先级低于内容本身；只有详情页的副标题例外，那里显示的是发布时间、试做人数这类数据，不是宣传语。

实现上没有在每个页面写一遍“删掉标题”，而是改公共组件 `AppHeader`：

1. `title` 从必填改成可选；
2. 渲染时先判断标题、说明、返回按钮、右侧操作是否都存在，全部为空就返回 `SizedBox.shrink()`，页头完全不占高度；
3. 说明文字的顶部间距根据有没有标题动态调整，避免标题删掉后文字位置下坠。

再说同一行按钮。页头去掉后，“晒饭”按钮失去位置，被移到“全部、附近”筛选的同一行右侧。同一行里要让不同用途的按钮看起来像一组，必须统一三件事：

- **高度**：筛选按钮固定 44 逻辑像素，晒饭按钮也从“最小高度 44”改成固定高度 44。最小高度在内容变化时可能被撑高，固定高度才能保证严格对齐。
- **圆角**：筛选按钮圆角 22（高度的一半，形成胶囊形），晒饭按钮原来的 24 改成 22。
- **对齐方式**：用 `Row` 加 `Spacer`，筛选靠左、晒饭靠右，不写死左右坐标；屏幕变宽变窄时两端仍然贴边。

这类值在工程上叫设计令牌（Design Token），指颜色、圆角、间距、字号这些可以复用的设计变量。面试里如果没有实际经验，可以这样回答：同一行的控件要么共用同一组令牌，要么由同一个基础组件生成，否则换一个人改一个值，视觉就不一致了。

详细说明见第三部分第十节第 9 小节。

## 二、知识点

### 1. 什么是测试用例

测试用例是“为了验证某个功能是否符合预期，而提前写好的一组操作步骤和判断标准”。

一条可执行的用例通常包含：

| 要素 | 作用 | 本项目示例 |
| --- | --- | --- |
| 编号 | 稳定引用，方便回归和缺陷关联 | `A-PUB-006` |
| 优先级 | 决定每次回归先测什么 | `P0` |
| 前置条件 | 执行前必须满足的状态 | 已登录、后端已启动 |
| 操作步骤 | 具体做什么 | 不填菜名直接点发布 |
| 预期结果 | 怎么判断通过 | 提示“给这顿饭起个名字” |

为什么要有预期结果：没有预期结果，就只能靠“感觉没问题”，无法判断回归是否真的通过。

### 2. 等价类划分

等价类划分是把大量输入分成若干组，每组挑一个代表值测试，因为同一组内的输入对程序来说行为相近。

以手机号为例：

| 类别 | 示例 | 预期 |
| --- | --- | --- |
| 有效等价类 | `13800138000` | 允许发送验证码 |
| 无效等价类：长度不足 | `1380013800` | 提示手机号错误 |
| 无效等价类：长度超出 | `138001380001` | 输入被截断或提示错误 |
| 无效等价类：开头不对 | `23800138000` | 提示手机号错误 |
| 无效等价类：含字母 | `1380013800a` | 输入框只允许数字，无法输入 |

好处：不用把每一种手机号都测一遍，也能覆盖主要风险。

### 3. 边界值分析

程序最容易出错的地方通常在边界，而不是中间值。边界值分析就是专门测试“最小值、最大值、最小值减一、最大值加一”。

本项目的实际边界：

| 字段 | 规则 | 需要测试的值 |
| --- | --- | --- |
| 菜名 | 1 至 24 字 | 0、1、24、25 |
| 评价 | 1 至 200 字 | 0、1、200、201 |
| 图片 | 1 至 9 张 | 0、1、9、10 |
| 人均价格 | 0 至 9999 元 | -1、0、9999、10000 |
| 口味标签 | 最多 3 个 | 3、4 |
| 图片大小 | 不超过 5 兆字节 | 5 兆字节、5 兆字节加 1 字节 |
| 图片边长 | 至少 200 像素 | 199、200 |

面试时能说出“为什么测 0、1、24、25”，比只背定义更有说服力。

### 4. 场景法

场景法是把用户完成一个目标的完整路径写出来，再补分支和异常。

以“发布饭帖”为例：

1. 主流程：登录 → 上传图片 → 填写菜名和评价 → 选择来源 → 发布成功提示 → 返回上一页 → 首页可见。
2. 分支流程：先存草稿 → 退出 → 从草稿箱继续编辑 → 发布。
3. 异常流程：图片超过 5 兆字节、菜名为空、外卖没填店家、地图不可用、网络中断、重复点击发布。

主流程保证“能用”，分支和异常保证“不容易坏”。

### 5. 优先级与回归测试

- P0：主流程和安全问题。坏了就不能上线。
- P1：主要异常分支、权限、边界、空状态。
- P2：展示细节和极端参数。

回归测试是“改完代码后，把以前能用的关键功能再测一遍”。本项目的第 7 节列出了每次迭代必须执行的最小回归清单。

为什么不能每次都全量执行：用例会越来越多，全量执行成本高；用 P0 清单保证主流程，再按改动模块追加 P1，是成本和风险的平衡。

### 6. 测试金字塔

测试金字塔把测试分成三层：

1. 单元测试：直接测一个函数或一个类，速度快、定位准，但离真实用户远。
2. 接口测试：直接调用后端接口，验证参数、权限、状态变化。速度快、稳定性好，是后端的主要测试层。
3. 界面测试：启动真实 App 或浏览器，验证用户看到和操作的东西。最接近用户，但慢、容易受环境影响。

常见比例是“大量单元测试、适量接口测试、少量界面测试”。本项目当前以接口测试和关键界面流程为主，因为个人项目没有足够成本维护大量单元测试。

### 7. 接口测试是什么

接口测试是不经过界面，直接向服务器发请求，检查响应是否符合约定。

需要关注：

| 关注点 | 例子 |
| --- | --- |
| 状态码 | 成功 200，参数错误 422，未登录 401，无权限 403，不存在 404 |
| 业务错误码 | 响应体里的 `code`，例如 `CODE_INVALID` |
| 响应结构 | 是否包含 `requestId`、`code`、`message`、`data` |
| 数据变化 | 发布后数据库是否真的多了一条 |
| 权限 | 不带令牌、带别人的令牌、带低权限管理员令牌 |
| 边界 | 标题 24 字和 25 字 |
| 幂等 | 同一个请求重复发送是否只产生一条数据 |

为什么业务错误码不能只看状态码：很多业务错误都返回 200 或 400，真正的原因在 `code` 里；客户端需要根据 `code` 显示不同提示。

### 8. 幂等

幂等是指“同一个操作执行一次和执行多次，最终结果一样”。典型场景是用户点了发布，网络慢，以为没成功又点了一次；没有幂等就会产生两条一样的饭帖。

本项目的做法：

1. 客户端生成一个 `Idempotency-Key`（幂等键），每次提交带同一个键。
2. 后端先查“这个用户 + 这个键”是否已经有非草稿、非删除的饭帖。
3. 如果有，直接返回第一次的结果，不再新建。

完整设计见第三部分《地图、定位与发布》的幂等键章节，后台审核幂等见第二部分《管理后台与角色权限》的知识点 7。

### 9. 权限测试

权限要分两层看：

1. 前端隐藏按钮：只是让界面更干净，不能当作安全措施，因为用户可以绕过界面直接调接口。
2. 后端校验权限：才是真正的安全边界。

本项目的例子：

- 只有 `post.review` 权限的管理员能看到“通过/拒绝”，但“下架”需要 `post.unpublish`。
- 普通用户不能编辑别人的草稿；后端统一返回 404，而不是 403。

### 10. 为什么“别人的资源”返回 404 而不是 403

401 表示没有登录，403 表示知道你是谁但明确没有权限，404 表示资源不存在。如果访问别人的草稿返回 403，攻击者就能根据“403 还是 404”推断这个编号确实存在，从而逐个枚举内容；统一返回 404 可以隐藏资源是否存在，这叫“不泄露信息”。

完整论证见第三部分《地图、定位与发布》的 404 章节。

### 11. 软删除怎么测

软删除是不真的删数据库记录，而是把状态改成 `deleted` 并记录删除时间，目的是保留关联数据与追溯证据。定义与取舍见第三部分《地图、定位与发布》的软删除章节。

需要验证：

1. 删除接口返回 `status=deleted` 和 `deletedAt`。
2. 首页、热榜、详情、我的发布都不再出现该内容。
3. 重复删除返回 404，不能把删除时间覆盖。
4. 点赞、收藏、审核记录仍然保留，不产生悬空引用。
5. 收藏列表里显示“收藏内容暂不可用”，而不是崩溃。

### 12. 测试数据与环境隔离

测试最怕“上一次测试留下的数据影响这一次”。本项目的约定：

1. 写操作用独立测试账号，避免污染演示账号。
2. AI 配额按设备和自然日累计，测额度前清理当天记录或换设备标识。
3. 测“待审核”时把 `AUTO_PUBLISH_POSTS` 改为 `false` 并重启后端；测“直接发布”时改回 `true`。
4. 图片上传准备固定样本：合格图片、超大图片、过小图片、假图片、空文件。

### 13. AI 功能怎么测

AI 功能比普通接口多了“不确定性”，测试重点是：

1. 供应商模式：本项目 `AI_PROVIDER=mock`，使用本地规则推荐器，结果可重复；切换成真实模型后要重新设计评测。
2. 配额：游客 5 次、登录 20 次，用完后返回 429。
3. 约束：时间、器具、食材、忌口是否真的参与筛选。
4. 来源：推荐必须来自已发布菜谱，不能编造不存在的菜谱。
5. 降级：没有完全匹配时，是否明确提示“放宽条件”，而不是假装满足。
6. 关联上下文：从饭帖进入 AI 时，是否引用当前饭帖；草稿和已删除内容不能被引用。

### 14. 已知缺陷怎么管理

已知缺陷不能从用例里删掉，否则下次执行会误以为功能正常。

正确做法：

1. 用例仍写“正确的预期结果”。
2. 在“已知问题”里写“当前实际结果”。
3. 在缺陷记录里关联用例编号。
4. 修复后执行关联用例，并更新缺陷状态。

本项目的 BUG-001 就是这样处理的：用例要求“选择正常/香辣应发布成功”，同时注明当前返回 422。

## 三、面试题

### 问题一：如何为一个项目设计一套测试用例？

**总结版本**：先列功能清单，再按主流程、分支、异常拆场景；用等价类和边界值补数据；给用例标优先级；最后形成可重复执行的回归清单。

**详细版本**：

1. 先盘点功能：用户能做什么，管理员能做什么，系统自动做什么。
2. 每个功能写一条主流程用例，保证“能用”。
3. 补分支：未登录、空数据、重复操作、权限不足。
4. 补异常：网络失败、第三方服务不可用、文件格式错误、参数越界。
5. 用等价类减少重复输入，用边界值覆盖最容易出错的点。
6. 标优先级：主流程和安全问题为最高优先级。
7. 形成回归清单：每次改代码至少跑最高优先级用例。
8. 持续维护：功能改了就用例改，功能删了就用例删。

本项目的实际做法是把三个端放在同一个文件里，用编号区分模块，避免用例散落。

### 问题二：等价类划分和边界值分析有什么区别？

**总结版本**：等价类划分是“分组选代表”，边界值是“专门测边缘”。两者通常一起用。

**详细版本**：

等价类划分关注“输入的种类”。例如菜名长度，可以分为有效（1 至 24 字）和无效（0 字、25 字以上）。每一类挑一个代表值即可。

边界值分析关注“边缘上的具体值”。因为程序经常在 `0`、`1`、最大值、最大值加一这些位置写错判断。例如菜名要测 0、1、24、25，而不是只测中间的 10 个字。

只做等价类，可能漏掉“24 和 25 的差一错误”；只做边界值，可能漏掉“完全不同的无效输入类型”。两者结合才完整。

### 问题三：为什么这个项目只维护一个测试用例文件？

**总结版本**：单人项目更需要“单一事实来源”。一个文件不容易出现版本不一致，搜索和回归都方便。

**详细版本**：

多个文件的好处是团队并行编辑冲突少；坏处是容易出现“这个模块改了，另一个文件没改”的漂移。

本项目是个人面试项目，模块数量有限，一个人维护。用一个文件可以：

1. 全局搜索用例编号，快速定位影响范围。
2. 每次迭代只改一个文件，减少遗漏。
3. 用固定编号建立“用例、缺陷、回归清单”的关联。

代价是文件会变长。控制方法是：稳定的编号规则、清晰的分节、只保留有价值的用例，删除过期用例。

### 问题四：接口测试和界面测试有什么区别？为什么先做接口测试？

**总结版本**：接口测试直接验证服务器逻辑，快且稳定；界面测试验证用户看到的效果，慢但接近真实体验。通常先做接口测试，再做关键界面流程。

**详细版本**：

接口测试不启动 App，直接发请求，能快速覆盖参数校验、权限、状态变化、分页、幂等。它不受手机型号、屏幕尺寸、动画时机影响，失败时也容易定位是后端问题。

界面测试要启动真实设备，验证按钮是否能点、提示是否出现、页面是否滚动、图片是否加载。它能发现接口测试发现不了的问题，例如按钮被遮挡、登录后没有继续原操作。

本项目的策略是：后端逻辑用接口用例覆盖；用户主流程用 App 用例覆盖；不追求每个按钮都写自动化。

### 问题五：什么是幂等？怎么测试幂等？

**总结版本**：幂等是同一操作重复执行，结果不变。测试方法是同一个幂等键提交两次，检查只产生一条数据、返回同一个编号。

**详细版本**：

幂等与幂等键的定义、以及本项目发布接口为什么用 `Idempotency-Key` 去重，见第三部分《地图、定位与发布》的幂等键章节；这里只讲测试视角。

测试要点：

1. 同一个键连续提交两次，第二次返回第一次的 `postId`。
2. 数据库里只有一条记录。
3. 不同用户用同一个键，不能互相影响。
4. 删除后用同一个键重新发布，应该创建新内容，不能返回已删除的旧内容。
5. 并发提交时，最终也只能有一条；这通常需要数据库唯一索引兜底。

### 问题六：为什么删除别人的内容返回 404 而不是 403？

**总结版本**：404 不暴露资源是否存在，能防止别人枚举编号；403 等于告诉对方“这个编号是真的，只是你没权限”。

**详细版本**：

401、403、404 的语义，以及为什么用 404 隐藏资源是否存在，见第三部分《地图、定位与发布》的 404 章节；这里只讲测试视角。

测试时关注：

1. 用另一个账号的令牌调用编辑、删除、查看草稿接口，确认返回 404，而不是 403 或 500。
2. 用一个不存在的编号调用同样的接口，返回的状态码和响应体要与上一条一致，不能让人区分“不存在”和“存在但无权访问”。
3. 服务端日志里要能查到真实原因（是无权限还是不存在），但响应体不能把原因带出来。

### 问题七：软删除怎么测试？

**总结版本**：验证状态变为已删除、所有公开入口不可见、重复删除返回 404、关联数据仍然保留。

**详细版本**：

软删除的定义和为什么不用物理删除，见第三部分《地图、定位与发布》的软删除章节；这里只讲测试视角。

测试要覆盖：

1. 删除接口返回删除状态和删除时间。
2. 首页、热榜、详情、我的发布都不再展示。
3. 作者自己也不能再编辑或再次删除。
4. 点赞、收藏、审核记录仍然能关联到这条记录，不能出现悬空引用。
5. 收藏列表对失效内容显示友好提示。
6. 数据库里记录还在，方便内容安全追溯。

### 问题八：权限测试为什么要前后端都测？

**总结版本**：前端隐藏按钮只是体验，后端校验才是安全。测试必须绕过界面直接调接口，验证后端真的拒绝。

**详细版本**：

前端权限的作用是“不让用户困惑”，例如没有下架权限就不显示下架按钮。但前端代码可以被修改，请求也可以被工具直接发送，所以后端必须独立校验。

测试方法：

1. 用低权限账号登录，确认菜单和按钮正确隐藏。
2. 直接用低权限令牌调用高权限接口，确认返回无权限错误。
3. 用普通用户令牌调用管理员接口，确认被拒绝。
4. 用别人的资源编号调用编辑、删除接口，确认返回 404。
5. 检查审计日志是否记录操作人和原因。

本项目管理后台的权限点包括 `post.review`、`post.unpublish`、`user.read`、`user.ban`、`audit.read`，菜单只负责展示，接口逐个校验。

### 问题九：测试金字塔是什么？个人项目怎么落地？

**总结版本**：底层多写单元测试，中层写接口测试，顶层少写界面测试。个人项目优先保证接口测试和关键界面流程。

**详细版本**：

金字塔的意义是提醒我们：越往上，测试越慢、越脆弱、维护成本越高。

- 单元测试：毫秒级，适合纯函数、校验逻辑、计算逻辑。
- 接口测试：秒级，适合权限、状态流转、分页、幂等。
- 界面测试：十秒到分钟级，适合登录、发布、审核这类主流程。

个人项目时间有限，可以先做：

1. 后端关键接口的自动化测试。
2. 一份手动的界面回归清单。
3. 对最核心的流程（登录、发布、审核）做端到端验证。

不要为了追求“测试多”而写大量脆弱的界面脚本，最后没人维护。

### 问题十：AI 功能怎么测试？

**总结版本**：固定供应商和规则，重点测配额、约束筛选、来源真实性、无匹配时的降级提示，以及上下文引用是否正确。

**详细版本**：

AI 的输出天然不确定，所以测试要分层：

1. 确定性层：配额、参数校验、权限、错误码，这些和普通接口一样测。
2. 规则层：本项目使用本地推荐器，可以断言“推荐必须来自已发布菜谱”“时间、器具、食材约束是否生效”。
3. 安全层：不能引用草稿、已删除内容；不能编造不存在的菜谱；不能把平台参考说成作者原创。
4. 体验层：没有完全匹配时，是否明确说“放宽条件”，而不是假装满足。
5. 降级层：供应商不可用时返回明确错误，客户端展示可理解的提示。

如果接入真实大模型，还需要准备评测集，用人工评分或规则评分检查回答质量，而不能只断言一段固定文本。
