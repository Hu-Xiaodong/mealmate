### 3. 切片规则：标题分节、段落累积、重叠、上下文头

本项目的切片器分四步：

**第一步：按标题分节。** 识别 Markdown 的一到六级标题（以 `#` 开头）。遇到标题就结束上一节、开始新一节，并用一个“标题栈”记录层级路径。例如：

```
# 番茄指南
## 选购
### 颜色
```

“颜色”这一节的路径是“番茄指南 / 选购 / 颜色”。为什么要路径：片段被单独取出来后，只写“颜色”不知道是谁的颜色。

**第二步：节内按空行分段。** 连续的非空行算一个段落；空行是段落分隔。段落是比句子更自然的语义单位，尽量不拆散。

**第三步：累积到目标长度。** 一段一段往缓冲区里加，达到目标长度后，如果再加下一段会超过上限，就先输出当前片段。本项目目标 400 字、上限 800 字。目标不是硬性下限：如果一节本身只有 100 字，就输出 100 字，不会为了凑数把别的节拼进来。

**第四步：保留重叠。** 输出当前片段后，把它的最后 80 个字带到下一片的开头。这样跨片的一句话至少有一片能看全。

另外还有两个细节：

- **超长段落强制切分**：如果单个段落就超过 800 字，会优先按句号、问号、感叹号、分号切开；找不到标点才按固定长度硬切，保证不会出现超长片段导致嵌入失败。
- **上下文头**：每片正文前加一行 `【番茄指南｜番茄指南 / 选购 / 颜色】`。它既参与向量化，也参与展示；标题路径太长时只保留最后两级，避免头部本身占用太多长度。

**为什么用字符数而不是 token 数**：token 是模型切分文本的单位，中文一个字通常约一个 token，英文一个单词约一到两个 token。精确 token 数需要加载具体模型的分词器，换模型就要换算法。用字符数是近似值，简单稳定，误差可以通过调整切片长度吸收。本项目另有一个粗略的 token 估算函数，只用于展示，不参与计费。
### 3.1 切片执行全流程：从入口到返回值（零基础）

> 本节与前面的“### 3. 切片规则”直接相连：第 3 节讲规则，本节讲代码里先调用哪个函数、每个函数具体怎么做、数据在每一步变成什么形状。读完的目标是：不看代码，也能按顺序把整条链路复述出来。

#### 3.1.1 总结版：一句话和一张表

一句话：`split_document` 是总调度。它先纠正参数，再调用 `_split_sections` 按 Markdown 标题分节；每节内部按空行拆成段落，交给 `_pack_paragraphs` 装箱；装箱时如果遇到超长段落，会先调用 `_split_long_paragraph` 按句子切开；装完后用 `_context_header` 给每片加“文档标题｜章节路径”，用 `estimate_tokens` 估算词元数，最后组装成 `TextChunk` 列表返回。

词元（token）是模型处理文字时的最小单位，可以粗略理解成“模型眼里的一个字或一个词”。本节提到“词元估算”，只是为了给每个切片记一个大小，不参与计费。

| 顺序 | 函数 | 作用 | 输入 → 输出 |
| --- | --- | --- | --- |
| 0 | `kb_service._split_text` | 上游入口：上传或重新切片时调用切片器 | 文档正文、标题、索引版本参数 → 调用 `split_document` |
| 1 | `split_document` | 总调度：纠正参数，按顺序调用下面的函数 | 正文 + 三个长度参数 → `TextChunk` 列表 |
| 2 | `_split_sections` | 按 Markdown 标题分节，记录标题路径 | 整篇正文 → 若干“节” |
| 3 | `re.split`（标准库） | 节内按空行拆段落 | 一节正文 → 段落列表 |
| 4 | `_pack_paragraphs` | 把段落累积成片段，处理目标长度与重叠 | 段落列表 → 片段文本列表 |
| 4.1 | `_split_long_paragraph` | 第 4 步内部调用：只处理超过上限的段落，按句子切开 | 一个超长段落 → 多个短段落 |
| 5 | `_context_header` | 生成每个片段开头的“文档标题｜章节路径” | 文档标题 + 标题路径 → 一行上下文头 |
| 6 | `estimate_tokens` | 粗略估算词元数 | 片段文本 → 整数 |
| 7 | `TextChunk` | 把正文、词元数、定位信息装成一个对象 | 各字段 → 切片对象 |

#### 3.1.4 第 0 步：谁调用切片器，参数从哪来

调用点在知识库服务 `kb_service._split_text`（上传和重新切片共用）：

```python
chunks = split_document(
    text_content,
    title=doc.title,
    target_chars=version.chunk_size,
    max_chars=version.chunk_size * 2,
    overlap_chars=version.chunk_overlap,
)
```

四个参数的含义：

| 参数 | 来源 | 作用 |
| --- | --- | --- |
| `text_content` | 数据库里保存的文档正文 | 要切的原始文本 |
| `title` | 文档标题 | 写进每个切片的上下文头 |
| `target_chars` | 启用中的索引版本的 `chunk_size` | 达到这个长度就可以考虑换片 |
| `max_chars` | `chunk_size * 2` | 绝对不能超过的上限，超过必须换片 |
| `overlap_chars` | 索引版本的 `chunk_overlap` | 相邻切片共享多少字 |

为什么切片器不自己去查数据库：切片器被设计成“纯函数”。纯函数的意思是：相同的输入一定得到相同的输出，函数内部不连数据库、不发网络请求、不修改外部状态。好处是单元测试只需要给一段文字，不用准备数据库；以后换存储、换框架，切片逻辑都不用改。

调用前，`_chunk_document` 已经把文档状态改成 `chunking`（切片中）；切片完成后改成 `chunked`（待建立索引），并把切片写入切片列表。这是为了让运营在后台看到文档卡在哪一步，也方便先检查切片质量。只有运营点“建立索引”后，才进入 `indexing`（生成向量中）。

#### 3.1.5 第 1 步：参数纠偏（`split_document` 开头）

代码先做三件事：

1. 如果 `max_chars <= 0`，直接抛出错误。因为“最大长度”是硬性上限，为零或负数没有意义。
2. 如果 `target_chars <= 0` 或 `target_chars > max_chars`，把目标长度改成 `min(400, max_chars)`。目标长度必须小于等于上限，否则“达到目标再换片”就永远不会发生。
3. 如果 `overlap_chars < 0`，改成 0。负数重叠没有意义；等于 0 表示不要重叠。

这一步不产生任何切片，只是保证后面的逻辑拿到一组合理的参数。面试时可以把它概括为“先做参数防御，避免脏参数把后面的装箱逻辑带偏”。

#### 3.1.6 第 2 步：`_split_sections` 按标题分节

输入是整篇正文，输出是一个列表，列表里每个元素是一节，包含四个字段：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `heading` | 最近一级标题的文字 | `冷冻保存` |
| `heading_path` | 从一级标题到当前标题的完整路径 | `番茄保存 / 冷冻保存` |
| `section_index` | 这是第几节，从 0 开始 | `1` |
| `body` | 这一节标题下面的正文 | 两段冷冻说明 |

函数内部按下面的顺序执行：

1. **统一换行符。** 把 Windows 的 `\r\n`、旧 Mac 的 `\r` 都换成 `\n`，再按 `\n` 切成一行一行。这样后面只需要处理一种换行符。
2. **准备状态变量。** `sections` 存结果；`stack` 是标题栈；`buffer` 是正文缓冲区；`current_heading` 和 `current_path` 记录当前标题与路径；`section_index` 记录节号。
3. **逐行扫描。** 每一行先用正则表达式判断是不是 Markdown 标题。正则表达式可以理解为“用一套符号描述一类字符串”的工具；这里的规则是“行首一到六个井号，后面至少一个空格，再后面是标题文字”。
4. **普通正文行**：直接塞进 `buffer`，继续看下一行。
5. **遇到标题行**：先调用内部函数 `flush()`，把上一节正文收成一条记录；然后清空 `buffer`；再维护标题栈；最后更新当前标题和路径。
6. **扫描结束后再调用一次 `flush()`。** 因为文档最后一段正文后面没有新标题来触发收节，不补这一次就会漏掉最后一节。

标题栈是“后进先出”的容器，像一摞盘子：最后放上去的标题在最上面。遇到新标题时，先把所有“层级大于等于新标题”的旧标题弹出去，再把新标题压进去。这样栈里剩下的永远是当前标题的上级链条。

用例子走一遍：

| 读到的行 | 动作 | 栈（层级, 标题） | 当前路径 |
| --- | --- | --- | --- |
| `# 番茄保存` | 遇到一级标题，前面没有正文，`flush()` 不产生节；压栈 | `(1, 番茄保存)` | `番茄保存` |
| 两行正文 | 放进 `buffer` | 不变 | 不变 |
| `## 冷冻保存` | 先 `flush()` 收下第 0 节；再压栈 | `(1, 番茄保存)`, `(2, 冷冻保存)` | `番茄保存 / 冷冻保存` |
| 后面四行正文 | 放进 `buffer` | 不变 | 不变 |
| 文档结束 | 再 `flush()` 收下第 1 节 | 不变 | 不变 |

得到的节列表：

| 节号 | `heading` | `heading_path` | `body` |
| --- | --- | --- | --- |
| 0 | 番茄保存 | 番茄保存 | 番茄常温可以放三到五天。冷藏可以延长到一周左右。 |
| 1 | 冷冻保存 | 番茄保存 / 冷冻保存 | 第一段冷冻说明 + 空行 + 第二段冷冻说明 |

`flush()` 里有一个细节：如果 `buffer` 拼起来是空字符串，就直接返回，不生成空节。比如文档一开头就是标题，或者两个标题紧挨着，都不会产生“没有正文的节”。

`flush()` 里还有 `nonlocal section_index`。`section_index` 定义在外层函数，`flush()` 是内层函数；Python 规定内层函数要修改外层变量时必须用 `nonlocal` 声明，否则会被当成新建一个局部变量。

边界情况：

- 文档没有任何标题：整篇正文会成为一节，`heading` 和 `heading_path` 都是空字符串。
- 标题层级跳跃，例如一级标题后直接出现三级标题：栈里只有实际存在的层级，路径就是“一级 / 三级”，不会自动补出二级。
- 代码块里以 `#` 开头的行也会被当成标题。这是当前实现的一个已知限制；如果以后要支持代码块，需要先识别并跳过代码围栏。

#### 3.1.7 第 3 步：节内按空行拆段落

拿到每一节的 `body` 后，用 `re.split(r"\n\s*\n", body)` 拆段落：

- `\n` 是换行；
- `\s*` 表示中间可以有任意多个空白字符（空格、制表符等）；
- 整体意思是“一个换行、若干空白、再一个换行”，也就是“空行”。

为什么按空行而不是按单个换行：Markdown 里单个换行常常只是同一段落的软换行，空行才表示“另起一段”。段落是比句子更自然的语义单位，尽量不拆散。

拆完以后，每一段都去掉首尾空白，并过滤掉空字符串。例子中第 1 节会得到两个段落：

```text
段落 A：冷冻前先去蒂，再切成块状。装入密封袋后尽量排出空气，然后放进冷冻室。
段落 B：冷冻番茄适合做汤、炖菜和炒蛋，不适合直接生吃，因为解冻后口感会变软。
```

#### 3.1.8 第 4 步：`_pack_paragraphs` 把段落装成片段

这是整个切片器最核心的一步。它维护一个“缓冲区” `buffer`，按顺序把段落往里加，直到该换片为止。

三个参数的分工：

- `target_chars` 是“可以考虑换片”的目标长度，不是必须达到的下限。如果一节只有 100 字，就输出 100 字，不会为了凑数去别的节拿内容。
- `max_chars` 是“必须换片”的硬性上限。合并后会超过它，就先把当前缓冲区输出。
- `overlap_chars` 是相邻片段共享的字数，用来避免跨片句子两边都检索不到。

对每个段落，先调用 `_split_long_paragraph(paragraph, max_chars)`，保证拿到的每一段都不超过上限；然后按三种情况处理：

| 分支 | 条件 | 动作 | 目的 |
| --- | --- | --- | --- |
| 分支一 | 当前缓冲区已经达到目标长度，且再合并会超过上限 | 输出当前缓冲区；取它最后 `overlap_chars` 个字，加上新段落，作为下一片的开头；如果这样仍超上限，再硬切一次 | 正常换片，并保留重叠 |
| 分支二 | 当前缓冲区还没到目标长度，但再合并会超过上限 | 输出当前缓冲区；同样用“末尾重叠 + 新段落”作为下一片开头 | 防止短缓冲区把新段落撑爆 |
| 分支三 | 合并后没有超过上限 | 把新段落接进缓冲区，继续累积 | 尽量让一个片段包含多个完整段落 |

用例子手算第 1 节：

| 轮次 | 当前缓冲区 | 缓冲区长度 | 读到的段落 | 合并后长度 | 命中分支 | 动作 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 空 | 0 | A（34 字） | — | 初始化 | `buffer = A` |
| 2 | A | 34 | B（34 字） | 34 + 2 + 34 = 70 | 分支一（34 ≥ 30 且 70 > 60） | 输出 A；新 `buffer` = A 的最后 8 字 + 空行 + B = 8 + 2 + 34 = 44 |
| 结束 | 44 字的新缓冲区 | 44 | 没有更多段落 | — | — | 输出这个缓冲区 |

第 0 节只有一个 24 字的段落，长度小于 30，也不会超过 60，所以直接输出 24 字。

最终这一节得到两个片段：

```text
片段 1：冷冻前先去蒂，再切成块状。装入密封袋后尽量排出空气，然后放进冷冻室。
片段 2：然后放进冷冻室。

冷冻番茄适合做汤、炖菜和炒蛋，不适合直接生吃，因为解冻后口感会变软。
```

片段 2 开头的“然后放进冷冻室。”就是片段 1 的最后 8 个字。重叠的代价是同一段文字存了两遍，检索时可能两片都命中；收益是跨片句子至少有一片能看全。80 字大约占目标长度 400 字的 20%，这是常见的折中范围。

#### 3.1.9 第 4.1 步：`_split_long_paragraph` 处理超长段落

这个函数只在“单个段落本身就超过 `max_chars`”时才会真正切分；如果段落没超长，它直接返回原段落，几乎不产生额外开销。

思路是：按句末标点把段落切成一句一句，再把句子往缓冲区里装；装不下就先输出当前缓冲。句末标点包括中文的句号、问号、感叹号、分号，也包括英文的对应符号和换行。

例子，设 `max_chars = 10`，段落是“清洗番茄。切成小块！装入袋子。”：

| 轮次 | 读到的句子 | 读之前缓冲区 | 加上后长度 | 是否超过 10 | 动作 |
| --- | --- | --- | --- | --- | --- |
| 1 | 清洗番茄。 | 空 | 5 | 否 | 缓冲区变成这句话 |
| 2 | 切成小块！ | 5 字 | 10 | 否（10 不大于 10） | 接进缓冲区 |
| 3 | 装入袋子。 | 10 字 | 15 | 是 | 输出前两句（10 字），缓冲区换成第三句（5 字） |
| 结束 | — | 5 字 | — | — | 输出第三句 |

结果是两个片段：“清洗番茄。切成小块！”和“装入袋子。”，都没有超过 10 字，而且是在句子边界切开的。

如果一整段里连一个句末标点都没有，比如 22 个字中间没有标点，`max_chars = 10`，就会退化为“按固定长度硬切”：先切 10 个字，再切 10 个字，最后剩 2 个字。这是最后一道保险，保证不会把超长文本直接塞给嵌入模型。

为什么优先按句子切：句子是能独立表达意思的最小单位。从句子中间切开，前后两片都可能读不懂；从句子边界切开，至少每一片内部是完整的。

#### 3.1.10 第 5 步：`_context_header` 生成上下文头

切片脱离原文后，只看到“颜色”两个字，不知道是谁的颜色。上下文头就是给每个片段补上“你是谁、你来自哪一节”。

函数接收两个值：文档标题 `title` 和这一节的标题路径 `heading_path`，然后：

1. 把两者拼成一个列表，空值丢掉；
2. 如果某一部分内部含有 `" / "`（说明它是标题路径），只保留最后两级；
3. 每个部分最多保留 60 个字；
4. 用中文竖线 `｜` 连接，外面套上 `【】`，最后加一个换行。

例子：

```text
title = 番茄指南
heading_path = 番茄保存 / 冷冻保存
结果 = 【番茄指南｜番茄保存 / 冷冻保存】
```

如果路径是“A / B / C”，只保留“B / C”，因为离正文最近的两级信息量最大。如果标题和路径都为空，就返回空字符串，片段不加头。

为什么上下文头要短：它会和正文一起送去生成向量，也会占用嵌入模型的输入长度。保留两级、每部分最多 60 字，是在“信息足够”和“别浪费长度”之间取平衡。

#### 3.1.11 第 6 步：组装 `TextChunk`，顺便估算词元数

每一节的所有片段共用同一个上下文头。对每个片段执行：

```python
content = f"{header}{piece}".strip()
```

然后调用 `estimate_tokens(content)` 估算词元数，最后创建 `TextChunk`：

| 字段 | 值 | 后续用途 |
| --- | --- | --- |
| `content` | 上下文头 + 片段正文 | 生成向量、后台预览、检索结果展示 |
| `token_count` | 粗略估算的词元数 | 统计切片大小，不参与计费 |
| `metadata.heading` | 最近一级标题 | 记录来源 |
| `metadata.headingPath` | 完整标题路径 | 记录来源 |
| `metadata.sectionIndex` | 节号 | 记录来源 |

`estimate_tokens` 的规则很简单：一个汉字算一个，一段连续的英文字母或数字算一个；标点符号不计数。用前面的切片 1 举例：

```text
【番茄指南｜番茄保存】
番茄常温可以放三到五天。冷藏可以延长到一周左右。
```

汉字一共 30 个（上下文头 8 个，正文 22 个），没有英文单词，所以估算结果是 30。真实分词器可能得到 32 到 35 之间的数字，因为标点也可能被算作词元。这个差异可以接受，因为这个数字只用于展示，不用于计费或长度控制。

`metadata` 的键名用 `headingPath`、`sectionIndex` 这种“驼峰写法”，是因为它最终会存成 JSON 文本，前端读取时可以直接用同名字段；切片正文本身用的是蛇形命名之外的普通字符串，不受影响。

#### 3.1.12 第 7 步：返回之后发生了什么

`split_document` 返回 `TextChunk` 列表后，`kb_service._save_drafts` 先把切片写入 `kb_draft_chunks`（切片列表），文档状态改成 `chunked`（待建立索引）。这一步不调用嵌入模型。

运营点“建立索引”后，`kb_service._build_index` 继续做三件事：

1. 把文档状态改成 `indexing`（生成向量中）；
2. 调用 `embedding_service.embed_texts`，把所有 `content` 按每批 32 条交给嵌入模型，得到与切片一一对应的向量；
3. 删除这篇文档的旧切片，再调用 `_insert_chunks` 写入新切片：正文、词元数、定位信息、向量一起进 `kb_chunks` 表；最后删除待索引切片。

最后文档状态改成 `ready`，并写一条审计日志。到这里，一篇文档才真正变成“可以被检索的知识”。

#### 3.1.13 完整数据变化一览

| 阶段 | 数据形状 | 用例子表示 |
| --- | --- | --- |
| 原始输入 | 一整段字符串 | 例子中的 Markdown 全文 |
| `_split_sections` 之后 | 2 个“节” | 第 0 节“番茄保存”，第 1 节“冷冻保存” |
| 节内拆段之后 | 每节一个段落列表 | 第 0 节 1 段；第 1 节 2 段 |
| `_pack_paragraphs` 之后 | 每节一个片段文本列表 | 第 0 节 1 片；第 1 节 2 片 |
| 加头、估算之后 | 3 个 `TextChunk` | 最终结果中的切片 1、2、3 |
| 写成待索引切片后 | 3 条无向量的数据库记录 | `kb_draft_chunks` 表 3 行，文档状态 `chunked` |
| 建立索引之后 | 3 条带向量的数据库记录 | `kb_chunks` 表 3 行，待索引切片删除，文档状态 `ready` |

#### 3.1.14 面试复述稿

**30 秒版（适合自我介绍后的一笔带过）**

> 切片的入口是 `split_document`。它先把目标长度、最大长度、重叠三个参数纠偏，然后调用 `_split_sections` 按 Markdown 标题分节，用标题栈记录章节路径；每节内部按空行拆段落，再交给 `_pack_paragraphs` 装箱。装箱时达到目标长度且再加会超上限，就输出当前片段，并把末尾一段作为下一片的开头形成重叠；单个段落超过上限时，先由 `_split_long_paragraph` 按句末标点切开。最后 `_context_header` 给每片加上文档标题和章节路径，`estimate_tokens` 估算词元数，组装成 `TextChunk` 列表返回，交给知识库服务写入切片列表；运营确认后再建立索引、生成向量。

**2 分钟版（适合面试官说“详细讲讲”时）**

1. **入口和参数**：上游是 `kb_service._split_text`，它把正文、文档标题、索引版本里的切片长度、两倍上限、重叠长度传给 `split_document`。切片器是纯函数，不碰数据库和网络。
2. **参数纠偏**：最大长度必须大于 0；目标长度必须落在 0 到最大长度之间，否则回退到默认值；重叠不能为负。
3. **按标题分节**：`_split_sections` 逐行扫描，遇到 Markdown 标题就用标题栈维护路径。比如一级标题“番茄保存”下面有一个二级标题“冷冻保存”，路径就是“番茄保存 / 冷冻保存”。遇到标题先收上一节，文档结束再补收最后一节。
4. **节内拆段**：用空行把每一节拆成段落。单个换行不算分段，空行才算，这是 Markdown 的段落规则。
5. **装箱**：`_pack_paragraphs` 维护一个缓冲区，把段落一段段加进去。达到目标长度并且再加会超过上限，就输出当前片段；输出时取末尾若干字作为下一片的开头，形成重叠。如果还没到目标长度但合并会超上限，也先输出；否则继续累积。
6. **超长段落**：装箱前每个段落都会先过 `_split_long_paragraph`。没超长就原样返回；超长就按句号、问号、感叹号、分号切开；连标点都没有才按固定长度硬切。
7. **收尾**：`_context_header` 生成“【文档标题｜章节路径】”，路径只保留最后两级、每部分最多 60 字；`estimate_tokens` 按“一个汉字一个、一个英文词一个”估算词元数；最后把内容、词元数、标题、路径、节号装进 `TextChunk` 返回。
8. **返回之后**：知识库服务把内容批量交给嵌入模型生成向量，删除旧切片，写入新切片，文档状态从“切片中”变成“生成向量中”，最后变成“可用”。

#### 3.1.15 常见追问

**问：为什么不直接按固定长度切，非要先按标题分节？**

固定长度切会把两个不相关的章节拼进同一个片段，一个向量表达两个主题，检索精度会下降；按标题分节可以保证一个片段不跨章节，还能记录来源路径。固定长度只在“单个段落超长”时作为最后兜底。

**问：为什么要同时有目标长度和最大长度？**

目标长度决定“什么时候可以考虑换片”，让片段大小比较均匀；最大长度是硬性上限，防止某个段落把片段撑得太大，超过嵌入模型的输入限制。只有目标长度，可能切得太碎；只有最大长度，片段会忽大忽小。

**问：重叠具体是怎么实现的？会不会浪费存储？**

输出当前片段后，取它最后 `overlap_chars` 个字，加上空行，再拼上新段落，作为下一片的开头。会多存一点重复文字，但重叠通常只占目标长度的 10% 到 20%，换来的是跨片句子至少有一片完整，值得。

**问：文档没有标题怎么办？标题层级跳跃怎么办？**

没有标题时，整篇正文会成为一节，标题和路径为空，上下文头只保留文档标题；如果文档标题也为空，就不加头。标题层级跳跃时，路径只包含实际出现的层级，不会自动补出不存在的中间级。

**问：为什么用字符数控制，而不是精确的词元数？**

精确词元数需要加载具体模型的分词器，换模型就要换算法。字符数是近似值，简单稳定；中文一个字大约一个词元，误差可以通过调整切片长度吸收。项目里另有一个粗略的词元估算函数，只用于展示。

**问：为什么不用现成的文本切分库？**

现成库（例如 LangChain 的文本切分器）功能更全，但会引入额外依赖；本项目规则不复杂，而且需要“标题路径”这种自定义定位信息，自己写一个纯函数更容易测试、更容易解释每一步。如果以后规则变复杂，再考虑引入库。

#### 3.1.16 本节面试复盘题（总结版 + 详细版）

**复盘题一：请按调用顺序讲一遍切片器的执行流程。**

总结版：

`split_document` 先纠偏参数，调用 `_split_sections` 按标题分节；每节按空行拆段，交给 `_pack_paragraphs` 装箱，超长段落由 `_split_long_paragraph` 按句子切开；最后 `_context_header` 加头、`estimate_tokens` 估算词元数，组装成 `TextChunk` 列表返回。

详细版：

入口在上传或重新切片时触发，参数来自启用中的索引版本。第一步纠正参数，保证目标长度不超过最大长度、重叠不为负。第二步 `_split_sections` 逐行扫描 Markdown，用标题栈维护“一级 / 二级”路径，遇到标题收上一节，结束时补收最后一节。第三步在每节内部用空行拆段落。第四步 `_pack_paragraphs` 用缓冲区累积段落：达到目标且再加会超上限，或者合并直接超上限，就输出当前片段，并用末尾若干字作为下一片开头；否则继续累积。超长段落先由 `_split_long_paragraph` 按句末标点切分，找不到标点才硬切。第五步 `_context_header` 拼“【文档标题｜章节路径】”，路径只留最后两级。第六步 `estimate_tokens` 估算词元数。最后把内容、词元数、标题、路径、节号装入 `TextChunk` 返回。

**复盘题二：目标长度、最大长度、重叠各解决什么问题？请用手算例子说明。**

总结版：

目标长度控制片段大小的均匀度，最大长度防止片段超限，重叠防止跨片句子两边都不完整。例子中目标 30、上限 60、重叠 8：第一段 34 字放进缓冲区，第二段 34 字合并后 70 字超过 60，于是输出第一段；取它最后 8 字加第二段作为下一片，得到 8 + 2 + 34 = 44 字。

详细版：

目标长度是“可以考虑换片”的信号，不是必须凑满的下限；一节本身很短时，不会为了凑数跨节拼接。最大长度是硬上限，任何片段都不应该超过它；当单个段落自己就超过上限时，由 `_split_long_paragraph` 先按句子切开。重叠是在输出当前片段后，取末尾 `overlap_chars` 个字放到下一片开头，让跨片句子至少有一片完整。代价是少量重复存储，收益是减少“两边都检索不到”的情况。

**复盘题三：超长段落怎么处理？为什么不能直接按固定长度切？**

总结版：

先按句号、问号、感叹号、分号把段落切成句子，再把句子往上限内装；只有一整句都超长、找不到标点时，才按固定长度硬切。按句子切是为了保证每一片内部语义完整，避免从句子中间断开导致两片都读不懂。

详细版：

`_split_long_paragraph` 先用正则表达式找出所有“到句末标点为止”的句子。缓冲区为空就先放第一句；再放下一句会超过上限，就先输出当前缓冲，再把这句放进新缓冲；如果某一句自己就超长，就用循环按固定长度切，保证每块不超过上限。固定长度硬切是最后兜底，因为从句子中间切开会产生“前半句在上一片、后半句在下一片”的问题，检索和阅读都会受影响。

**复盘题四：上下文头有什么作用？为什么切片器要设计成纯函数？**

总结版：

上下文头让片段脱离原文后仍然知道自己属于哪篇文档、哪一章节，既提升向量语义，也方便展示来源；纯函数让切片逻辑不依赖数据库和网络，测试简单、行为稳定、以后容易替换。

详细版：

片段被单独取出来后，只看到正文可能不知道在讲什么，例如只看到“颜色”不知道是谁的颜色。上下文头用“【文档标题｜章节路径】”补上归属，并且路径只保留最后两级、每部分最多 60 字，避免头部本身占用太多长度。纯函数的意义是：输入相同就输出相同，不在内部查数据库、不发网络请求，所以单元测试只要给一段文字就能验证；切片规则调整时也不会牵连数据库事务和外部服务。上游 `kb_service` 负责取数据和写库，切片器只负责文本处理，职责清晰。
