# MealMate 项目规则

## 技术选型与生产级标准（2026-11-26 起，暂定）

- 本项目整体对标**中小型公司真实生产级项目**的方案与技术标准：功能设计、数据模型、接口、权限、部署、测试、日志与可观测性都以“小团队能维护、能上线、能排障”为暂定目标，不按课堂练习或纯 Demo 标准实现。
- “生产级”不等于堆最复杂的技术。选型要与项目规模匹配：优先成熟稳定、容易维护、可观测、可降级、成本可控的方案，避免为了显得高级而引入用不上的中间件。
- **每次引入一项新技术，必须先让用户知道，并说明为什么引入。** 在动手实现前或方案说明中至少讲清：
  1. 这项技术是什么（新名词要用大白话解释，不使用未解释的缩写）；
  2. 它解决什么问题，不用它会出现什么后果；
  3. 市面上常用的同类技术还有哪些，各自优势和劣势；
  4. 中小型公司真实生产中大多数情况用什么；
  5. 本项目为什么选它，会新增哪些依赖、配置、费用或运维工作；
  6. 它不可用或配置错误时如何降级，会不会影响核心功能。
- 未经说明，不得直接引入新的框架、中间件、云服务、第三方接口或客户端依赖。
- 前端开发沿用用户已明确的偏好：前端技术栈内的常规实现不需要长篇解释；后端、数据库、缓存、消息队列、部署、监控、安全等非前端内容必须按用户规则详细解释并加注释。
- 引入新技术后，按既有规则同步更新 `docs/测试用例.md`、`docs/面试题/面试知识点与面试题.md` 和 `README.md`。

## 测试用例维护（2026-11-20 起）

- 每次更新项目功能（新增、修改、删除）时，必须同步更新测试用例，不允许只改代码不更新用例。
- 测试用例只维护 `docs/测试用例.md` 这一个文件，不新建其他测试用例文件，也不按模块拆分。
- 用例结构保持稳定：模块分组 + 稳定编号；已删除的功能要删除对应用例，不能留着误导执行。

## 开发范围（2026-11-19 起）

- 小程序端（`app_mini/`）暂停开发：后续需求不修改、不构建、不验证小程序。
- 后续客户端开发只考虑 Flutter App（`app_flutter/`）；接口设计、功能实现与验收均以 App 为准。
- 后端（`server/`）保持通用接口设计，但不为小程序单独做兼容或联调。
- 如某个需求确实必须改动小程序，先与用户确认，确认后再动。
